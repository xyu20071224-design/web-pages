一句话核心

信号的全部机制就是内核在目标进程的上下文里改写几位：发送 = 置一位 pending，阻塞 = 置一位 blocked，递送 = 算一次 pending & ~blocked 再清掉那一位。真正的难点不在位运算，而在处理器是与主程序并发的第二条逻辑流 —— 所以它只能调用异步信号安全的函数、访问共享数据前要阻塞信号。

2.3 问题：后台作业会变成永不回收的僵尸原第 18–19 页

课件第 18 页把话挑明：shell 是设计来长期运行的，不应该累积不需要的资源（内存、子进程、文件描述符）。上面这份代码对前台作业做对了 —— 它 wait 并回收了每一个前台子进程；但对后台作业完全没管：

  • 后台作业终止后会变成僵尸；
  • 它们永远不被回收，因为 shell（通常）不会终止；
  • 僵尸会占着内核里的进程表项，形成内存泄漏，严重时能把内核的内存耗光。

第 19 页用一个场景说明「后台作业」的必要性：unix> sleep 7200; rm /tmp/junk 会让 shell 卡住两小时；写成 unix> (sleep 7200 ; rm /tmp/junk) & 就立刻拿到提示符，输出 [1] 907。所谓后台作业，就是我们不想等它的那个进程。

僵尸（zombie）到底是什么
第 4 页复习里已经给出答案：exit 会「把进程置为僵尸状态」。僵尸是已经跑完、但父进程还没 wait 它的进程 —— 它只剩一个退出状态等着被取走。父进程取走状态的那一刻（reap，回收），内核才真正删掉这条记录。

2.4 异常控制流来救场原第 20 页

课件第 20 页给出一句话的解法：当后台进程完成时，内核会打断正常的处理来提醒我们。在 Unix 里，这个「提醒机制」就叫信号（signal） —— 于是 shell 不必轮询、也不必阻塞等待，只要在信号到来时把僵尸收掉即可。这句话也是接下来 40 多页的纲领。

3. 信号：概念、未决与阻塞原第 22–32 页

信号（signal）是一条小消息，通知某个进程「系统里发生了某类事件」。它的全部内容只有两样东西：信号的编号，以及「它到了」这件事本身 —— 没有参数、没有数据、没有顺序保证。

3.1 信号在异常控制流里的位置原第 22 页

课件的「（部分）分类」把 ECF 分成异步与同步两支：异步的是中断，同步的是陷阱、故障与终止，它们都由内核处理；而信号是另一条路 —— 内核对它的默认处置仍在核心里完成，但真正的反应可以由用户进程自己写的处理器来决定（第 5 节会展开）。这也是第 2 页把信号写成「内核软件 + 应用程序」的原因。

3.2 信号表原第 23 页

课件只列了五个信号，但每一个都值得记住：信号类型用 1–30 的小整数编号，每种类型有预设的默认动作，也对应一类固定的系统事件。

SIGKILL 的默认动作是终止，且课件特别注明它不能被覆盖（override）也不能被忽略 —— 换句话说，你在程序里写 signal(SIGKILL, …) 也不会生效。相对地，SIGINT（ctl-c）与 SIGTSTP（ctl-z）都是可以被程序改写的，这正是第 5 节 sigint.c 与第 9 节 restart.c 能玩出花样的前提。

3.3 未决（pending）与阻塞（blocked）原第 24–25 页

两条定义要先分清：发送（send，也叫 deliver）是内核在目标进程上下文里写下「有信号了」；接收（receive）则是进程被内核强迫对这个信号做出反应。两者之间隔着一段时间，这段时间里信号处于未决（pending）状态。规则有三条，全都来自「信号不是队列」这一个事实：

至多一个

任何类型最多只能有一个未决信号。若类型 k 已有一个未决信号，之后发给它的所有类型 k 信号都被丢弃。

可以阻塞

进程可以阻塞某些信号的接收。被阻塞的信号可以被发送但不会被接收，直到解除阻塞。

至多一次

一个未决信号至多被接收一次 —— 这直接判了「用信号数事件个数」的死刑（第 7 节）。

第 25 页给出内核视角的实现：内核在每个进程的上下文里维护两个位向量。pending 表示「已发送、尚未接收」的信号集合（内核递送类型 k 的信号时置第 k 位，进程接收时清第 k 位）；blocked 表示被阻塞的信号集合，可以用 sigprocmask 函数设置与清除，它还叫信号掩码（signal mask）。

4. 发送信号：进程组、/bin/kill 与键盘原第 33–37 页

内核为什么要发信号？课件第 26 页给出两种理由：内核自己检测到系统事件（例如除零 SIGFPE、子进程终止 SIGCHLD），或者别的进程调用 kill 系统调用要求它发。而收件人既可以是一个进程，也可以是一个进程组 —— 这正是键盘上那两个组合键的威力所在。

4.1 进程组原第 33 页

每个进程恰好属于一个进程组，进程组用它的「组长 pid」来命名（叫 pgid）。课件给的两个 API 是 getpgrp()（返回当前进程的进程组）与 setpgid()（修改某个进程的进程组）。第 33 页的图是本节的主角：shell 自己一组（pid=10, pgid=10），它派生出的前台作业是 20 号组（pid=20 带着两个子进程 pid=21、22，三者的 pgid 都是 20），另外两个后台作业各自成组（pgid=32 与 pgid=40）。

第 35 页接着说键盘：敲 ctrl-c（或 ctrl-z）时，内核把 SIGINT（或 SIGTSTP）发给前台进程组里的每一个作业。两者的默认动作不同 —— SIGINT 终止每个进程，SIGTSTP 停止（挂起）每个进程。

交互：进程组与作业控制 —— 敲 ctrl-c / ctrl-z / fg，看谁被打断
只有前台进程组收得到键盘信号
键盘事件由内核交给前台进程组；后台进程组碰不到键盘（不然你在 vim 里按 ctrl-c，后台的编译进程也会被误杀）。第 36 页的 ps w 输出里那个 + 号就是「属于前台进程组」的标记 —— ps w 之后紧跟的 ps 自己是 R+，而停止在 T 状态的 ./forks 17 就没有 +。

4.2 /bin/kill 程序与 kill 函数原第 34、37 页

/bin/kill 程序可以给一个进程或一个进程组发送任意信号。课件第 34 页用 forks 16 演示了「正数 = 单个进程、负数 = 整个进程组」这条规则：两个子进程的 pid 是 24818 与 24819，它们的 pgrp 是 24817（父进程的 pid）。

/bin/kill –9 24818  ← 只给进程 24818 发 SIGKILL
/bin/kill –9 –24817  ← 给进程组 24817 里的每个进程发 SIGKILL
交互：/bin/kill 目标解析器 —— 输入参数，看它会打到谁

第 37 页给出 C 里的对应写法（forks.c 的 fork12）：父进程 fork 出 N 个死循环的子进程，然后逐个 kill(pid[i], SIGINT)，最后用 wait 收尸，并用 WIFEXITED 判断子进程是「正常退出」还是「异常终止」—— 被信号杀死的子进程走的是 else 分支（打印 Child %d terminated abnormally）。

为什么输出是 abnormally
SIGINT 的默认动作是终止，但终止方式不是 exit：进程是被信号杀死的，没有返回退出码。所以 WIFEXITED(child_status) 为假，父进程打印的是「异常终止」那一行 —— 这正好给后面「WIFEXITED 只管正常退出」埋一个对照。

4.3 键盘中断的现场：ctrl-z 之后 ctrl-c原第 36 页

第 36 页是一段完整的实验记录：./forks 17 在前台跑着（父进程 28107、子进程 28108，同属 28107 组），按 ctrl-z 之后 shell 报 Suspended，两次 ps w 的输出里两个 forks 都变成 T（stopped）状态；随后 fg 把它拉回前台，再按 ctrl-c，两个进程就都消失了。

5. 接收信号与信号处理器原第 38–46 页

发送信号只是「置一位」，真正有戏的是接收：进程被内核强迫对信号做出反应。反应有三种，其中最有威力的一种要用户自己写代码 —— 即信号处理器（signal handler）。而处理器一旦登场，就带来了新的麻烦：它是一条与主程序并发的逻辑流。

5.2 内核怎么挑信号：pnb = pending & ~blocked原第 39–40 页

当内核从一个异常处理器返回、准备把控制权交给进程 p 时（第 39 页强调：所有上下文切换都是通过调用某个异常处理器发起的），它会做这样一段判断（第 40 页原文）：

pnb = pending & ~blocked

  • 如果 pnb == 0：把控制权交给 p 逻辑流里的下一条指令；
  • 否则：挑 pnb 里最小的非零位 k，强制 p 接收信号 k（这一次接收会触发某个动作），然后对所有非零位 k 重复，最后把控制权交给 p 的下一条指令。

5.3 默认动作的五种结局原第 41 页

每种信号类型都有一个预设的默认动作，只能是下列之一：进程终止；进程终止并 dump core；进程停止，直到被 SIGCONT 信号重启；进程忽略这个信号。

5.4 安装处理器：signal 函数原第 42–43 页

signal 函数修改「收到 signum 信号时的动作」：handler_t *signal(int signum, handler_t *handler)。handler 取三种值之一：SIG_IGN 忽略该类型信号；SIG_DFL 恢复默认动作；否则就是一个用户级处理器的地址。课件把这几个术语钉得很清楚：把处理器交给内核叫安装（install），执行处理器叫捕获（catch）或处理（handle）；处理器 return 时，控制权回到被信号打断的那条指令。

课件连用两页强调同一件事：信号处理器是一条独立的逻辑流（不是独立进程），它与主程序并发运行；不过这条流只存在到它返回主程序为止。第 46 页再往前推一步：处理器自己也能被打断 —— 主程序捕获信号 s 进入处理器 S，S 运行期间又来了信号 t，控制权转给处理器 T，T 返回 S，S 再返回主程序。

6. 阻塞信号、安全处理器与异步信号安全原第 47–53 页

处理器与主程序共享同一份全局数据，而且随时可能在任何一条指令之间插进来 —— 于是「怎么写处理器」变成了一门手艺。课件先给机制（阻塞），再给六条指南，最后落在一份函数白名单上。

6.1 隐式阻塞与显式阻塞原第 47–48 页

隐式阻塞机制

内核会自动阻塞「当前正在处理的那个类型」的所有未决信号。例如 SIGINT 的处理器运行期间，另一个 SIGINT 不可能把它打断 —— 所以处理器不必可重入地防自己。

显式阻塞机制

用 sigprocmask 加四个集合操作函数：sigemptyset（空集）、sigfillset（加入所有信号）、sigaddset（加入一个）、sigdelset（删掉一个）。

第 48 页给出一段「暂时屏蔽 SIGINT」的标准模板：先 Sigemptyset + Sigaddset(&mask, SIGINT) 造出集合，用 Sigprocmask(SIG_BLOCK, &mask, &prev_mask) 阻塞它并保存原来的掩码，把不想被打断的代码放进中间，最后用 Sigprocmask(SIG_SETMASK, &prev_mask, NULL) 恢复原掩码（从而解除阻塞）。

6.2 为什么处理器容易写错原第 49–50 页

第 49 页点题：处理器与主程序并发，而且共享同一批全局数据结构，这些结构可能被破坏。课件在第 50 页给出六条指南：

指南内容课件给的理由 / 例子
G0让处理器尽量简单例如：设一个全局标志然后返回
G1处理器里只调用异步信号安全的函数printf、sprintf、malloc、exit 都不安全！
G2进入与退出时保存、恢复 errno免得别的处理器覆盖掉你的 errno
G3访问共享数据结构时临时阻塞所有信号防止可能的破坏
G4全局变量声明为 volatile防止编译器把它放进寄存器

G4 与 G5 为什么必须放在一起
volatile 管的是编译器：别把变量缓存进寄存器，否则主循环可能永远读不到处理器写下的新值（第 60–61 页的 while (!pid) 就靠它）。sig_atomic_t 管的是读改写不可分割：它保证单次读或单次写在硬件层面是原子的。两者合起来，一个标志位才能在「一条流写、另一条流读」的情况下可信 —— 而 flag++ 是「读 + 写」两步，超出 sig_atomic_t 的承诺，所以 G5 特意点名。

7. 并发陷阱：信号不排队、竞态与 sigsuspend原第 54–63 页

这一节是本讲的深水区。它把第 3 节那条「信号不是队列」的规则变成三个真实的 bug：用信号数子进程会挂住、父子进程谁先跑会让作业列表错乱、等待信号的三段式写法都有毛病 —— 最后一个由 sigsuspend 收场。

7.1 陷阱一：不能用信号计数原第 54–55 页

课件的 fork14 程序 fork 出 5 个子进程，让它们几乎同时退出（都是 Sleep(1); exit(0)），父进程则用一个信号处理器来数数：处理器里 ccount--，主程序 while (ccount > 0) ; 自旋等它减到 0。课件自己给这页贴了标签：这段代码是错的 —— 实跑结果是只回收了两个孩子就永久挂住。

linux> ./forks 14
Handler reaped child 23240
Handler reaped child 23241
. . .（挂住）

原因是第 24 页学的规则在这里报应：每种信号只有一个未决位。5 个子进程在处理器运行期间陆续退出，那些 SIGCHLD 里只有第一个能把 pending 位置 1，其余全被丢弃；于是处理器只跑了两次，ccount 停在 3，主程序永远转下去。结论：不能用信号去统计事件个数。

7.2 陷阱二：父子谁先跑 —— addjob / deletejob 竞态原第 56–58 页

第 56 页的 procmask1.c 里，父进程 fork 之后才 addjob(pid)，而 SIGCHLD 处理器里做的是 deletejob(pid)。问题在于代码假设了父进程总在子进程之前运行：如果子进程跑得足够快、在父进程 addjob 之前就退出，处理器会先执行 deletejob —— 删掉一个还没被加进列表的作业。第 57 页的处理器用「阻塞所有信号」保护自己的临界区；第 58 页的 procmask2.c 给出真正的修法：在 fork 之前就阻塞 SIGCHLD，fork 后在子进程里先恢复掩码（这样孩子在 execve 前不会被滞留的信号打断），父进程 addjob 之后再解除阻塞 —— 于是「加作业」与「收信号」之间不可能再插进来。

7.4 sigsuspend：原子地「换掩码再挂起」原第 62–63 页

int sigsuspend(const sigset_t *mask) 的语义是：原子地（不可打断地）把信号掩码换成 *mask，然后挂起进程直到收到一个信号；返回时掩码恢复到调用前的值。它存在的唯一理由就是补上第 61 页那条缝：while (!pid) pause(); 的问题在于「检查 pid」与「进入 pause」之间可能收到信号，而 sigsuspend 把「换掩码」和「挂起」合成一个不可分割的动作，信号要么在挂起前就被接收（此时 pid 已非零，循环条件直接为假），要么在挂起期间唤醒进程。

勘误：第 62 页「等价代码」的第一行应为 SIG_SETMASK
课件第 62 页把 sigsuspend(&mask) 写成「下面三行的原子版本」：sigprocmask(SIG_BLOCK, &mask, &prev); / pause(); / sigprocmask(SIG_SETMASK, &prev, NULL);。 第一行写错了：sigsuspend 的语义是把掩码整体替换为 *mask（SIG_SETMASK），而不是把 mask 里的信号加进阻塞集合（SIG_BLOCK）。按 SIG_BLOCK 写的话，那些本就阻塞着的信号永远不会被解除阻塞：课件第 63 页的 sigsuspend.c 里 Sigsuspend(&prev)（prev 是不含 SIGCHLD 的旧掩码）将无法解除 SIGCHLD 的阻塞，程序会死锁 —— 而课件的本意（以及第 61 页那段竞态分析）恰恰是「临时解除阻塞」。本页按 sigprocmask(SIG_SETMASK, &mask, &prev) 呈现，并用 C 实测验证过两种写法的差别（见报告）。
一句话记住 sigsuspend
sigsuspend(&prev) 在 sigsuspend.c 里的角色是「原子地解除 SIGCHLD 的阻塞并睡到它到来」：prev 是 Sigprocmask(SIG_BLOCK, &mask, &prev) 保存下来的旧掩码，也就是「SIGCHLD 尚未被阻塞」的那个版本。用旧掩码去挂起，等于把阻塞临时撤销 —— 这就是它比 pause() 强的地方。

8. 非本地跳转：setjmp 与 longjmp原第 65–70 页

信号负责「进程之间」的异常控制流，这一节负责「一个进程内部」的：从深层嵌套的函数里直接跳回上层，跳过中间所有的返回。机制只有两个函数，但用错的代价是崩溃 —— 因为它受栈纪律约束。

8.1 setjmp：在栈上留一个书签原第 65 页

int setjmp(jmp_buf j) 是「把当前的位置记在 j 里」：必须在 longjmp 之前调用，它为后续的 longjmp 标识一个「返回点」。实现上，它把当前的寄存器上下文、栈指针与 PC 值存进 jmp_buf，然后返回 0。课件用一个短语记住它的调用特征：调用一次，返回一次或多次。

8.2 longjmp：把书签读出来并跳过去原第 66 页

void longjmp(jmp_buf j, int i) 的语义是：从 j 记住的那个 setjmp 处再次返回，只不过这次返回的是 i 而不是 0。必须在 setjmp 之后调用；调用一次，永不返回。实现上是三步：恢复 j 里的寄存器上下文（栈指针、基址指针、PC 值）→ 把返回值 %eax 设成 i → 跳到 j 里记录的 PC 处。

8.3 例子：从深层函数直接回到 main原第 67–68 页

目标是从深层嵌套的函数直接返回原始调用者。foo 出错就 longjmp(buf, 1)，bar 出错就 longjmp(buf, 2)，而 main 只用一个 switch (setjmp(buf)) 就把三种情况分辨出来 —— 这就是非本地跳转最典型的用法：一处集中处理分散在各层的错误。

8.4 限制：只能在栈纪律之内跳原第 69–70 页

课件用两页反复强调同一条限制：非本地跳转只在栈纪律（stack discipline）之内成立 —— 你只能跳到「已经被调用、但还没有返回」的那个函数的环境里去。

  • 第 69 页是合法情形：P1 调 P2，P2 调 P3，P3 里 longjmp(env, 1) 跳回 P1 的 setjmp —— 此时 P1 的栈帧仍然活着，跳回去完全正确；
  • 第 70 页是非法情形：如果 P2 里 setjmp、但 P2 已经返回到 P1 之后才有人 longjmp(env, 1)，那么 env 指向的栈帧早已不存在 —— 课件在这张图上直接打了一个 X。
这条限制解释了信号处理器为什么偏爱 sigsetjmp
第 71 页的 restart.c 用的是 sigsetjmp/siglongjmp 而不是 setjmp/longjmp：在信号处理器里跳转时，除了寄存器上下文，还必须把信号的阻塞掩码一起恢复，否则跳回来之后掩码会停在「处理器运行期间」的状态。setjmp 系列不保存掩码，sigsetjmp 系列会保存（第二个参数非零表示要保存）—— 这是「栈纪律」之外的第二重纪律。

9. 综合案例：按下 ctrl-c 就重启的程序原第 71 页

课件把信号与非本地跳转合起来做了一个只有 20 行的程序：restart.c。它故意把 ctrl-c 的默认动作（终止）改成「回到程序开头」，于是你在终端里怎么按都杀不死它 —— 除非用 SIGKILL。

#include "csapp.h"
sigjmp_buf buf;
 
void handler(int sig)
{
    siglongjmp(buf, 1);
}
 
int main()
{
    if (!sigsetjmp(buf, 1)) {
        Signal(SIGINT, handler);
        Sio_puts("starting\n");
    }
    else
        Sio_puts("restarting\n");
 
    while(1) {
        Sleep(1);
        Sio_puts("processing...\n");
    }
    exit(0); /* Control never reaches here */
}
交互：restart.c 模拟 —— 跑起来，然后拿 ctrl-c 打它
这 20 行把本讲的全部要点都串起来了
信号安装（Signal(SIGINT, handler)）改写了 ctrl-c 的默认动作；处理器里只做一件事 —— siglongjmp（正好符合 G0「尽量简单」）；非本地跳转把控制权从处理器直接送回 main 的 sigsetjmp 处；而 sig 前缀保证了跳转时信号掩码被一并恢复。最后那句注释 exit(0); /* Control never reaches here */ 也不只是玩笑 —— 主循环是 while(1)，正常路径永远走不到 exit。

跳转方向两者都只能在栈纪律之内：只能跳回「已被调用但尚未返回」的函数（第 69–70 页）

10. 总结与测验原第 72 页

第 72 页用两段话收官：信号提供进程级的异常处理（可以由用户程序产生、可以声明处理器来定义效果、写处理器时必须非常小心）；非本地跳转提供进程内部的异常控制流（但受栈纪律约束）。

信号：一句话流程

发送（置 pending 位）
→ 未决（pending）
→ 被阻塞则先等着（blocked）
→ 内核算 pnb = pending & ~blocked
→ 取最小非零位 k → 强制接收 → 清位 k

本讲的六个坑
  • 信号不排队：不能用它计数（第 54 页）
  • 处理器里不能调用 printf/malloc/exit（第 51 页）
  • 访问共享数据前要阻塞信号（G3）
  • 全局标志要 volatile sig_atomic_t（G4/G5）
  • while (!pid) pause(); 有竞态，要用 sigsuspend（第 61–62 页）
  • 非本地跳转跳不回已返回的函数（第 70 页）
