一句话核心

堆就是一段由分配器自己记账的连续虚拟内存。分配器的全部工作只有四件事：从空闲内存里挑一块（放置策略）、切下需要的部分（拆分）、把块头写回去（释放）、把相邻空闲块拼起来（合并）。四种分配器（隐式 / 显式 / 分离 / 按大小排序）的区别只在「空闲块怎么找」和「额外空间花在哪」。

1.2 malloc 包的契约原第 5 页

课件把 stdlib.h 里这套接口的契约写得很完整，逐条对应：

接口契约（原第 5 页原文的展开）
void *malloc(size_t size)成功时返回一个指向至少 size 字节的块的指针，且在 x86-64 上对齐到 16 字节边界；失败时返回 NULL（0）并把 errno 设为 ENOMEM；本讲配套实现约定 size == 0 时返回 NULL
void free(void *p)把 p 指向的块还给空闲内存池；p必须来自之前某次 malloc / calloc / realloc 的返回值
void *calloc(size_t n, size_t size)是 malloc 的变体，把分配到的块清零
void *realloc(void *p, size_t size)改变一个已分配块的大小
void *sbrk(intptr_t incr)分配器内部用它来让堆变大或变小（不是给应用调的）
补一句口径（非课件原文）
课件把「size == 0 返回 NULL」写成了 malloc 契约的一部分，这是本讲配套实现 mm-reference.c 的选择。标准（POSIX）在这里留了余地：malloc(0) 也可以返回一个「唯一的、可以安全 free 的指针」，glibc 就是这么做的。做题时按课件的口径，读真实代码时按标准的口径。

1.3 程序员怎么用它原第 6 页

第 6 页那段 foo() 是本讲的样板代码：申请 → 检查 NULL → 使用 → 归还。四步缺一不可，后面第 9、10 节讲的所有 bug 都是漏掉其中某一步造成的。

void foo(long n) {
  long i, *p;
  /* Allocate a block of n longs */
  p = (long *) malloc(n * sizeof(long));
  if (p == NULL) { perror("malloc"); exit(0); }
  /* Initialize allocated block */
  for (i=0; i<n; i++) p[i] = i;
  /* Do something with p */
  /* Return allocated block to the heap */
  free(p);
}

2. 分配器的约束与性能指标原第 10–15 页

第 10 页列出分配器必须遵守的规矩，第 11–15 页给出两把尺子：吞吐率和峰值内存利用率。课件反复强调一件事：这两把尺子经常互相打架。

2.1 双方的约束原第 10 页

应用可以做的
  • 可以发出任意顺序的 malloc / free 请求；
  • free 的参数必须来自之前 malloc 的块。
分配器必须忍的
  • 不能控制块的数量和大小；
  • 必须立即响应 malloc —— 不能重排、不能缓冲请求；
  • 只能把块放进空闲内存里；
  • 必须满足对齐要求（64 位系统上 16 字节）；
  • 只能改空闲内存，已分配的块一动不能动。
课件的设问：为什么不允许压缩（compaction）？
移动一个已分配的块意味着它的地址变了，而应用手里握着的是地址（指针）—— 分配器根本不知道有谁存了这个地址，也没有办法去更新它们。所以压缩只有在能「重定位所有指针」的环境里才可能，这正是垃圾回收器（第 11 节）能做的事，也是 C 的 malloc 做不到的事。

2.2 尺子一：吞吐率原第 11 页

给定请求序列 R0, R1, …, Rn−1，吞吐率 = 单位时间内完成的请求数。课件给的例子是 5000 次 malloc 加 5000 次 free 共耗时 10 秒，于是吞吐率是 1000 次操作/秒。

3.1 内部碎片原第 17–18 页

3. 分离空闲链表按大小分类，每类一条空闲链表同显式链表，外加一个链表头数组接近常数（对数级）第 8 节
4. 按大小排序的块把空闲块按大小放进平衡树（如红黑树），长度当 key树指针对数级，且近似 best fit页面只作介绍
四种方法的共同点
不管用哪种，块头里的长度字段都是必需的（否则释放时不知道块有多大），合并与拆分也都是必需的。差别只在「找空闲块快不快」和「每个块多花多少字节」。

4. 隐式空闲链表原第 24–35 页

第一种方案最省脑力：不额外维护任何链表，靠块头里的长度字段把堆里所有块串成一条「隐式」的链 —— 下一个块就是「当前块地址 + 当前块大小」。代价是分配时可能要走过整个堆。

4.1 块头：一个字装下两件事原第 25 页

每个块同时需要大小和是否已分配。存两个字太浪费，课件给出的标准技巧是：块是对齐的，所以大小字段的低位永远是 0 —— 拿一位来当标志位。

+--------+----------------------------+
| size | a |   低 4 位空闲（size 是 16 的倍数，低 4 位总是 0）
+--------+---+   a = 1：已分配块  a = 0：空闲块
  Size：整个块的大小（含块头）  读取时必须把标志位掩掉

课件特别提醒：读 Size 时一定要掩掉这一位。第 28 页的两行代码就是这件事的全部：

get_alloc(block)  →  return header & 0x1;     /* 取标志位 */
get_size(block)   →  return header & ~0xfL;   /* 掩掉低 4 位才是大小 */
write_header(block, size, alloc)  →  block->header = size | alloc;
交互：块头编解码器 —— 在「大小 + 标志位」和「头部字」之间来回算

4.3 走遍所有块：find_next原第 29 页

「隐式链表」的全部精髓就是一行加地址：下一个块 = (char*)block + get_size(block)。有了它，从 heap_start 一直加到 heap_end 就遍历完了整个堆。

static block_t *find_next(block_t *block)
{
  return (block_t *) ((unsigned char *) block + get_size(block));
}
交互：块遍历器 —— 输入块序列，逐块走（含越界与非法头的检测）

4.4 找一块够大的空闲块：三种放置策略原第 30–31 页

课件的 find_fit 就是「从 heap_start 走一遍，第一个「空闲且够大」的块就用它，都没有就返回 NULL」：

static block_t *find_fit(size_t asize) {
  for (block = heap_start; block != heap_end; block = find_next(block))
    if (!get_alloc(block) && (asize <= get_size(block))) return block;
  return NULL;   // 没找到
}
策略怎么挑代价后果（课件原话）
first fit从头扫，第一个够大的就用线性（与总块数成正比）会在链表开头留下「小碎块（splinters）」
next fit像 first fit，但从上次搜索结束的地方接着扫通常比 first fit 快（避免重复扫描没用的块）有研究表明碎片反而更严重
best fit扫全表，挑剩下最少的那个够大的块通常比 first fit 慢把碎块留小，内存利用率通常更好；但仍是贪心，不保证最优
交互：三种策略同台比较 —— 同一串空闲块、同一个请求，看它们各挑谁

4.6 拆分：多出来的空间怎么办原第 33–34 页

如果挑中的空闲块比需要的大得多，就把它的尾巴切出来放回链表。第 33 页的图：原布局 32 32 48 16 8，split_block(p, 32) 之后变成 32 32 32 16 16 8 —— 48 被切成 32（拿走）+ 16（留下）。

static void split_block(block_t *block, size_t asize) {  /* 第 34 页给的是不完整版本 */
  size_t block_size = get_size(block);
  if ((block_size - asize) >= min_block_size) {  /* 剩下的够不够一个最小块？ */
    write_header(block, asize, true);           /* 前面这块：要的大小 + 已分配 */
    block_t *block_next = find_next(block);
    write_header(block_next, block_size - asize, false);
    /* 完整版还要写两边的新脚部，见第 41 页 */
  }
}
为什么要设 min_block_size 这道门槛
如果一个块拆完剩下的零头连「块头 + 脚部」都装不下（本讲实现里是 16 字节），那这个零头既没法再被分配，又永远留在链表里被反复扫描 —— 纯亏。所以剩下不足 min_block_size 时干脆不拆，整块给出去（多出来的部分算内碎片）。这个门槛在页面模拟器里叫「拆分阈值」，可以自己改着玩。

5. 合并与边界标记（含堆模拟器）原第 36–49 页

这一节是本讲的技术核心：怎么在常数时间内把一个刚释放的块和它左右邻居拼起来。答案只有一个字 —— 脚部（footer）。第 38 页借 Knuth 的书把这项技术命名为边界标记（boundary tag），并注明「重要且通用」。

5.1 与后一个块合并原第 36–37 页

5.5 堆的整体结构与两个哨兵原第 47 页

6. 无边界标记的优化与策略总结原第 50–57 页

脚部很好用，但它永远用不上「空闲块才需要被找」这个事实 —— 已分配的块没人会去读它的脚部。于是可以省掉一半脚部，代价是块头里多塞一位。

6.1 脚部的代价与优化空间原第 50–51 页

第 50 页先自问自答：脚部带来内部碎片，能优化吗？「哪些块需要脚部？」—— 只有空闲块需要。因为脚部的唯一用途是「让后一个块能找到我、知道我的大小」，而合并只会发生在空闲块旁边。

第 51 页给出做法：块大小是 16 的倍数，所以块头的低 4 位是空的，用其中两位：

+--------+----+----+    a = 1：本块已分配   a = 0：本块空闲
| size | b1 | b0 |    b1 = 1：前一个块已分配  b1 = 0：前一个块空闲
+--------+----+----+    课件写法：(previous block allocated)<<1 | (current block allocated)

有了 b1，释放一个块时不用再去看前一个块的脚部就能知道它是不是空闲；只有当 b1 = 0 时才去读 header - 8 那个空块的脚部拿它的 size。于是已分配块可以不带脚部，只有空闲块带 —— 内碎片直接省掉一个字/块。

交互：两位块头解码器 —— 拨前后状态，看块头的位与释放时的动作

6.4 隐式链表小结原第 57 页

  • 实现非常简单；

7. 显式空闲链表原第 58–69 页

隐式链表的分配要走过堆里所有的块；显式空闲链表把空闲块单独串成一条双向链表，于是分配只走「空闲块」。代价是每个空闲块要空出两个字放指针 —— 但因为只有空闲块需要，这个代价在内存紧的时候反而划算。

7.1 空闲块里放什么原第 59–61 页

课件把两种方法的图并排放在第 59 页：隐式链表用长度串起所有块，显式链表用指针把空闲块串起来。空闲块的载荷区本来没人用，正好拿来放两个指针：

已分配块： [ Size | a ][ payload … ][ (脚部) ]
空闲块：    [ Size | a ][ Next ][ Prev ][ … ][ Size | a ]

关键的三句话：① 「下一个」空闲块在内存里可能离得很远，所以必须存前向/后向指针，光靠大小走不过去；② 仍然需要边界标记来做合并 —— 因为合并要按内存顺序找相邻块，而链表顺序是另一回事；③ 因为空闲块里要放两个字，本讲实现的最小块大小从 16 变成 32 字节。

8.1 尺寸类原第 71 页

每个尺寸类（size class）一条空闲链表。课件第 71 页画了三个例子：16（每个小尺寸单独一类）、32–48、64–∞；文字说明里补了两条规则：

  • 大尺寸：按 2 的幂分组 —— 课件原文写作 [2i + 1, 2i+1]，即每个尺寸类覆盖一个二倍区间。

8.2 分配与释放原第 72–73 页

分配一个 n 字节的块
  1. 在 n 对应的尺寸类里做 first fit（找 size > n 的块）；
  2. 找到 → 拆分，把余料放进它该去的那个类；
  3. 找不到 → 试下一个更大的类，一直往上试；
  4. 所有类都试完 → 用 sbrk 向 OS 再要一块堆内存，从新内存里切 n 字节，剩下的作为一个空闲块放进合适的类。
释放一个块
  1. 合并（与相邻空闲块，做法同第 5 节）；
  2. 把合并结果放进它尺寸对应的类。
为什么它又块又省（课件原话）
吞吐率更高：如果类按 2 的幂划分，找到合适的类只要 log 时间，而线性搜索是线性时间。
利用率更好：在「接近请求大小」的那个类里做 first fit，近似于在整个堆上做 best fit。极端情况下，如果每个块大小自成一类，那就等价于 best fit。

10.1 陷阱 4：引用不存在的变量原第 86 页

int *foo() {
  int val;
  return &val;   /* 函数一返回，val 所在的栈帧就失效了 */
}

局部变量在函数返回时就消失了。返回它的地址得到的是一个「悬空指针」：那块栈空间马上会被别的调用覆盖。正确做法是 malloc（堆上的块在 free 之前一直有效）或者让调用方传地址进来。

10.2 陷阱 5：重复释放原第 87 页

x = malloc(N*sizeof(int));
<manipulate x>
free(x);         /* 第一次：正确 */
y = malloc(M*sizeof(int));  /* y 很可能就落在刚释放的 x 上 */
<manipulate y>
free(x);         /* 第二次：把 y 给释放了！ */

课件的批注是 Nasty!。第二次 free(x) 释放的其实是已经属于 y 的那块内存：此后 x 和 y 指向同一块，其中任何一个被再次分配出去，两个「活」指针就会互相踩。更糟的是，合并逻辑会把这块内存和它的邻居拼起来 —— 堆的元数据从此错乱，崩溃点离 bug 点十万八千里。

10.3 陷阱 6：引用已释放的块原第 88 页

x = malloc(N*sizeof(int));
free(x);
…
y = malloc(M*sizeof(int));   /* 拿到了 x 原来那块 */
for (i=0; i<M; i++) y[i] = x[i]++;  /* 通过已经失效的 x 读写 */

课件的批注是 Evil!。程序「看起来在工作」—— 因为 x 和 y 恰好指向同一块内存，写入生效了。但这是未定义行为：换个分配器、换个执行路径就不成立了。注意 x[i]++ 还顺手改了 y 的数据。

10.4 陷阱 7：内存泄漏原第 89–90 页

第一种：压根没释放。函数返回时那块内存再也没有指针指向它，可分配器不知道 —— 它只会记得「这块已分配」。

  int *x = malloc(N*sizeof(int));
  return;   /* x 没了，块还在 */

第二种更隐蔽：只释放数据结构的头，漏掉后面的链。第 90 页的链表只 free(head)，后续节点全部泄漏 —— 这是「半释放」的典型。

课件的定性是 Slow, long-term killer!：单次泄漏几字节，看不出问题；服务器跑几周之后 malloc 开始返回 NULL，或者被 OOM killer 干掉。

11. 垃圾回收原第 92–100 页

显式分配器把「什么时候还」交给了程序员，程序员就会忘。隐式分配器的思路是：应用只管申请，回收由内存管理器代劳 —— 它必须能自己判断「这块内存以后还用得到吗」。这一节的答案出人意料地简单：没人能指向它，就用不到了。

11.1 垃圾回收是什么原第 93–94 页

垃圾回收（garbage collection）：自动回收堆上分配过的存储 —— 应用永远不需要显式释放。课件给的例子一眼就能看懂：

void foo() {
  int *p = malloc(128);
  return;  /* p 这个块从此成为垃圾 */
}

它在动态语言里是常态（Python、Ruby、Java、Perl、ML、Lisp、Mathematica 都有）；C / C++ 也有变体 —— 保守的垃圾回收器（conservative GC），但课件提醒：它不一定能回收所有垃圾。

内存管理器怎么知道一块内存以后用不到了？课件给了两条：

  • 原则上不可能准确预测未来 —— 未来用不用得到取决于条件分支；
  • 但可以退一步：如果没有任何指针指向它，它就一定用不到了。

为此必须对指针做三个假设：内存管理器能区分指针和非指针；所有指针都指向块的起始地址；指针不能被藏起来（例如先强转成 int 再转回来）。

11.4 标记 - 清除原第 97–99 页

第 97 页给出流程：可以架在 malloc/free 之上 —— 一直用 malloc 分配，直到「空间用尽」；这时：

  1. 在每个块的块头里留一个额外的标记位（mark bit）；
  2. 标记（mark）：从根开始，把每个可达块的标记位置 1；
  3. 清除（sweep）：扫描所有块，把没有标记的已分配块 free 掉。
交互：标记 - 清除模拟器 —— 从根出发标记，再扫掉垃圾

课件第 99 页的伪代码把这两步写成了两个函数。标记用深度优先遍历：

ptr mark(ptr p) {
  if (!is_ptr(p)) return;            // 不是指针 → 什么都不做
  if (markBitSet(p)) return;         // 已经标记过 → 什么都不做
  setMarkBit(p);                    // 打上标记
  for (i=0; i < length(p); i++)  // 对块里的每个字
    mark(p[i]);                    // 递归下去
}

清除用长度字段走向下一个块（这正是第 4 节那个 find_next）：

ptr sweep(ptr p, ptr end) {
  while (p < end) {                  // 扫遍整个堆
    if markBitSet(p)                 // 到过这里？
      clearMarkBit();                 // 是 → 只需清掉标记位
    else if (allocateBitSet(p))     // 从没到过：它是已分配的吗？
      free(p);                      // 是 → 它是垃圾，释放
    p += length(p);                    // 走到下一个块
  }
}

（伪代码里的 length(b)、is_ptr(p)、get_roots() 这些「指令」的假设都在第 98 页：应用只能用 new(n) 申请、read(b,i) / write(b,i,v) 读写；每个块有一个块头字，用 b[-1] 寻址；回收器用到 is_ptr(p)（判断 p 是不是指针）、length(b)（块长，不含块头）、get_roots()（拿到所有根）。）

11.5 C 里的保守标记 - 清除原第 100 页

给 C 程序做 GC 有个额外的麻烦：指针可以指向块的中间，所以「所有指针都指向块首」这个假设不成立。于是：

  • is_ptr() 的判断方式是「这个字是否落在某个已分配块里」；
  • 要标记块头，就得从块中间的地址反推块首 —— 课件给的办法是用一棵平衡二叉树记录所有已分配块（key 是块的首地址）；
  • 树的指针就存在块头里（多用两个字）；左子树放更小地址，右子树放更大地址。
为什么叫「保守」
因为它不区分真正的指针和长得像指针的整数：只要某个字看起来指向某个已分配块，它就当作指针、把那块当作可达。宁可漏回收（假活），绝不误回收（那样程序会崩）。所以课件说它「不一定能回收所有垃圾」。

第 103 页用 int (*(*f())[13])() 演示了「一层一层往里读」的过程，每剥一层就把已知部分换成一句人话：
