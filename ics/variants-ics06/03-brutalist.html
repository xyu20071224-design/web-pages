课程导览原第 1–3 页

北京大学《计算机系统导论》第 6 讲：机器级编程 III —— 过程（procedures）。上一讲看清了「程序怎么决定下一步走哪」，这一讲看清「函数调用是怎么实现的」：怎么跳过去、把数据带过去、把现场保住，然后再干干净净地回来。

本讲提纲
  1. 过程的三种机制（mechanisms）
  2. 栈结构：push / pop
  3. 调用约定（calling conventions）：
    传递控制 · 传递数据 · 管理局部数据
  4. 递归的完整图景
一句话核心

机器层没有「函数」这个概念。过程调用的全部秘密就是两条指令 —— call 把返回地址压栈后跳过去，ret 把它弹出来跳回来；剩下的（参数怎么传、局部变量放哪、谁的寄存器能改）都是写在 ABI 里的约定。

和上一讲的衔接

第 5 讲的跳转都是「跳过去就不回来了」或者「跳到固定标签」。这一讲的 call 多做一件事：把回来的路记在栈上。这一条小小的差别，就撑起了整个函数调用、递归和 mutual recursion。

1. 过程的机制与 ABI原第 4–9 页

课件先用 5 页把「一次过程调用要干什么」拆成三种机制 —— 这一节的结论会贯穿全讲：机制靠机器指令实现，但「怎么用」是人为约定。

1.1 三种机制原第 4–7 页

课件用一对最小的调用方 / 被调方展示三种机制各要做什么：

P(…) {
  • y = Q(x);
  • print(y)
}
int Q(int i)
{
  int t = 3*i;
  int v[10];
  return v[t];
}
机制要做什么落在 P/Q 的哪里
传递控制
passing control		跳到过程代码的开头；结束后来到返回点y = Q(x) 要跳进 Q，Q 结束要回到 print(y)
传递数据
passing data		把过程参数（arguments）递进去；把返回值带回来x 进 Q，return v[t] 回到 P 的 y
内存管理
memory management		执行期间分配空间；返回时释放Q 的 t 和 v[10] 要在执行期间有地方放

课件强调：这三种机制全部用机器指令实现；而 x86-64 对一次具体的过程调用，只实现它需要的那部分机制（例如 Q 若能把所有局部变量都放进寄存器，就不必动栈）。

谁决定「怎么做」？—— 应用二进制接口（ABI）原第 8 页
课件原话：「Machine instructions implement the mechanisms, but the choices are determined by designers. These choices make up the Application Binary Interface (ABI).」
指令只提供了「能这么做」的能力；参数放在哪个寄存器、栈往哪边长、谁的寄存器不能动 —— 这些选择是设计者定下的约定，合起来就是 ABI。本讲后面所有「约定」（调用约定、寄存器保存约定）都是 ABI 的一部分。
交互：三种机制分别靠哪些指令实现

2. x86-64 栈：push 与 pop原第 10–17 页

栈是这一讲的主角。先把它的三条物理事实钉死：它就是一段普通内存；它向低地址生长；%rsp 永远指着「栈顶」那个元素。

2.1 栈在哪里、往哪边长原第 10–12 页

课件把栈定义为「用栈纪律（stack discipline）管理的一段内存区域」：内存本身就是一个字节一个大数组，不同区域有不同用途（这跟 ABI 一样，是策略决定，不是硬件限制）。x86-64 的栈在内存高地址一端，并且 grows toward lower addresses —— 向低地址方向生长：

事实内容
栈底（Stack “Bottom”）栈在高地址一端的起点，地址最大
生长方向向低地址生长（Increasing Addresses 与生长方向相反）
栈指针 %rsp保存最低的栈地址 —— 也就是「栈顶（Stack “Top”）」元素的地址
最容易拧巴的一件事：「栈顶」是地址最小的一端
日常语言里「往箱顶摞东西」是往高处摞；x86-64 的栈是往低地址摞。所以「压栈」让 %rsp 变小，「弹栈」让它变大。课件图里「Stack “Bottom”」在上（高地址）、「Stack “Top”」在下（低地址），第一次看别被左右上下绕晕。

2.2 pushq Src：压栈原第 13–14 页

三步，顺序固定：

步动作效果
1取操作数从 Src 读出 val
2%rsp −= 8栈顶向上（低地址）让出一个 8 字节格子
3写入内存把 val 写到 %rsp 新指向的地址

2.3 popq Dest：弹栈原第 15–17 页

步动作效果
1读内存读出 %rsp 指向的值 val
2%rsp += 8栈顶退回高地址
3存入 Destval 写进 Dest（通常是个寄存器）
课件特意用一整页强调：pop 不擦除内存
「The memory doesn't change, only the value of %rsp」—— 弹栈后那个格子里的 8 个字节原封不动地留在原地，只是 %rsp 已经越过它，它从此成了「栈外的垃圾」。这就是后面「返回地址弹掉了但还在栈上」「旧栈帧的数据能被越界读到」一类现象的物理根源。

3. 传递控制：call 与 ret原第 18–24 页

有了栈，控制传递只差一对指令：call 负责走，ret 负责回。它们合起来就是第 1 节说的第一种机制。

3.1 贯穿本讲的例子：multstore / mult2原第 19 页

C 代码
void multstore(long x, long y,
               long *dest) {
  long t = mult2(x, y);
  *dest = t;
}

long mult2(long a, long b) {
  long s = a * b;
  return s;
}
反汇编
0000000000400540 <multstore>:
  400540: push   %rbx        # Save %rbx
  400541: mov    %rdx,%rbx   # Save dest
  400544: callq  400550 <mult2>
  400549: mov    %rax,(%rbx) # Save at dest
  40054c: pop    %rbx        # Restore %rbx
  40054d: retq               # Return

0000000000400550 <mult2>:
  400550: mov    %rdi,%rax   # a
  400553: imul   %rsi,%rax   # a * b
  400557: retq               # Return

3.2 call 与 ret 各自做什么原第 20 页

指令动作 1动作 2
call label把返回地址压栈跳到 label
ret从栈里弹出地址跳到那个地址
返回地址是什么？
「紧挨着 call 的下一条指令」的地址。课件拿上面的反汇编举例：callq 在 0x400544，于是压进栈的是 0x400549 —— 不是 call 自己的地址，也不是 label 的地址，而是回来后该继续执行的那条 mov %rax,(%rbx)。

3.4 自己算返回地址

返回地址 = call 指令自己的地址 + call 指令的编码长度。直接跳转的 call 有两种编码：近调用 rel8（2 字节）与 rel32（5 字节）。课件例子里 callq 400550 用的是 5 字节编码：0x400544 + 5 = 0x400549。

4. 传递数据：寄存器与栈原第 25–27 页

控制过去了，数据怎么跟着过去？x86-64 的答案非常抠门：前 6 个参数用寄存器，返回值用 %rax，实在放不下了才用栈。

4.1 参数与返回值的「规定座位」原第 26 页

内容去哪
第 1–6 个参数%rdi、%rsi、%rdx、%rcx、%r8、%r9
返回值%rax
第 7 个及以后栈 —— 由调用者在自己栈帧顶部预先放好（argument build 区）

课件在这页图的栈那一侧只标了 Arg n … Arg 8、Arg 7，并写了一句原则：「Only allocate stack space when needed」—— 参数不超过 6 个的过程，压根不需要为参数动栈。

交互：参数分配器 —— 给 N 个参数排座位

4.2 数据流示例原第 27 页

回到 multstore / mult2，这回盯住参数与返回值走哪条路：

multstore:
  # x in %rdi, y in %rsi, dest in %rdx
  • • •
  400541: mov   %rdx,%rbx  # Save dest
  400544: callq  400550 <mult2>  # mult2(x,y)
  # t in %rax
  400549: mov   %rax,(%rbx)  # Save at dest
  • • •
mult2:
  # a in %rdi, b in %rsi
  400550: mov   %rdi,%rax  # a
  400553: imul  %rsi,%rax  # a * b
  # s in %rax
  400557: retq  # Return

三个值得看的细节：

  • 参数直接「已在」寄存器里：注释写 x in %rdi 而不是「把 x 放进 %rdi」—— 传参就是调用者事先把值放进约定的寄存器，没有一条专门的「传参指令」。
  • 返回值经 %rax 回家：mult2 把 s 留在 %rax 就 ret；multstore 从 %rax 里接住 t。
  • 超过 6 个的部分才走栈：这个例子一共 3 个参数，全在寄存器里 —— 所以这两段汇编里看不到任何为传参准备的压栈。

5. 栈帧与调用链原第 28–43 页

栈把内存切成一帧一帧（frame），每次过程执行都拥有一帧自己的地盘。递归之所以可能，全靠「每次调用都有自己的一帧」。

5.1 基于栈的语言原第 29 页

概念内容
支持递归的语言C、Pascal、Java……代码必须是可重入的（reentrant）
可重入同一个过程可以同时存在多个活跃的实例（比如递归中的 amI）—— 每个实例都要有地方放自己的状态：参数、局部变量、返回指针
栈纪律
stack discipline		每个实例的状态只在有限时间内需要：从被调用到返回；被调用者（callee）一定先于调用者（caller）返回
帧（frame）栈按帧分配：一帧 = 单个过程实例的全部状态

本节的例子是一串三层调用，其中 amI 调自己：

yoo(…) {
  • who();
  • • •
}
  who(…) {
  • • •

调用链是 yoo → who → amI → amI → amI：一路下到递归的最深处，再原路退回。

6. 管理局部数据：incr 例子原第 44–53 页

第三种机制「内存管理」怎么落地？课件用 10 页追一个小函数：局部变量 v1 住在栈上，跨过一次调用还要活着，用完再拆掉。

6.1 被调方：incr原第 44 页

C 代码
long incr(long *p, long val) {
  long x = *p;
  long y = x + val;
  *p = y;
  return x;
}
汇编与寄存器用途
incr:
  movq (%rdi), %rax
  addq %rax, %rsi
  movq %rsi, (%rdi)
  ret
寄存器用途
%rdi参数 p（指针）
%rsi参数 val，后来放 y
%raxx，也是返回值

incr 一条指令都不「浪费」：x 和 y 都没上栈，全在寄存器里倒手 —— 这正是第 1 节说的「只实现需要的机制」。它还顺手把 *p 从旧值改成了 x + val，这个副作用马上会在调用方看到。

6.2 调用方：call_incr 全程追踪原第 45–53 页

调用方把局部变量 v1 = 15213 放在自己栈帧里，把它的地址递给 incr：

C 代码
long call_incr() {
  long v1 = 15213;
  long v2 = incr(&v1, 3000);
  return v1+v2;
}
汇编
call_incr:
  subq $16, %rsp
  movq $15213, 8(%rsp)
  movl $3000, %esi
  leaq 8(%rsp), %rdi
  call incr

6.3 Aside 1：为什么是 movl $3000, %esi原第 47 页

课件在这一页停下来问了一个小问题：往 64 位寄存器 %rsi 放一个 3000，为什么用 movl（32 位）而不是 movq？答案有两半：

  • movl 会把高 32 位清零：x86-64 规定，任何写到 32 位寄存器（%e…）的操作都把那个 64 位寄存器的高 32 位清成 0 —— 所以 movl $3000, %esi 之后 %rsi 恰好就是干净的 3000，不会残留垃圾；
  • 编码更短。
勘误：短了 2 字节，不是 1 字节
课件写的是「Why use movl instead of movq? 1 byte shorter」。实测（本机 clang --target=x86_64 汇编 + objdump）： movl $3000, %esi 编码为 be b8 0b 00 00（5 字节）， movq $3000, %rsi 编码为 48 c7 c6 b8 0b 00 00（7 字节）—— 差的是 2 字节（寄存器目的地要用 C7 /0 格式，还得带 REX.W 前缀）。「1 字节」的数字只有在内存目的地的场合才成立（那里两种写法只差一个 REX.W 前缀）。结论不变：movl 又对又短，但数字按 2 字节记。
交互：movl 的「高 32 位清零」实验台

6.4 Aside 2：leaq 8(%rsp), %rdi 干的是本行原第 48 页

要把 v1 的地址递给 incr，编译器写的是 leaq 8(%rsp), %rdi —— 计算出 %rsp + 8 这个数（地址就是数），不访问内存。课件的原话带着一点得意：「Actually, used for what it is meant!」—— 上一讲说过 lea 常被编译器拿来凑算术，这一次它干回了老本行：取地址。

7. 寄存器保存约定原第 54–65 页

16 个寄存器是所有过程共享的一块白板。如果 A 用 %rdx 存了个宝贝，调用了 B，B 把 %rdx 改了 —— 回来时宝贝就没了。这节讲 x86-64 Linux 怎么用一张约定表把这事定死。

7.1 先看事故现场原第 54 页

课件给了一段「出事」的代码：yoo 把 15213 存进 %rdx，调用 who；who 毫不知情地把 %rdx 减成 15213 − 18213。回到 yoo，%rdx 里早已不是 15213 ——

yoo: who:
  • • • • • •
  movq $15213, %rdx subq $18213, %rdx
  call who • • •
  addq %rdx, %rax ret
  • • •
  ret

7.2 两种补救约定原第 55 页

约定谁负责怎么做
Caller Saved
调用者保存		调用者调用别人之前，把自己的临时值存进自己的帧；回来再取
Callee Saved
被调用者保存		被调用者想用某个寄存器之前先把旧值存进自己的帧；返回前恢复原值
两种约定的分工本质
一条界线：caller-saved 寄存器，调用一发生就默认作废（谁想留值谁自己压栈）；callee-saved 寄存器，跨过任何调用都原封不动（想用的人自己先存后还）。编译器按「值的生命周期」挑寄存器：要跨调用活着的值放 callee-saved，只在调用前用一小下的放 caller-saved。

7.3 x86-64 Linux 寄存器用法原第 56–57 页

交互：寄存器分类表 —— 点一个寄存器看它的「户口」
勘误：课件漏了 %r15 —— 它也是 callee-saved
课件第 57 页把 callee-saved 列为「%rbx, %r12, %r13, %r14」（外加 %rbp 与 %rsp）。System V AMD64 ABI 的寄存器使用表规定 callee-saved 是 RBX、RSP、RBP、R12–R15 —— %r15 与 %r12–%r14 完全同级。本页用编译器实测佐证：让一个函数跨调用保住 %r15 里的值，clang 生成的序言/尾声会自动加上 pushq %r15 / popq %r15（它必须保存恢复，否则违反 ABI）。本页所有表格与模拟器都按 ABI 把 %r15 归入 callee-saved。

7.4 用上约定：call_incr2原第 58–65 页

现在解决一个真问题：x 从 %rdi 进来，可是 incr 的第一个参数也要用 %rdi，而且 x 要活过那次调用 —— 放哪？课件先抛问题，再用 8 页给出答案：放 callee-saved 寄存器 %rbx。

C 代码
long call_incr2(long x) {
  long v1 = 15213;
  long v2 = incr(&v1, 3000);
  return x+v2;
}
汇编
call_incr2:
  pushq %rbx
  subq  $16, %rsp
  movq  %rdi, %rbx
  movq  $15213, 8(%rsp)
  movl  $3000, %esi
  leaq  8(%rsp), %rdi
  call  incr
  addq  %rbx, %rax
  addq  $16, %rsp
  popq  %rbx
  ret
交互：call_incr2 逐条执行模拟器（盯住 x 的旅程）
对照两个版本，看懂「约定的用处」
call_incr 没有需要跨调用保活的值，所以连一个寄存器都不用存；call_incr2 有 x，于是序言多了 pushq %rbx、尾声多了 popq %rbx。这就是「callee-saved」四个字的全部含义：不白承诺 —— 用的人自己出代价保存恢复，别人（调用者）免费得到「我的 %rbx 绝对不会变」的保证。

8. 递归：pcount_r原第 66–74 页

把前七节的机制合起来跑一遍，就是递归 —— 课件选了数二进制 1 的 pcount_r：它调用自己，却不需要任何一条新指令、任何特殊机制。

8.1 递归 popcount：C 与汇编原第 67 页

C 代码
/* Recursive popcount */
long pcount_r(unsigned long x) {
  if (x == 0)
    return 0;
  else
    return (x & 1)
      + pcount_r(x >> 1);
}
汇编
pcount_r:
  movl  $0, %eax
  testq %rdi, %rdi
  je    .L6
  pushq %rbx
  movq  %rdi, %rbx
  andl  $1, %ebx
  shrq  %rdi        # (by 1)
  call  pcount_r
  addq  %rbx, %rax
  popq  %rbx
.L6:
  rep; ret

每一条都在本讲出现过：testq 判零（第 5 讲）、pushq %rbx 保存 callee-saved 寄存器（7.4）、call / ret 传递控制（第 3 节）、%rdi 进参 / %rax 出参（第 4 节）。

8.2 每个寄存器在这一刻的角色原第 68–72 页

课件用 5 页把执行过程中同一寄存器的含义变化列成了表 —— 递归难读，难就难在「同一个寄存器在不同时刻装着不同的东西」：

时刻%rdi%rbx%rax
刚进入（还没递归）x（参数）——0 / 返回值
保存之后（register save）x旧值已压栈，本帧腾出 %rbx0
递归调用前（call setup）x >> 1（递归参数）x & 1（callee-saved 跨调用保活）——
递归返回后（call）（已无用）x & 1递归调用的返回值
收尾（result）——x & 1本层最终返回值
为什么 %rbx 能活得过递归调用？
andl $1, %ebx 算出的 x & 1 要等递归返回后才用。中间隔着一次 call，而 %rbx 是 callee-saved —— 递归进去的每一层想用 %rbx 都得先把自己的旧值压栈，返回前弹回来。于是每层帧里都存着自己那个 x & 1，互不干扰。

8.4 关于递归的观察原第 74 页

观察依据
不需要特殊处理栈帧让每次调用都有私有存储：保存的寄存器与局部变量、保存的返回指针
互不践踏寄存器保存约定防止一次调用毁掉另一次的数据 —— 除非 C 代码自己越界（第 9 讲的缓冲区溢出）
栈纪律 = 调用 / 返回模式若 P 调用了 Q，Q 一定先于 P 返回 —— 后进先出（LIFO）
mutual recursion 也一样P 调 Q、Q 调 P —— 约定不关心「是不是同一个函数」

9.1 x86-64 过程机制：要点清单原第 75 页

  • 栈是过程调用 / 返回的正确数据结构：若 P 调用 Q，则 Q 先于 P 返回。
  • 递归（以及 mutual recursion）由普通调用约定自动搞定，不需要任何特殊机制。
  • 可以安全地把值放在本帧的栈空间里、放在 callee-saved 寄存器里。
  • 要传的参数（第 7 个起）放在栈顶；结果通过 %rax 返回。
  • 指针就是地址 —— 指向栈上的值，或指向全局的值。
