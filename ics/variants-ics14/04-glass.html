课程导览原第 1–2、5、19、32 页

北京大学《计算机系统导论》第 14 讲：代码优化（Program Optimization）。同一段逻辑，写法不同、给编译器的信息不同，实际速度可以差 10 倍到 40 倍 —— 本讲回答三件事：编译器能替你做什么、什么东西会拦住它、以及你还能在机器层面压榨出多少。

本讲提纲
  1. 性能现实与优化编译器的边界
  2. 通用的机器无关优化：代码外提、强度削减、公共子表达式
  3. 案例：冒泡排序从 29/25 条指令减到 15/9 条
  4. 两类优化拦路虎：过程调用、内存别名
  5. 基准测试与 CPE（每元素周期数）
  6. 现代 CPU：功能单元、延迟与吞吐界限
  7. 循环展开、重结合、多累加器
  8. 向量指令（AVX2）与分支预测
一句话核心

程序的性能 = 算法 × 读写的数据表示 × 编译器的发挥。编译器受「不得改变程序行为」的硬约束，所以真正的加速来自两处：写出编译器敢优化的代码（消除过程调用与别名的干扰），以及亲自动手打破串行依赖（展开、重结合、多累加器、向量指令）。

和前后讲的衔接

第 4–8 讲给了你看汇编、算地址、读结构体的能力；第 10–13 讲（处理器体系结构与存储层次）给了你延迟、吞吐、流水线的机器模型。本讲把这两件事合起来用：先用编译器的视角改代码，再用处理器的视角改循环。最后一张「高性能清单」（原第 69 页）是这一讲给你带走的实用结论。

1. 性能现实与优化编译器原第 3–4、20 页

在动手改代码之前，先把两件事实摆清楚：常数因子和 big-O 一样重要，而编译器受一条铁律约束 —— 不得改变程序行为。这一节的两个清单是后面所有讨论的出发点。

1.1 性能现实原第 3 页

  • 性能不只是渐进复杂度。课件原话：There's more to performance than asymptotic complexity.
  • 常数因子同样重要。同样一段逻辑，因为写法不同，很容易看到 10:1 的性能区间。
  • 必须在多个层次上优化：算法、数据表示、过程（procedures）、循环。
  • 必须理解系统才能优化性能：程序如何被编译与执行、现代处理器与存储系统如何工作、如何测量程序性能并定位瓶颈、以及如何在提升性能的同时不破坏代码的模块化与通用性。

1.2 优化编译器做什么原第 4 页

编译器会做的编译器通常不会做的
  • 寄存器分配（register allocation）
  • 代码选择与排序 / 调度（scheduling）
  • 死代码消除（dead code elimination）
  • 消除细小的低效（eliminating minor inefficiencies）
  • 不改进渐进效率：选更好的整体算法是程序员的事；big-O 上的节省通常比常数因子更重要（但常数因子也要紧）
  • 难以克服「优化拦路虎」：潜在的内存别名（memory aliasing）、潜在的过程副作用（procedure side-effects）

1.3 编译器为什么这么「胆小」：四条基本约束原第 20 页

  1. 不得改变程序行为（例外只在于程序使用了非标准语言特性）。这条约束常常让编译器放弃那些「只在病态条件下才会影响行为」的优化。
  2. 程序员眼里显然的事，会被语言和写法掩盖。例如：数据的实际取值范围可能远小于变量类型所暗示的范围 —— 编译器只看到类型。
  3. 大多数分析只在一个过程内部做。全过程分析（whole-program analysis）在多数情况下太贵；较新的 GCC 会在单个文件内做过程间分析，但不跨文件。
  4. 大多数分析只看静态信息（static information）—— 编译器很难预知运行时会输入什么。
一句话总结这一节
当编译器拿不准时，它必须保守（when in doubt, the compiler must be conservative）。后面两节的「拦路虎」都是这条规矩的直接后果：过程调用让编译器不敢假设「同一个参数返回同一个值」，内存别名让编译器不敢假设「两次访问互不影响」。

1.4 循环开销计数器：combine1 每轮多做了什么原第 34–35、38 页

课件第 35 页的 combine1 把「取长度」和「取元素」都写成了函数调用，第 38 页的 combine4 把它们换成了局部变量与局部指针。下面这个工具按两段代码的结构计出每一层调用的次数（不是估算运行时间，而是数「每一次循环迭代要额外做多少次函数进入/退出与边界检查」）：

/* combine1（原第 35 页） */            /* combine4（原第 38 页） */
*dest = IDENT;                         long length = vec_length(v);
for (i = 0; i < vec_length(v); i++) {    data_t *d = get_vec_start(v);
  data_t val;                             data_t t = IDENT;
  get_vec_element(v, i, &val);         for (i = 0; i < length; i++)
  *dest = *dest OP val;                  t = t OP d[i];
}
交互：combine1 的循环开销 —— 输入元素个数，数一数每轮多做了什么
这个计数说明了什么
vec_length 在循环条件里，所以每轮判断都要调用一次（n 轮循环共 n+1 次函数调用）；get_vec_element 每轮调用一次，而它的第一件事就是课件第 34 页写的边界检查 if (idx >= v->len) return 0;。combine4 把这两件事都提到了循环外：长度只取一次，元素用指针直接 d[i] 取，没有边界检查。这就是课件第 39 页 Combine4 那一行把 CPE 从 10.12 压到 1.27（Int+）的主要来源之一。

2. 通用优化：外提与强度削减原第 6–9 页

课件把第 6–9 页的内容归为「不管什么处理器、什么编译器都该做」的优化（generally useful optimizations）：代码外提、强度削减、公共子表达式。三者的共同点是与机器无关 —— 省掉的是计算本身，而不是让计算跑得更快。

2.1 代码外提（Code Motion）原第 6–7 页

代码外提的规则一句话：如果某段计算的结果每次都一样，就降低它的执行频率 —— 尤其是把它挪出循环。set_row 是标准例子（原第 6 页）：

/* 改写前（原第 6 页） */                  /* 改写后（原第 6 页右栏：程序员手写） */
void set_row(double *a, double *b,    long j;
             long i, long n)    {
{                                        long ni = n*i;
  long j;   /* 循环体的每一条都依赖 j */  double *rowp = a+ni;
  for (j = 0; j < n; j++)              for (j = 0; j < n; j++)
    a[n*i+j] = b[j];                  *rowp++ = b[j];
}

课件第 7 页最有说服力的一点是：编译器在 -O1 就会做这件事。下面这段是课件给出的 GCC 产物（原文照录，注释是课件自己加的）：

set_row:
  testq  %rcx, %rcx       # Test n
  jle    .L1                 # If 0, goto done
  imulq %rcx, %rdx        # ni = n*i       ← 移到循环外
  leaq  (%rdi,%rdx,8), %rdx  # rowp = A + ni*8  ← 移到循环外
  movl  $0, %eax          # j = 0
.L3:                         # loop:
  movsd (%rsi,%rax,8), %xmm0     # t = b[j]
  movsd %xmm0, (%rdx,%rax,8)    # M[A+ni*8 + j*8] = t
  addq  $1, %rax          # j++
  cmpq  %rcx, %rax      # j:n
  jne   .L3                 # if !=, goto loop
.L1:                         # done:
  rep ; ret
本机实测（x86-64 交叉编译复核）
用 clang --target=x86_64-apple-darwin -O1 -S 编译课件同一段 set_row，产物结构完全一致：imulq %rcx, %rdx 与 leaq (%rdi,%rdx,8), %rax 都落在循环之前，循环体只剩 movsd / movsd / incq / cmpq / jne 五条。「编译器会自动做代码外提」这句话是真的（不同编译器选的具体指令可能不同）。

2.2 强度削减（Reduction in Strength）原第 8 页

  • 用更简单、更便宜的运算替换昂贵的运算：用移位与加法代替乘法或除法，例如 16*x --> x << 4。
  • 它有机器依赖性：是否划算取决于乘法/除法指令的代价。课件给的参照是 Intel Nehalem：整数乘法需要 3 个 CPU 周期。
  • 还要能「认出乘积序列」：把 n*i 这种随循环变化的乘积改成增量累加 —— ni += n。
/* 原第 8 页：乘积序列的识别 */           /* 改写后 */
for (i = 0; i < n; i++) {                   int ni = 0;
  int ni = n*i;                              for (i = 0; i < n; i++) {
  for (j = 0; j < n; j++)                for (j = 0; j < n; j++)
    a[ni + j] = b[j];                    a[ni + j] = b[j];
}                                        ni += n;  ← 乘法变成加法
                                         }
交互：强度削减分解器 —— 输入常数乘数，看它怎么被换成移位与加法

2.3 共享公共子表达式原第 9 页

课件用「取 i,j 的四个邻居」说明第三个通用技巧：复用表达式的片段。四个下标里都有 i*n —— 朴素写法算 3 次乘法，先算出 inj = i*n + j 就只剩 1 次。

/* 原第 9 页左栏（3 次乘法） */                 /* 右栏（1 次乘法） */
up    = val[(i-1)*n + j  ];        long inj = i*n + j;
down  = val[(i+1)*n + j  ];        up    = val[inj - n];
left  = val[i*n + j-1];               down  = val[inj + n];
right = val[i*n + j+1];               left  = val[inj - 1];
sum = up + down + left + right;     right = val[inj + 1];

课件给的汇编也印证了这一点：朴素版有 3 条 imulq（(i+1)*n、(i-1)*n、i*n），改写后只剩 1 条 imulq %rcx, %rsi。

交互：公共子表达式计数器 —— 输入 i、j、n，看四个地址怎么算
本机实测
把这两段写成 C（nebr_naive / nebr_cse）后 clang -O1 编译：朴素版的功能块里有 3 条 imulq，改写版只剩 1 条 imulq —— 与课件第 9 页的结论一致。（课件用的是 GCC，实际生成的指令选型略有不同，但「乘法条数 3 → 1」这个结论被独立复现。）
注意 ni 的位置
右栏的 int ni = 0; 必须在外层循环之前，循环体里只写 ni += n;。初始化放在循环里就会错：每轮把 ni 重置为 0，a[ni + j] 会永远只写第一行。这条改写同时用到两个技巧：把 n*i 这个乘积换成了加法（强度削减），以及用累加代替每轮重算（归纳变量消除）。

3. 案例：冒泡排序九次改写原第 10–18 页

课件用整整九页（原第 10–18 页）把一段冒泡排序一步步改到不能再省：内层循环从 25 条指令减到 9 条，外层从 29 条减到 15 条。这是「机器无关优化」最完整的一次演示 —— 全程只用算术恒等式，不碰任何处理器细节。

3.1 被优化的程序原第 10 页

课件先把数据结构交代清楚（这几条前提决定了后面所有地址计算的形式）：

  • 数组 A 分配在静态存储里；
  • 每个元素占 4 个字节，机器按字节寻址；
  • 元素下标从 1 到 n（n 是变量）；
  • 因此 A[j] 的位置是 &A + 4*(j−1)。
for (i = n-1; i >= 1; i--) {
  for (j = 1; j <= i; j++)
    if (A[j] > A[j+1]) {
      temp = A[j];
      A[j] = A[j+1];
      A[j+1] = temp;
    }
}

3.2 翻译成（伪）代码原第 11 页

课件把 C 语言翻译成一种只含简单运算的伪代码：没有 * 的隐含语义、没有下标糖，每个「中间值」都起个名字（t1、t2……）。这样才数得清「一个内层循环迭代到底要执行多少条指令」。第一版数出来是：

初版（原第 11 页）

29 条指令在每次外层循环迭代（即跑完一遍内层循环）中执行；25 条在内层循环里执行。

「一条指令」指什么

伪代码里的一行简单运算（一次赋值、一次比较、一次跳转）算一条。这不是真实的机器指令数，而是一个与机器无关的计算量度量；用它比较同一算法的不同写法，比比较运行时间更稳定。

为什么要先做这一步
把 C 降到伪代码之后，「冗余」才看得见：A[j] 在 C 里是一个字符，在伪代码里是 t1:=j-1; t2:=4*t1; t3:=A[t2] 三条；交换时同一对下标又各算了一遍。九页的改写，本质就是把重复出现的子表达式合并、把随循环线性变化的量改成增量。

3.3 三个冗余，三次消除原第 12–17 页

第一次：地址计算冗余（原第 12–13 页）· 29/25 → 20/16
t4:=j+1; t5:=t4-1; t6:=4*t5  →  t6:=4*j
算 A[j+1] 时先把 j 加 1 再减 1，纯绕路；4*j 与 4*(j-1) 在同一轮里各算一次 —— 合并成一次。
第二次：交换用的中间量（原第 14–15 页）· 20/16 → 15/11
temp := A[j]; A[j] := A[j+1]; A[j+1] := temp  →  A[t2] := t7; A[t6] := t3
交换本来就先把两个值都读进临时变量（t3 与 t7），temp 是多余的第三份拷贝：直接写回 t3 即可。
第三次：值为 4 的倍数（原第 16–17 页）· 15/11 → 15/9
t2 := 4*t1; t6 := 4*j  →  t2 := t2+4; t6 := t6+4（循环外 t19 := i << 2）
既然 j 每轮加 1，那么 4*j 每轮就加 4。乘法换成加法，同时把内层循环的终止条件从 j>i 换成 t6>t19（比较对象也提前算好）。

课件第 18 页把前面积累的改写合到一起，并把「4*i」也写成移位（t19 := i << 2，就是第 2 节的强度削减）：

4. 拦路虎一：过程调用原第 21–27 页

这是全讲最有冲击力的一个例子：一段「把字符串转小写」的代码，因为把 strlen 写在了循环条件里，性能从平方级掉到线性级 —— 改成 len = strlen(s) 只是把它挪出循环一行。而且，这个优化编译器不敢自己做。

4.1 出问题的代码原第 21 页

课件特别注明：这段函数「摘自 1998 年秋季 213 份实验提交」—— 也就是说，这是学生反复踩中的一个真实陷阱。

void lower(char *s)
{
    size_t i;
    for (i = 0; i < strlen(s); i++)  // 每轮都调用一次 strlen！
        if (s[i] >= 'A' && s[i] <= 'Z')

4.2 性能后果：平方级原第 22、24 页

  • 课件第 22 页的测量曲线：字符串长度翻倍，时间变 4 倍 —— 典型的 平方（quadratic）性能。
  • 原因（第 24 页）：要确定一个字符串的长度，唯一的办法是从头扫到尾找 '\0'。于是长度为 N 的字符串上：
    • strlen 被调用 N 次；
    • 每次分别要扫过 N、N−1、N−2、…、1 个字符；
    • 总工作量 ≈ N(N+1)/2 —— O(N²)。

4.3 修复：把调用挪出循环原第 23、25–26 页

课件先把它转成 goto 形式（第 23 页），让「strlen 每轮都执行」这件事变得一目了然：

goto 形式（原第 23 页）

size_t i = 0;
if (i >= strlen(s)) goto done;
loop:
  if (s[i] >= 'A' && s[i] <= 'Z')
    s[i] -= ('A' - 'a');
  i++;
  if (i < strlen(s)) goto loop;
done:

判断条件里两次出现 strlen，都在循环体内或循环边界上。

改写后（原第 25 页）

size_t i;

for (i = 0; i < len; i++)
  if (s[i] >= 'A' && s[i] <= 'Z')
    s[i] -= ('A' - 'a');

结果不随迭代变化 → 这是代码外提的一种形式。

课件第 26 页给出对照曲线：长度翻倍、时间只翻倍 —— 恢复线性。

4.4 编译器为什么不肯做这个外提原第 27 页

  • 过程可能有副作用：每次调用都可能改写全局状态；
  • 函数对同样的参数可能返回不同的值：返回值可能依赖全局状态的其它部分；
  • 被调用的过程可能与调用者互相影响（课件举例：lower 可能和 strlen 有交互）。

课件给出的示例把这条说得很直白 —— 假设 strlen 里有一个全局计数器：

size_t lencnt = 0;          // 全局状态
size_t strlen(const char *s)
{
    size_t length = 0;
    while (*s != '\0') { s++; length++; }
    lencnt += length;         // 每次调用都改变全局状态
    return length;
}
警告（课件原文）
编译器把过程调用当作黑箱（treats procedure call as a black box），因此它附近的优化都很弱。只要一次调用可能改变全局状态，编译器就不能把第二次调用的结果换成第一次的结果 —— 哪怕它完全看得懂这段代码。

补救办法（课件第 27 页）：

  • 使用 inline 函数 —— GCC 在 -O1 就会在单个文件内做内联；
  • 自己动手做代码外提（Do your own code motion）：既然你知道 strlen(s) 在循环里不会变，就自己把它提出来。
本机实测（x86-64 交叉编译 + 运行）

5. 拦路虎二：内存别名原第 28–31 页

第二个拦路虎比过程调用更隐蔽：编译器不知道两个指针会不会指向同一块内存。于是它不敢把「写内存」从循环里提出来 —— 而只要写上「累加进局部变量」，这个优化立刻就能做。

5.1 一句写得很自然的代码，编译器却动不了原第 28 页

目标：把一个 n×n 矩阵的每一行分别求和，存进向量 b。最自然的写法是直接累加到 b[i]：

void sum_rows1(double *a, double *b, long n) {
    long i, j;
    for (i = 0; i < n; i++) {
        b[i] = 0;
        for (j = 0; j < n; j++)
            b[i] += a[i*n + j];
    }
}

课件给出的内层循环汇编（原第 28 页，GCC -O1）：

# sum_rows1 inner loop
.L4:
  movsd (%rsi,%rax,8), %xmm0    # FP load     ← 每轮都要把 b[i] 读进来
  addsd (%rdi), %xmm0            # FP add
  movsd %xmm0, (%rsi,%rax,8)    # FP store    ← 每轮都要写回去
  addq  $8, %rdi
  cmpq  %rcx, %rdi
  jne   .L4

中间结果 每一轮都要写回内存再读回来（3 条浮点操作：load / add / store）。课件的问题：为什么编译器不把这个中间量放进寄存器？

5.4 别名小结原第 31 页

  • 别名（aliasing）：两个不同的内存引用指向同一个位置；
  • 在 C 里很容易发生：因为允许做地址算术、可以直接访问存储结构；
  • 养成引入局部变量的习惯，尤其是在循环里做累加时 —— 这既消除了别名的影响，也顺便让值留在寄存器里；
  • 课件原话：这就是你告诉编译器「不用检查别名」的方式（your way of telling compiler not to check for aliasing）。
本机实测（x86-64 交叉编译复核）
clang -O1 -S 编译这两段函数，内层循环与课件完全同构：
sum_rows1 内层 = addsd + movsd %xmm0, (%rsi,%rcx,8)（store） + incq + cmpq + jne；

6.5 基本优化：combine4原第 38–39 页

void combine4(vec_ptr v, data_t *dest)
{
    long i;
    long length = vec_length(v);     // ① 长度移出循环
    data_t *d = get_vec_start(v);    // ② 基址移出循环
    data_t t = IDENT;                 // ③ 用局部变量累加
    for (i = 0; i < length; i++)
        t = t OP d[i];                 // 直接下标，不再有边界检查
    *dest = t;
}
① 把 vec_length 移出循环

第 1 节那个计数器算的就是这一条的收益：调用次数从 n+1 次降到 1 次。

② 避免每轮的边界检查

用 d[i] 直接解引用，绕开 get_vec_element 里的 idx >= v->len。

③ 在临时变量里累加

这一条同时解决了第 5 节的别名问题：局部变量不可能与任何指针别名。

7. 现代 CPU：延迟与吞吐原第 40–45 页

为什么 Int Mult 卡在 3.01、FP Mult 卡在 5.01？因为现代处理器一次能开工很多条指令，但一条指令自己的延迟不会变。这一节把机器模型讲清楚 —— 后面所有加速手段都是在这个模型上「找空隙」。

7.1 现代 CPU 的两半：指令控制与执行原第 40、62 页

Instruction Control（指令控制）
  • 取指（Fetch）按地址从指令内存里取指令；
  • 指令译码（Instruction Decode）把指令变成一组「操作」；
  • 寄存器缓存 / 寄存器堆：记录寄存器的最新值；
  • 退休控制（Retirement Control）：确认某条指令的结果可以真正写入寄存器；
  • 分支预测：猜分支走向，猜对了才能一直有指令可发。
Execution（执行）
  • 一组功能单元（Functional Units）：分支、算术（多个）、加载、存储；
  • 操作从数据缓存里取/存数据；
  • 寄存器更新：执行完的操作把结果写回寄存器缓存；
  • 课件图上的关键一问：分支预测是否猜对（Prediction OK?）—— 这条线决定了执行单元会不会白干。

7.2 超标量处理器原第 41 页

定义（课件原文）
超标量（superscalar）处理器可以在一个周期里发射并执行多条指令。这些指令从顺序的指令流里取出，通常由硬件动态调度。
  • 好处：不需要程序员额外做什么，超标量处理器就能利用大多数程序本来就有的指令级并行（ILP）。
  • 普遍性：大多数现代 CPU 都是超标量的；Intel 从 1993 年的 Pentium 起就是。

void unroll2a_combine(vec_ptr v, data_t *dest)
{
    long length = vec_length(v);
    long limit = length-1;
    data_t *d = get_vec_start(v);
    data_t x = IDENT;
    long i;
    /* Combine 2 elements at a time */
    for (i = 0; i < limit; i+=2) {
        x = (x OP d[i]) OP d[i+1];
    }
    /* Finish any remaining elements */
    for (; i < length; i++) {
        x = x OP d[i];
    }
    *dest = x;
}

课件对这一版的评语：每次迭代做 2 倍的有用工作（perform 2x more useful work per iteration）。

课件第 48 页的两个反问（答案见下）
「这会不会改变计算结果？」 会 —— 对浮点（FP）会。
「为什么？」 因为浮点加法与乘法不满足结合律（not associative）：(a+b)+c 与 a+(b+c) 的舍入结果可能不同。整数运算满足结合律，所以对整数完全安全。课件第 33 页事先就点明了这条限制：编译器常常不能做这类变换，正因为浮点运算缺少结合律与分配律。

9.2 泛化：展开 L 倍、用 K 个累加器原第 54 页

做法
  • 可以展开到任意因子 L；
  • 可以并行累加 K 个结果；

限制
  • 收益递减；

10.4 分支：处理器的下一个大麻烦原第 61、63–64 页

挑战（原第 61 页）

指令控制单元必须跑在执行单元前面很多，才能产生足够的操作把执行单元喂饱。而一旦遇到条件分支，它无法可靠地确定接下来该从哪里继续取指 ——「如何继续？」（How to continue?）

两种去向（原第 63 页）
  • Branch Taken：把控制权转移到分支目标；
  • Branch Not-Taken：继续执行序列中的下一条指令；
  • 在分支/整数单元把结果算出来之前，无法确定是哪种。
404663:  mov $0x0,%eax
404668:  cmp (%rdi),%rsi
40466b:  jge 404685    ← 取指跑到这里就卡住了：跳（去 404685）还是不跳（去 40466d）？
40466d:  mov 0x8(%rdi),%rax
  . . .
404685:  repz retq

分支预测（原第 64 页）的答案：猜。猜完就沿着猜的位置开始执行指令，但不去真正修改寄存器或内存数据 —— 猜错了代价很小，因为什么都没落地。

10.6 预测器的实际水平原第 68 页

  • 默认行为：向后的分支（backwards）常常是循环，预测 taken；向前的分支（forwards）常常是 if，预测 not taken。
  • 预测器的平均准确率好于 95% —— 因为大多数分支本来就好预测。

11.1 高性能清单原第 69 页

① 好的编译器与编译选项

课件的四条实用建议里的第一条。第 6 节的表说明了差距：同一段 combine1，-O3 比未优化快 4–5 倍。

② 别做傻事（Don't do anything stupid）
  • 当心隐藏的算法低效——本讲最典型的例子是 lower1 把 strlen 写进循环条件（第 4 节）；
  • 写编译器友好的代码；
  • 当心两类优化拦路虎：过程调用与内存引用（别名）；
  • 仔细检查最内层循环——绝大部分工作都发生在那里。
③ 针对机器调优代码
  • 利用指令级并行（展开、重结合、多累加器）；
  • 避开不可预测的分支；
  • 让代码对缓存友好（课件注明：本课程后面会讲）。
④ 记住三条基本事实
  • 常数因子和 big-O 一样真实（第 1 节）；
  • 编译器受「不得改变行为」约束，会保守（第 1、4、5 节）；
  • 性能上限由功能单元吞吐决定，不由代码写得漂不漂亮决定（第 9 节）。
