课程导览原第 1–2 页

北京大学《计算机系统导论》第 15 讲：链接（Linking）。这一讲回答一个被很多人跳过、但天天在用的过程：一个个 .o 文件是怎么被拼成一个能跑的可执行文件的。课件第 2 页的提纲把它拆成四块：目标文件、链接机制（符号与符号解析、重定位）、库、动态链接与库打桩。

本讲提纲原第 2 页
  1. 链接：把目标文件组合成程序
  2. 目标文件（三类）与 ELF 格式
  3. 链接机制之一：符号与符号解析
  4. 链接机制之二：重定位
  5. 库：静态库与共享库
  6. 动态链接、加载与执行
  7. 库打桩（library interpositioning）
一句话核心

链接器只做两件事：符号解析（把每个符号引用接到唯一一个符号定义上）与重定位（把各模块同类型的节合并、分配运行时地址、再把代码与数据里所有引用改写过去）。其余的一切 —— 库、动态链接、打桩 —— 都是这两件事在不同时机（编译时 / 加载时 / 运行时）的变体。

为什么值得学

课件第 67 页的收尾：链接通常悄无声息，偶尔给出匪夷所思的错误（符号解析错误、.o／.a／.so 的顺序依赖）；而对高手来说，理解链接才能用库打桩去追踪别人的程序。这一讲里的「谜题」「顺序」「类型不检查」都是真实会咬人的坑。

1. 从 .c 到可执行文件：编译工具链原第 3–8 页

课件第 3 页先给出这一讲反复使用的例子 —— 两个文件、一个数组、一个函数调用；第 4 页指出真正干活的是 gcc 背后的四个程序。链接是这条流水线的最后一步，也是本讲的主题。

1.1 课件的示例程序原第 3、8 页

/* main.c */
int sum(int *a, int n);
int array[2] = {1, 2};

int main(int argc, char** argv)
{
  int val = sum(array, 2);
  return val;
}
/* sum.c */
int sum(int *a, int n)
{
  int i, s = 0;
  for (i = 0; i < n; i++) {
    s += a[i];
  }
  return s;
}

这一对文件贯穿全讲：main.c 定义了 array 与 main、引用了 sum；sum.c 定义了 sum。链接器的全部工作就是把这两半接上。

1.5 静态链接全景原第 8 页

课件第 8 页的图把「分别编译、一次链接」画清楚了：

main.c   sum.c                   ← 源文件 Source files

  ▼        ▼
Translators  Translators       ← (cpp, cc1, as) 各来一遍
  │        │
  ▼        ▼

        │

为什么第 9、10 页说链接器有用
模块化：程序可以写成一组较小的源文件，而不是一大坨；公共函数还能攒成库（数学库、标准 C 库……）。 效率：时间上 —— 改一个文件只重编这一个，再重新链接即可（其余文件不必重编，还可以并行编译）；空间上 —— 库提供两种省法：静态链接让可执行文件与内存映像里只含真正用到的库代码，动态链接干脆不让可执行文件带库代码，运行时所有进程共享同一份库代码。

2. 三种目标文件与 ELF 格式原第 14–18 页

链接器面前只有「模块」。课件第 14 页把模块分成三类，第 15–18 页说明它们用同一个二进制格式 ELF 装着 —— 区别不在格式，而在用途：可重定位（再组合）、可执行（直接复制进内存就能跑）、共享（加载或运行时再链接）。

2.1 三类目标文件原第 14 页

类别后缀课件原话
可重定位目标文件.o里面的代码和数据可以与其他可重定位目标文件组合成可执行目标文件；每个 .o 恰好由一个 .c 文件产出
可执行目标文件a.out代码和数据可以被直接复制到内存并执行
共享目标文件.so一类特殊的可重定位目标文件，可以在加载时或运行时被动态加载并链接进程序；Windows 管它叫动态链接库 DLL

2.2 统一格式 ELF原第 15 页

  • ELF = Executable and Linkable Format，目标文件的标准二进制格式；
  • 一种格式覆盖三种文件：.o、a.out、.so —— 统称 ELF 二进制；
  • 最初出现在 System V Release 4 Unix（约 1989 年）；Linux 约 1995 年换成 ELF，BSD 更晚，约 1998–2000 年。

2.3 ELF 里装着什么原第 16–17 页

课件第 16–17 页把 ELF 的部件逐个点名，第 18 页说明为什么同一份文件有「两种看法」。点下面的部件看它的用途，以及它在链接视图／执行视图里的身份：

交互：ELF 部件查看器
ELF 头 程序头表／段 节头表 .text .rodata .data .bss .symtab .rel.text .rel.data .debug .line / .strtab .init .interp .dynamic
两种看法：节（Section）与段（Segment）
课件第 18 页把同一份 ELF 文件并排画了两遍：链接视图看到的是「ELF 头 → 程序头表（可选）→ 节 1…节 n → 节头表（必需）」；执行视图看到的是「ELF 头 → 程序头表（必需）→ 段 1、段 2、段 3……→ 节头表（可选）」。 一句话：链接时按节看，执行时按段看 —— 段是把若干节合并起来交给加载器的单位。
程序头表用来构造进程映像（也就是「执行一个程序」），所以可重定位文件不需要它；反过来，链接时用的文件必须有节头表。
BSS 这个名字的两个说法（课件第 16 页原文）
课件同时给出了两个解释："Block Started by Symbol" 与 "Better Save Space"。它装的是未初始化的全局变量； 关键在于后半句：它有节头，但不占文件空间 —— 全是 0 的东西没必要真的存进文件里（这一点在执行视图里变成「段在内存里比在文件里大」）。

3. 符号与符号解析原第 11–12、19–25 页

链接器的第一步是符号解析（symbol resolution）：把程序里每个符号引用，关联到恰好一个符号定义上。这一步听起来平淡，但「强符号／弱符号」「链接器不做类型检查」这些坑全在这里。

3.1 链接器做两件事原第 11、13 页

步骤做什么原第 11、13 页
第一步：符号解析
Symbol resolution		程序由符号的定义与引用组成（void swap() {…} 定义 swap，swap(); 引用 swap，int *xp = &x; 定义 xp、引用 x）。汇编器把定义收进目标文件的符号表（一个条目数组，每项含名字、大小、位置）；链接器则把每个引用接上恰好一个定义。
第二步：重定位
Relocation		把各模块里同类型的代码节与数据节合并成单个节；把符号从 .o 里的相对位置搬到可执行文件里的最终绝对地址；再把所有对这些符号的引用改成新位置。（第 4、5 节详细讲）

3.2 三类链接器符号原第 19、21 页

类别定义例子
全局符号
Global		由模块 m 定义、并能被其他模块引用非 static 的 C 函数、非 static 的全局变量
外部符号
External		被模块 m 引用、但由别的模块定义main.o 里的 sum
局部符号
Local		只由模块 m 自己定义并引用用 static 定义的函数与全局变量
「局部符号」不是「局部变量」
课件第 19 页专门加了一句：Local linker symbols are not local program variables. 函数里的局部（非 static）变量在栈上（课件第 21 页：local non-static C variables: stored on the stack），跟链接器毫无关系；而局部 static 变量虽然名字里带「局部」，却要真的分配空间 —— 存在 .bss 或 .data 里，并在符号表里占一条（还是「局部符号」）。
课件第 21 页的 static-local.c：
static int x = 15;　　　　　/* 文件作用域，名字就叫 x */

int f() { static int x = 17; return x++; }　/* 编译器给唯一名字 x.1721 */
int g() { static int x = 19; return x += 14; }　/* 另一个 x.1724 */
int h() { return x += 27; }　/* 这里用的是文件作用域那个 x */
课件原话：编译器为每一处定义在 .data 里分配空间，并在符号表里建一条唯一名字的局部符号 —— 例如 x、x.1721、x.1724。 （那两个数字是编译器自己生成的计数器，不同编译器／不同版本会不一样。）

3.4 重复符号名：强与弱原第 22–23 页

链接器把符号分成强（strong）与弱（weak）两类。课件第 22 页的对照：p1.c 里的 int foo=5; 与 p1() {} 都是强符号；p2.c 里的 int foo; 是弱符号，p2() {} 是强符号。编译器把这种信息交给汇编器，汇编器再把它隐含地编码进 ELF 的符号表。

强／弱什么样的符号原第 22 页
强 Strong过程（函数）、已初始化的全局变量
弱 Weak未初始化的全局变量；或者用 extern 说明符声明的那些
规则 1

允许多个强符号？不允许。每个条目只能被定义一次，否则链接器报错。

规则 2

一个强符号 + 多个弱符号：选强符号；对弱符号的那些引用也解析到强符号上。

规则 3

多个弱符号：任选一个。课件附注：可以用 gcc -fno-common 改掉这种行为。

交互：符号解析器 —— 写下各模块的符号，看链接器怎么裁决

3.5 链接器谜题原第 24 页

课件第 24 页用五组 p1.c／p2.c 把上面三条规则的后果摊开 —— 这也是最有价值的一页，因为每一个「Evil!」「Nasty!」都是真的会发生的 bug：

#p1.cp2.c结果（课件原话）为什么
1int x;
p1() {}		p1() {} 链接时错误：两个强符号（p1）

课件第 24 页的两句警告
Important: Linker does not do type checking.（链接器不做类型检查 —— 所以 int x 与 double x 这种冲突它照单全收。）
Nightmare scenario：两个一模一样的弱 struct，被不同编译器按不同的对齐规则编译 —— 链接器照样接上，程序在运行时开始出错。
交互：八道判断题 —— 点在规则与「不检查」的边界上
本页补充：这条规则在今天需要加一句前提（-fcommon）
课件第 22 页把「未初始化的全局变量」归为弱符号，谜题 2、3、5 也都建立在「两个弱符号可以共存」之上。这是传统的 -fcommon 行为。 但现代编译器（GCC 10+、clang 11+）已经把 -fno-common 变成默认：本页用 clang 实测（--target=x86_64-linux-gnu，默认参数）确认，int x; 会被放进 .bss 并成为强符号（nm 显示 B），加上 -fcommon 才回到课件那种 COMMON 弱符号（nm 显示 C）。
后果：在今天的默认参数下，两个文件各写一个 int x; 会变成重复强符号而报链接错误 —— 也就是课件规则 1 而不是规则 3。 课件第 23 页其实已经把这层机关写在规则 3 的附注里（「Can override this with gcc -fno-common」），只是没展开说默认值已经反过来了。 上面判断题的第 1 题按课件的模型判定（两个 int x; 链接通过），学的时候要记得这层前提。

3.6 避免类型不匹配的四条建议原第 25 页

  • 尽量避免全局变量；
  • 尽量用 static；
  • 所有非 static 的东西都要在头文件里声明：每个相关的地方都要 include 这个头文件（包括定义这些符号的文件本身）；
  • 头文件的声明里一律写 extern：对函数声明来说虽属多余但无害，对全局变量却能避开「不带 extern 的全局变量」那种古怪行为；
  • 函数没有参数时一定要写 (void)：extern void no_args(void);。不写 void 的意思是「我不说这个函数要什么参数」，这等于关掉参数类型检查。
把这四条记成一句话
链接器不给类型把关（第 24 页），所以把关的责任全在声明与 static 上：能藏就藏（static）、要露就露在头文件里（extern + 到处 include）、空参数就写 (void)。

4.1 合并：从若干 .o 到一个可执行文件原第 26 页

4.3 重定位条目长什么样原第 28 页

课件第 28 页给出 SHT_RELA 型节里的结构体：

/* Relocation table entry with addend (in section of type SHT_RELA). */
660  typedef struct
661  {
662    Elf64_Addr   r_offset;  /* Address */
663    Elf64_Xword  r_info;    /* Relocation type and symbol index */
664    Elf64_Sxword r_addend;  /* Addend */
665  } Elf64_Rela;
 
673  #define ELF64_R_SYM(i)  ((i) >> 32)
674  #define ELF64_R_TYPE(i) ((i) & 0xffffffff)
字段含义（课件原话）
r_offset将被修改的那个引用在节内的偏移
ELF64_R_SYM(r_info)指出这个引用应该指向哪个符号（符号表下标）
ELF64_R_TYPE(r_info)告诉链接器怎么改这个引用（重定位类型）
r_addend一个常数，某些重定位类型用它做偏移调整

为什么一个 64 位的 r_info 要拆成两半？因为「符号下标」和「类型」都是小整数，塞进一个 8 字节字段刚好 —— 于是半条重定位条目的全部信息就是「改哪儿（offset）+ 改成谁（符号下标）+ 怎么改（类型）+ 加多少（addend）」。

4.4 两种最基本的重定位类型原第 29 页

R_X86_64_PC32

重定位一个使用 32 位 PC 相对地址的引用 —— 存的是「从这个字段到目标」的位移（call、jmp 这类指令用的就是它）。

R_X86_64_32 / R_X86_64_32S

重定位一个使用 32 位绝对地址的引用 —— 存的就是目标的绝对地址（mov $array, %edi 这类把地址当立即数用的指令）。32S 表示按有符号解释。

为什么汇编器不能自己算
汇编器只看得到本文件：它知道 array 在本节里的偏移，但不知道这个节最终被放在哪里，更不知道 sum 会在哪个地址（那要等链接器把所有模块合并完）。 所以它只能在原地留一个 32 位的空位（全 0），再写一条重定位条目 ——「改哪儿、改成谁、怎么改、加多少」—— 交给链接器。下一节就来看这张表。

4.5 链接器实际怎么改：relocate 例程原第 29 页

课件第 29 页下半部分印着链接器做重定位的那段例程（原文引用）—— 它把上面两种类型浓缩成一个循环，下面第 5 节的计算器实现的就是这两条分支：

for each section s {
  foreach relocation entry r {
    refptr = s + r.offset;                   /* ptr to reference to be relocated */

    /* Relocate a PC-relative reference */
    if (r.type == R_X86_64_PC32) {
      refaddr = ADDR(s) + r.offset;          /* ref's run-time address */
      *refptr = (unsigned) (ADDR(r.symbol) + r.addend − refaddr);
    }

    /* Relocate an absolute reference */
    if (r.type == R_X86_64_32)
      *refptr = (unsigned) (ADDR(r.symbol) + r.addend);
  }
}
这段话里的 ADDR(s) 是「输入模块的节的运行时基址」
注意例程里有两个不同的量：refptr = s + r.offset 是指针（拿节的位置当起点），而 refaddr = ADDR(s) + r.offset 是引用处的运行时地址 —— 两者都用同一个「节」s，而 r.offset 正是这条条目在该节内部的偏移。 第 36 页那个例子里的 0xbabf18 就是 ADDR(s)：main.o 自己的 .text 被链接器摆到了那里（合并后的大 .text 从 0xbabe00 开始，系统代码占了前面 0x118 个字节）。
例程里没有 r.type 之外的分支
只有 PC 相对与绝对两种写法 —— 其它重定位类型（R_X86_64_32S、R_X86_64_64、GOT 相关的一大堆）要么是同一套算式的变体（有符号 / 64 位），要么是给动态链接用的，本讲不展开。

5.2 课件第 31–32 页的「Dear Linker」原第 31–32 页

这两页把上面两条条目翻译成了给链接器的「信」，非常清楚地说明了 addend 是干什么的：

对第 1 条（offset 0x15，R_X86_64_32，array + 0）

「亲爱的链接器：请在 .rela.text 节的偏移 0x15 处打一个 32 位的值。等你定下 .data 的地址后，算 array 的地址 + addend（等于 0），把结果放到指定的地方。」—— 署名：汇编器

对第 2 条（offset 0x1a，R_X86_64_PC32，sum − 4）

「……请在偏移 0x1a 处打一个 32 位的 PC 相对值：定下 sum 的地址后，算 sum 的地址 + addend（等于 −4）− 节地址 + 偏移，把结果放到指定的地方。」

那个 −4 是哪来的
x86-64 的 call 指令是 5 个字节（1 字节操作码 + 4 字节位移），而 CPU 计算目标地址时用的是指令末尾（也就是 refptr + 4）作为基准。 但 refptr 按定义指向位移字段本身，两者差 4 个字节 —— 于是 addend = −4 正好把这个差补上。 下面 5.3 的计算器会用课件第 36 页的真实地址把这一步算出来（答案是 0x0a）。

两个「节的地址」别搞混（课件第 36 页那张图的关键细节）
课件第 36 页同时印了 .text = 0xbabe00 和 addr_of_main = 0xbabf18，看着矛盾，其实是两个不同的东西：
  • .text = 0xbabe00 是合并之后那个总代码节的起点 —— 系统代码、启动代码就排在这 0x118 个字节里；
  • 0xbabf18 是 main.o 自己那段 .text 被摆到的地方（正好等于 main 的地址，因为 main 就是 main.o 里 .text 的第一个符号）；同理 sum.o 的 .text 被摆在 0xbabf40；

上面计算器里的「引用所在节的基址」默认就是 0xbabf18：填对了它，rpOut 算出来的字段地址才会正好落在课件印的两个字节上 —— 0xbabf18 + 0x15 = 0xbabf2d（babf2c: bf … 里的那 4 个字节）与 0xbabf18 + 0x1a = 0xbabf32（babf31: e8 … 里的那 4 个字节）。两边的字节值也一致：10 fe ca 00 与 0a 00 00 00。

6. 静态库：打包一堆函数原第 38–44 页

「把常用函数攒成库」是链接器存在的第二大理由。课件第 38 页先摆出两条笨办法，第 39–43 页给出老式答案 —— 静态库（.a 归档文件），第 44 页则点出用它时最容易踩的坑：命令行顺序。

6.1 两种笨办法原第 38 页

办法做法问题

6.2 老式答案：静态库原第 39–41 页

  • 静态库是 .a 归档文件：把相关的可重定位目标文件拼接成一个文件，并带一个索引（叫做 archive）；
  • 链接器被增强了：遇到未解析的外部引用时，它会去一个或多个归档里找这些符号；
  • 某个归档成员如果解决了引用，它才会被链接进可执行文件。

    z[i] = x[i] + y[i];
}

6.4 库为什么必须写在后面原第 44 页

课件第 44 页给出链接器解析外部引用的算法：

  1. 按 命令行顺序扫描 .o 与 .a 文件；
  2. 扫描过程中维护一张当前未解析引用的清单；
  3. 每遇到一个新的 .o 或 .a（记作 obj），就试着用 obj 里定义的符号去解决清单里的每一项引用；
  4. 扫描结束时清单里还有东西 —— 报错。
unix> gcc -static -o prog2c -L. -lvector main2.o  ← 库写到了前面
main2.o: In function `main':
main2.c:(.text+0x19): undefined reference to `addvec'
collect2: error: ld returned 1 exit status
第 44 页的结论
命令行顺序要紧！所以有条经验之谈：把库放在命令行的末尾。（原因就在算法里：库在前时，那张未解析清单还是空的 —— 没有任何引用需要它解决，于是它一个成员都不会被拉进来。）
交互：静态库顺序模拟器 —— 改命令行顺序，看链接器一步一步怎么扫

7. 加载与动态链接原第 37、45–53 页

7.2 为什么需要共享库原第 45–46 页

静态库的三个缺点原第 45 页
  • 存下来的可执行文件里有重复（每个程序都要一份 libc）；
  • 运行中的可执行文件里也有重复；
  • 系统库修一个小 bug，每个应用都要重新链接一遍（课件还引了 Google 安全博客里 glibc getaddrinfo 那个著名的 CVE-2015-7547 当例子：要不要把一切都用 glibc 重新构建一遍？）
共享库原第 45–46 页

包含代码与数据、可在加载时或运行时被动态加载并链接进应用的目标文件；也叫动态链接库、DLL、.so 文件。 Linux 上最常见的是加载时链接（由动态链接器 ld-linux.so 自动完成），标准 C 库 libc.so 通常就是动态链接的。 动态链接也可以发生在程序开始之后（运行时链接），在 Linux 上通过 dlopen() 接口完成。共享库的例程还能被多个进程共享。

课件第 46 页给运行时链接列了三个用途：分发软件、高性能 Web 服务器（惰性绑定）、运行时的库打桩。

7.4 运行时链接：程序自己加载库原第 49–51 页

课件第 49–50 页给了一个完整的 dll.c（节选，原文引用）：

#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int x[2] = {1, 2}; int y[2] = {3, 4}; int z[2];

int main(int argc, char** argv)
{
  void *handle;
  void (*addvec)(int *, int *, int *, int);
  char *error;

  /* Dynamically load the shared library that contains addvec() */
  handle = dlopen("./libvector.so", RTLD_LAZY);
  if (!handle) { fprintf(stderr, "%s\n", dlerror()); exit(1); }

  /* Get a pointer to the addvec() function we just loaded */
  addvec = dlsym(handle, "addvec");
  if ((error = dlerror()) != NULL) { fprintf(stderr, "%s\n", error); exit(1); }

  /* Now we can call addvec() just like any other function */
  addvec(x, y, z, 2);
  printf("z = [%d %d]\n", z[0], z[1]);

  /* Unload the shared library */
  if (dlclose(handle) < 0) { fprintf(stderr, "%s\n", dlerror()); exit(1); }
  return 0;
}

第 51 页的流程图与第 48 页几乎一样，只有一处关键差别：加载器把控制权交给程序之后，程序自己再通过 dlopen 去叫动态链接器（原文标注：Call to dynamic linker via dlopen）。链接自己时用 gcc -rdynamic –o prog2r dll.o -ldl，产物 prog2r 是 8784 字节。

三个 API 记住就够了
dlopen 加载库并返回句柄 → dlsym 按名字取函数地址 → dlclose 卸载。出错时用 dlerror() 取错误信息（课件的代码每一处都检查了它）。

7.6 静态 vs 动态的取舍原第 53 页

静态
  • 运行时不需要查找库
  • 不需要额外的 PLT 间接跳转
  • 每个程序里都有一份库的副本，更费内存
动态
  • 磁盘／内存占用更少（hello world：7K vs 571K）
  • 共享库已经在内存与热缓存里
  • 要付出查找与间接跳转的开销

8. 库打桩：三种时机原第 54–66 页

库打桩（library interpositioning）是一种很强的链接技巧：拦截对任意函数的调用。课件第 55 页说它可以发生在三个时机 —— 编译时、链接时、加载／运行期 —— 而这三者在「要不要源码」「要不要重新编译」上差别很大。第 58–65 页用同一个 malloc／free 追踪程序把三种做法都演了一遍。

8.1 什么是库打桩原第 54–57 页

课件第 55 页：这个技巧在教材（CS:APP）第 7.13 节有完整记述。打桩可以发生在：编译时（源码被编译的时候）、链接时（可重定位目标文件被静态链接成可执行文件的时候）、加载／运行期（可执行文件被载入内存、动态链接并执行的时候）。

用途原第 56–57 页课件举的例子
安全限制（沙箱化）；背后悄悄做加密
调试2014 年 Facebook 两位工程师用打桩调试了 iPhone 应用里一个高一岁的凶险 bug：SPDY 网络栈里的代码写错了位置，靠拦截 POSIX 的 write、writev、pwrite 找到根因
监控与剖析统计函数被调用的次数、刻画调用点与参数；malloc 追踪（检测内存泄漏、生成地址轨迹）
错误检查课程自己的 C Programming Lab 就用定制版 malloc／free 做细致的错误检查；其它实验（malloc、shell、proxy）也用打桩增强检查能力
被追踪的示例程序原第 58 页
#include <stdio.h>
#include <malloc.h>
#include <stdlib.h>

int main(int argc, char *argv[])
{
  int i;

  for (i = 1; i < argc; i++) {
    void *p = malloc(atoi(argv[i]));
    free(p);
  }

  return(0);
}
目标（课件原话）：在不破坏程序、也不修改源码的前提下，把每次分配／释放的地址与大小记录下来。三种解法分别在编译期、链接期、加载／运行期打桩 malloc 与 free。

8.2 三种打桩方式原第 59–65 页

交互：打桩方式台 —— 切换方式、输入被拦截的函数名

8.2.1 编译期打桩的关键：宏与 -I.

课件第 59 页的 mymalloc.c 用 #ifdef COMPILETIME 包住两个包装函数；第 60 页的 malloc.h 才是真正的机关（原文引用）：

#define malloc(size) mymalloc(size)
#define free(ptr) myfree(ptr)

void *mymalloc(size_t size);
void myfree(void *ptr);
为什么必须加 -I.
课件第 60 页在命令行旁边标了一句：Search for <malloc.h> leads to /usr/include/malloc.h —— 只有把当前目录放到搜索路径前面（-I.）， 编译器才会用你自己那个 malloc.h；否则它会去找系统的头文件，宏就没生效。三个文件的编译命令是 gcc -Wall -DCOMPILETIME -c mymalloc.c 与 gcc -Wall -I. -o intc int.c mymalloc.o。

8.2.2 链接期打桩的关键：--wrap

课件第 61 页的写法：包装函数叫 __wrap_malloc，里面调用 __real_malloc 去够到真正的 libc 实现；第 62 页说明链接器怎么被说服的：

gcc -Wall -Wl,--wrap,malloc -Wl,--wrap,free -o intl \   int.o mymalloc.o
  • -Wl 把后面的参数转交给链接器，并且把每个逗号换成空格；
  • --wrap,malloc 要求链接器用特殊方式解析引用：对 malloc 的引用解析成 __wrap_malloc，对 __real_malloc 的引用解析成 malloc。（free 同理。）

8.2.3 加载／运行期打桩的关键：LD_PRELOAD 与 RTLD_NEXT

课件第 63–64 页的写法很特别：函数名就叫 malloc／free（注意它没有 #include <malloc.h>），里面对真正的实现用 dlsym(RTLD_NEXT, "malloc") 去拿：

void *malloc(size_t size)
{
  void *(*mallocp)(size_t size);
  char *error;

  mallocp = dlsym(RTLD_NEXT, "malloc"); /* Get addr of libc malloc */
  if ((error = dlerror()) != NULL) { fputs(error, stderr); exit(1); }

  char *ptr = mallocp(size);       /* Call libc malloc */
  printf("malloc(%d) = %p\n", (int)size, ptr);
  return ptr;
}
gcc -Wall -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl
gcc -Wall -o intr int.c
(LD_PRELOAD="./mymalloc.so" ./intr 10 100 1000)
课件第 65 页对 LD_PRELOAD 的解释（原文）
「LD_PRELOAD 环境变量告诉动态链接器：解析未解析的引用（例如对 malloc 的引用）时，先去 mymalloc.so 里找。」 课件还提示，有些 shell 要用 env LD_PRELOAD=./mymalloc.so ./intr 10 100 1000 这种写法。 三种方式里只有它能用在任何动态链接的二进制上（第 66 页）。

8.3 三方式回顾原第 66 页

时机怎么做到限制
编译时对 malloc/free 的调用被宏展开成 mymalloc/myfree做法简单，但必须有源码并重新编译
链接时用链接器技巧做特殊的名字解析：malloc → __wrap_malloc、__real_malloc → malloc不需要源码，但要在链接这一步插手（要有 .o）
加载／运行期自己实现一套 malloc/free，用动态链接在另一个名字下把库里的 malloc/free 载进来（dlsym(RTLD_NEXT, …)）可用在任何动态链接的二进制上 —— 连 gcc 自己都能拦：env LD_PRELOAD=./mymalloc.so gcc –c int.c
课件第 63 页那处特意标注的对比
加载／运行期的写法里 不包含 <malloc.h>（课件原文标注：Observe that DON'T have #include <malloc.h>）—— 因为如果包含了它，编译器会看到 libc 对 malloc 的声明，可能引起属性（如 alloc_size）与你的定义冲突。自己写一个同名函数时，声明与定义必须完全一致。

9. 总结与测验原第 54、67 页

课件用两条「总结页」收尾：第 54 页讲链接是什么、可以发生在什么时候，第 67 页讲它在实践中会给你什么麻烦、又能给你什么能力。

9.1 链接总结原第 54、66–67 页

第 54 页
  • 链接是一项让程序可以由多个目标文件构造出来的技术；
  • 链接可以发生在程序生命周期的不同时刻：编译时（程序被编译时）、加载时（程序被载入内存时）、运行时（程序执行过程中）；
  • 理解链接能帮你避开难缠的错误，让你成为更好的程序员。
第 67 页
  • 通常：它就这么发生了，没什么大不了；
  • 有时：奇怪的错误 —— 坏的符号解析、.o／.a／.so 之间的顺序依赖；
  • 对高级用户：用打桩来追踪程序 —— 有源码没源码都行。
把这一讲压成四句话
  1. 工具链：cpp → cc1 → as → ld；汇编器产出可重定位目标文件（.o），链接器产出可执行文件（a.out），共享库是 .so。
  2. 符号解析：每个引用接上唯一一个定义；多个强符号报错，强压弱，多个弱任选一个 —— 而且链接器不检查类型。
  3. 重定位：合并节、分配地址、按重定位条目改写引用；PC 相对写「位移」，绝对引用写「地址」。
  4. 库与打桩：静态库按需拉成员（顺序要紧），共享库把链接推到加载时或运行时；#define／--wrap／LD_PRELOAD 是拦截调用的三种时机。
