课程导览原第 1–4 页

北京大学《计算机系统导论》第 16 讲：异常控制流（ECF）：异常与进程。到上一讲为止，程序的控制流都是「自己说了算」的：跳转、分支、调用、返回。这一讲处理另一种情况 —— 处理器被外部事件或指令自身的结果打断，控制权交给操作系统内核；再往前一步，内核用它造出「每个程序独占一台机器」的假象，这个假象的名字叫进程。

本讲提纲
  1. 异常控制流（ECF）
  2. 异常（Exceptions）
  3. 进程（Processes）
  4. 进程控制（Process Control）

课件的提纲页（原第 4 页）在第 8、19、31 页又重复出现三次 —— 每进入一个大主题就重贴一遍，本页也沿用这个结构。

一句话核心

CPU 只会一件事：按顺序取指、执行、再取下一条。要让它响应「磁盘数据到了」「用户按了 Ctrl-C」「除零了」，就必须允许控制流被事件劫持：硬件记下当前指令的位置、查一张表跳进内核、处理完再决定回到哪条指令。这就是异常；而进程，是内核用这套机制造出来的「独占 CPU 和内存」的假象。

与前后讲的衔接

上一讲（第 15 讲）刚讲完链接：程序被拼装成可执行文件。本讲打开「程序开始运行之后」的世界：控制权如何在用户程序与内核之间来回。下一讲（第 17 讲，ECF II）会补上信号与非局部跳转，并深入 fork/execve 的更多细节。

1. 控制流与异常控制流原第 5–7 页

先把「控制流」这个词说清楚，再看它为什么需要被「异常」地改写。处理器只做一件事：从启动到关机，按顺序读入并执行（解释）一串指令，一次一条 —— 这个序列就是 CPU 的控制流。

1.1 物理控制流原第 5 页

课件用一条竖直的时间轴画出「物理控制流」：时间从上往下流，CPU 依次执行 inst₁、inst₂、inst₃ …… inst_n，两端分别是 <startup> 与 <shutdown>。

<startup> → inst₁ → inst₂ → inst₃ → … → inst_n → <shutdown>

这条链上的每一步都由上一步决定 —— 只要程序是纯计算的，控制流就完全由程序自己说了算。麻烦出在「外界」。

1.2 改变控制流：现有机制为什么不够原第 6 页

到此为止我们学过两种改变控制流的机制，它们有一个共同点：都只是对「程序状态」变化的反应。

机制例子它响应什么
跳转与分支jmp / jne / 循环程序状态（比如上一条指令算出的条件码）
调用与返回call / ret程序状态（比如函数指针的值）

对一个有用的系统来说这是不够的 —— 下面这些情况都是「系统状态」变了，而程序内部的分支指令对此无能为力：

  • 数据从磁盘或网络适配器到达；
  • 指令除以零；
  • 用户在键盘上按下 Ctrl-C；
  • 系统定时器到期。

于是系统需要一套新机制：异常控制流（Exceptional Control Flow, ECF）。课件在第 7 页说：ECF 存在于计算机系统的所有层次。

2. 异常与异常表原第 9–11 页

异常（exception）是为响应某个事件（即处理器状态的改变）而把控制转移给 OS 内核。内核（kernel）是 OS 中常驻内存的那部分代码。这一节解决两个问题：异常怎么跳、跳到哪里去（异常表）。

2.1 异常的四步：从事件到返回原第 9 页

课件第 9 页画的是横跨「用户代码 / 内核代码」的一条控制流：正在执行的指令记为 I_curr，它的下一条记为 I_next；事件发生时，控制权交给内核里的异常处理器（exception handler），处理器处理完之后有三种出路：

返回路径含义谁会这样返回
返回 I_current回到刚才那条指令，重新执行它故障（如缺页：把页装入后再执行一次就成功了）
返回 I_next回到下一条指令，继续往下走中断与陷阱（如系统调用、定时器中断）
终止（abort）不返回，直接结束当前程序中止（如非法指令、奇偶校验错、机器检查）

课件第 9 页举的事件例子：除零、算术溢出、缺页、I/O 请求完成、按下 Ctrl-C。

2.2 异常表与异常号原第 10 页

  • 每一类事件都有一个唯一的异常号 k（exception number）；
  • k 是异常表（exception table）的下标 —— 这张表也叫中断向量（interrupt vector）；
  • 异常 k 每次发生，都调用处理器 k（handler k）。

表长 n，表项是 0、1、2、……、n−1，每一项指向一段「Code for exception handler i」。所以「跳到哪里」这件事在硬件里就是一次数组索引。

交互：异常处理流程模拟器 —— 给定异常号与返回类型，走一遍「事件 → 查表 → 处理器 → 返回」
为什么用「表」而不是「长 if-else」
异常号是硬件在事件发生的那一瞬间给出来的，处理必须快且不依赖分支预测：把 k 直接当数组下标，一次访存就能拿到处理器入口地址。这也解释了为什么异常号必须是「每种事件唯一」的 —— 它是索引，不能撞车。

2.3 异常的两大族与四小类原第 11 页

ECF
├── Asynchronous（异步，来自处理器外部） ── Interrupts（中断）
└── Synchronous （同步，执行指令的结果） ── Traps（陷阱）· Faults（故障）· Aborts（中止）

第 11 页只是把这棵「（不完全的）分类树」先摆在台面上；第 12、13 页再分别展开异步与同步两支 —— 下一节。

3. 中断、陷阱、故障、中止原第 12–13 页

四类异常的差别可以压成两个问题：事件来自哪里（处理器外部 / 执行指令的结果），以及处理器返回后去哪（下一条 / 刚才那条 / 不返回）。把这两问当成两个坐标轴，四类异常就各占一个格子。

3.1 异步异常：中断原第 12 页

  • 由处理器外部的事件引起；
  • 通过置起处理器的中断引脚（interrupt pin）来表示；
  • 处理器返回「下一条」指令（I_next）—— 被打断的指令已经执行完了。

课件给的例子：

  • 定时器中断：外部定时器芯片每隔几毫秒触发一次中断，内核靠它把控制权从用户程序手里收回来（这正是第 7 节上下文切换的动力源）；
  • 来自外部设备的 I/O 中断：键盘上按 Ctrl-C、网络包到达、磁盘数据到达。

3.2 同步异常：陷阱、故障、中止原第 13 页

类别是否有意可恢复性课件给的例子返回行为
陷阱
Traps		有意（intentional）—系统调用、断点陷阱、特殊指令返回到「下一条」指令
故障
Faults		无意，但可能可恢复可恢复 / 不可恢复缺页（可恢复）、保护性故障（不可恢复）、浮点异常要么重新执行出错的那条（当前）指令，要么终止
中止
Aborts		无意且不可恢复不可恢复非法指令、奇偶校验错、机器检查终止当前程序

三类同步异常的「事件」都是执行指令的结果：陷阱是程序主动要求的（syscall 指令），故障是执行中出了问题但还有救，中止是出了没法救的问题。

交互：异常分类判定器 —— 选一个事件，页面按课件给的规则判定它的四类归属与返回点
交互：判断题 —— 四类异常与 ECF 的易错点
注意「故障」的两条出路
课件对故障的表述是 “Either re-executes faulting (‘current’) instruction or aborts”：缺页是「重执行」那一支（装入页面后再执行一次就通过），保护性故障是「终止」那一支。同属故障，结局不同 —— 判断时看的是处理器返回前问题有没有被解决。

4. 系统调用：一种「有意」的陷阱原第 14–16 页

系统调用（system call）是陷阱里最常用的一类：程序主动执行一条特殊指令，主动把控制权交给内核，请内核替它做一件用户态做不到的事（读写文件、创建进程……）。课件用「打开文件」把这条路径走了一遍。

4.1 每个 x86-64 系统调用都有唯一的编号原第 14 页

调用系统调用时，程序放进 %eax（%rax 的低 32 位）的不是函数地址，而是编号。课件给出的例子：

编号名字描述
0read读文件
1write写文件
2open打开文件
3close关闭文件
4stat取得文件信息
57fork创建进程
59execve执行一个程序
60_exit终止进程
62kill向进程发送信号

4.2 例：打开文件原第 15 页

用户调用 open(filename, options)，它调用 __open 函数，后者执行系统调用指令 syscall：

00000000000e5d70 <__open>:
  ...
e5d79:  b8 02 00 00 00    mov   $0x2,%eax   # open 是 2 号系统调用
e5d7e:  0f 05               syscall          # 返回值在 %rax
e5d80:  48 3d 01 f0 ff ff cmp   $0xfffffffffffff001,%rax
  ...
e5dfa:  c3                  retq

课件的三点总结：%rax 放系统调用号；其余参数在 %rdi、%rsi、%rdx、%r10、%r8、%r9；返回值在 %rax —— 负值表示出错，其绝对值对应负的 errno。

交互：系统调用速查器 —— 输入编号或名字，看它是什么，并生成调用它的两条指令

4.3 「几乎像一个函数调用」——但有一个重要差别原第 16 页

课件把系统调用和函数调用逐条对照，四点相同、若干点不同：

交互：系统调用 vs 函数调用 —— 切换两侧，逐项对比
别把「编号」当成「地址」
课件的原话是：其他差别「比如，『函数』的『地址』在 %rax 里」。普通函数调用把目标地址放进 call 的操作数；系统调用把编号放进 %eax，具体跳到哪段内核代码由异常表（第 2 节）决定。另一处差别是错误处理：系统调用出错时返回值是负的 errno，而标准库函数出错时返回 −1 并把 errno 这个全局变量设好 —— 第 8 节会详细讲。

5. 故障实例：缺页与非法地址原第 17–18 页

课件用同一行源代码 a[500] = 13; 的两种写法，把「故障」的两条出路各演示一遍：下标在数组内 → 缺页 → 装入后再执行一次就成功；下标越界 → 非法地址 → 发信号杀掉进程。

5.1 缺页：故障 → 装入 → 重新执行原第 17 页

int a[1000];
main ()
{
  a[500] = 13;
}
80483b7: c7 05 10 9d 04 08 0d  movl  $0xd,0x8049d10

用户写内存位置 a[500]，而这段内存所在的页当前还在磁盘上。控制流是：

movl 执行 → 异常：缺页（page fault） → 把页从磁盘拷入内存 → 返回并重新执行 movl → 这一次成功
  • 缺页处理器必须把该页装入物理内存；
  • 处理器返回给出错的那条指令（I_current）；
  • 第二次尝试成功。

5.2 非法内存引用：故障 → 检测非法 → 终止原第 18 页

int a[1000];
main ()
{
  a[5000] = 13;
}
80483b7: c7 05 60 e3 04 08 0d  movl  $0xd,0x804e360

这次同样先发生缺页异常，但处理器一看地址：它根本不是这个进程的合法地址。于是：

movl 执行 → 异常：缺页 → 检测到非法地址 → 给进程发信号 → 用户进程以 “segmentation fault” 退出

课件原文：向用户进程发送 SIGSEGV 信号，用户进程带着 “segmentation fault” 退出。

交互：缺页 / 非法地址模拟器 —— 输入下标，页面现算地址与页号，判定走哪条路
基址是反推出来的，不是抄的
课件只给了两条汇编里的有效地址：a[500] → 0x8049d10、a[5000] → 0x804e360。两个地址之差 0x804e360 − 0x8049d10 = 0x4650 = 18000 = (5000 − 500) × 4 恰好等于下标差乘 sizeof(int) —— 说明两条汇编彼此自洽；由此可反推数组基址 a = 0x8049540。上面的模拟器默认就用这个反推值，你可以把下标改成 500 或 5000 验证它能不能还原出课件里的两个地址。

6. 进程：一个正在运行的程序的实例原第 20–23、36 页

定义：进程（process）是一个正在运行的程序的实例。课件称它是计算机科学中最深刻的思想之一 —— 它不等于「程序」，也不等于「处理器」。进程给每个程序提供两个关键抽象，而这两个抽象都靠内核机制造出来。

6.1 两个抽象与提供它们的机制原第 20 页

抽象程序看到的现象内核机制
逻辑控制流
Logical control flow		每个程序看起来独占 CPU —— 好像自己的指令一条接一条地往下走，中间没有别人的指令插进来上下文切换
context switching
私有地址空间
Private address space		每个程序看起来独占主存 —— 好像整片内存只有自己在用虚拟内存
virtual memory

课件第 20 页右侧画的是同一个地址空间的四个区：从低地址到高地址依次是 Code（代码）→ Data（数据）→ Heap（堆）→ Stack（栈），再加上寄存器 —— 每个进程都有各自的一份。

6.2 多进程的假象原第 21 页

「多处理」的第一张图是纯粹的假象：内存里并排站着许多份 Memory（Stack / Heap / Data / Code）与 CPU（Registers），每个进程都以为自己有一台完整的机器。现实是：计算机同时在跑很多进程 —— 一个或多个用户的应用（浏览器、邮件客户端、编辑器……），再加上后台任务（监视网络与 I/O 设备）。

6.4 进程的三个状态原第 36 页

状态含义（课件原文展开）
运行 Running进程正在执行，或者等待被执行、最终会被内核调度（即被选中执行）
停止 Stopped进程的执行被挂起，在收到进一步的指示之前不会被调度（下一讲讲信号时会用到）
终止 Terminated进程永久停止

注意 Running 的定义里包含「已就绪但还没上 CPU」这一档：从程序员视角看，它和「正在执行」不必区分 —— 区分它们的是内核的调度器，不是你的程序。

交互：进程状态机 —— 点事件，看进程在三个状态之间怎么走
「已终止」还没结束：僵死状态

7. 复用 CPU：上下文切换与并发原第 23–30 页

「每个程序独占一台机器」是假象，造假的原材料是四样东西：内存里给每个进程留的寄存器保存区、CPU 里那一组寄存器、地址空间，以及一个每隔几毫秒响一次的定时器。这一节把假象拆开。

7.1 传统现实：单核轮流执行原第 23–26 页

课件用四页把同一张图改四遍，每页只标一句话 —— 四句话连起来就是上下文切换的全过程：

原页这一步做什么
23非执行进程的寄存器值保存在内存里（图中每个进程旁边多出一个 “Saved registers” 框）
24把当前寄存器保存进内存
25调度下一个进程执行
26装入保存的寄存器并切换地址空间（这一步整体叫上下文切换，context switch）
交互：上下文切换模拟器 —— 单核上三个进程轮流跑，寄存器在 CPU 与内存之间来回搬

7.2 现代现实：多核原第 27 页

  • 一颗芯片上有多个 CPU；
  • 它们共享主存（以及部分缓存）；
  • 每个核可以执行一个独立的进程 —— 于是「同时」在某种意义上成了真的，但进程数通常远大于核数；
  • 处理器（进程？）到核心的调度由内核完成。

7.3 并发与顺序：靠时间重叠来判定原第 28–29 页

说法课件原文
逻辑控制流每个进程都是一条逻辑控制流
并发 concurrent两个进程的控制流在时间上重叠，它们就是并发的
顺序 sequential否则它们就是顺序的

课件给的例子（单核上跑 A、B、C 三个进程）：并发：A & B、A & C；顺序：B & C。第 29 页「用户视角」再补一句：并发进程的控制流在物理上是互不重叠的，但我们可以把它们想成在互相并行地运行。

交互：并发 / 顺序判定器 —— 输入三个进程的运行区间，页面按「时间是否重叠」逐对判定并画时间轴

7.4 上下文切换发生在什么代码里原第 30 页

课件第 30 页画出两个进程的甘特图：user code → kernel code（上下文切换）→ user code，切换来回发生。三条要点：

  • 进程由内核管理，内核是一块共享的、常驻内存的 OS 代码；
  • 重要：内核不是独立的进程 —— 它作为某个已存在的进程的一部分运行；
  • 控制流通过上下文切换从一个进程传到另一个进程。
「内核不是进程」这句话的三个推论
① 内核代码没有自己的地址空间，它借用当前进程的页表（所以第 5 节的缺页处理「就发生在你的进程里」）；② 定时器中断打断的是某个具体进程，内核是在这个进程的上下文里把控制权交给调度器的；③ 用户看到的每条逻辑控制流都是「用户代码 + 内核代码」交替的连续体，不是两样东西。

8. 进程控制：错误处理、PID 与 fork原第 32–42 页

从这里开始写真正的系统编程代码。课件先立一条规矩（检查每个系统调用），再给出创建与终止进程的三个函数（fork / exit / wait），最后用它把「一个程序变成两个」这件事讲透。

8.1 系统调用的错误处理原第 32–34 页

课件第 32 页：出错时，Linux 的系统级函数通常返回 −1，并把全局变量 errno 设成出错原因。接着是一条「金科玉律」：

Hard and fast rule（课件原文）
你必须检查每一个系统级函数的返回状态；唯一的例外是那几个返回 void 的函数。

课件随后给出三层简化写法：第 32 页直接在 if 里检查并打印 strerror(errno)；第 33 页抽出一个 unix_error(char *msg) 函数（课件原注：csapp.c 里它是以 0 退出）；第 34 页再进一步，用 Stevens 风格的错误处理包装函数，把检查藏进 Fork() 里，页面上直接写 pid = Fork();。课件同时提醒：这在真实应用里「一般不是你想要的做法」—— 不是所有场合都应该一出错就退出。

交互：错误处理判定器 —— 填一个系统调用的返回值，看它算不算出错、该用哪种写法处理

8.3 fork：调用一次，返回两次原第 37–38 页

父进程调用 fork 创建一个新的、正在运行的子进程。它的返回值是这个函数最反直觉的地方：

返回值谁收到含义
< 0父进程创建失败（出错，见 8.1 节）
= 0子进程「你是新创建的那个」
> 0父进程新创建的子进程的 PID

子进程几乎与父进程完全相同：

  • 得到父进程虚拟地址空间的一份完全相同但相互独立的副本；
  • 得到父进程打开的文件描述符的相同副本；
  • 但 PID 与父进程不同。

第 38 页的「概念视图」：完整复制执行状态 → 指定一个是父、一个是子 → 恢复父或子的执行。课件对 fork 的评价是：它有意思（也常常令人困惑），因为它被调用一次，却返回两次。

交互：fork 进程数计算器 —— 选一种 fork 结构，页面模拟出进程树并数出进程数

8.4 fork 的两个例题：谁先打印说不准原第 39–42 页

int main(int argc, char** argv) {
  pid_t pid; int x = 1;
  pid = Fork();
  if (pid == 0) {  /* Child */
    printf("child : x=%d\n", ++x); return 0;
  }
  /* Parent */
  printf("parent: x=%d\n", --x); return 0;
}

课件连跑四次，打印顺序两种都出现过（父先两次、子先两次）：

linux> ./fork   parent: x=0  child : x=2     （另一种：child : x=2 先出现）

课件提醒这只是「看起来随机的两种顺序」，实际由调度器决定。第 40–41 页更狠：写一个 fork 的替身（myfork.c），在父、子两条分支里插入随机延迟（ms_sleep(parent_delay) / ms_sleep(child_delay)），把「谁先跑」的概率摊平，从而暴露程序里潜在的竞争条件。

交互：forkx2 值推演器 —— 两个进程各自改自己的 x，互不影响（课件第 42 页）
为什么 x=-1 会出现
第 42 页的 forkx2 与第 39 页的 fork 是同一段代码，只是把两条 printf 各写了两遍：子进程里 ++x 跑两次（1 → 2 → 3），父进程里 --x 跑两次（1 → 0 → −1），所以输出是 parent: x=0、parent: x=-1、child : x=2、child : x=3 这四行。两个进程的 x 是各自地址空间里的两份，改一个不影响另一个 —— 这正是第 6 节「私有地址空间」的直接后果。

9. 进程图与 fork 输出原第 43–48 页

前面已经看到「谁先打印说不准」。这一节给出判断「哪些输出可能发生、哪些不可能」的工具：进程图。它把并发程序里唯一确定的东西 —— 偏序 —— 画出来，剩下的交给拓扑排序。

9.1 进程图：把「happens before」画出来原第 43 页

  • 进程图（process graph）是刻画并发程序中语句偏序的有用工具；
  • 每个顶点是一条语句的执行；
  • a → b 表示 a 在 b 之前发生；
  • 边可以用变量的当前值标注；
  • printf 顶点可以用输出标注；
  • 每张图都从一个没有入边的顶点开始。

关键结论：图的任意一个拓扑排序都对应一个可行的全序 —— 所谓全序，就是「所有边都从左指向右」的顶点排列。反过来，违反任意一条边的排列都不可能出现。

10. 终止、收割与等待原第 49–57 页

进程怎么死、死了之后谁来收尾、父进程怎么等它 —— 三件事。僵尸（zombie）与孤儿（orphan）这两个词就是这里来的。

10.1 终止进程原第 49 页

进程会因为三个原因之一变成「终止」状态：① 收到一个默认动作是终止的信号（下一讲）、② 从 main 返回、③ 调用 exit 函数。

void exit(int status)
  • 以退出状态 status 终止；
  • 约定：正常返回状态是 0，出错时非零；
  • 另一种显式设置退出状态的方法，就是从 main 返回一个整数值；
  • exit 被调用一次，但永不返回。

10.2 收割子进程：僵尸与孤儿原第 50 页

概念课件的说法
为什么需要收割进程终止后仍然占用系统资源：退出状态、各种 OS 表项
僵尸 zombie处于这种状态的进程叫「僵尸」—— 课件的形容是「活着的尸体，半生半死」
收割 reaping由父进程对已终止的子进程执行（用 wait 或 waitpid）：父进程拿到退出状态信息，内核随后删除僵尸子进程
父进程不收割呢任何父进程在未收割子进程的情况下终止，孤儿子进程应当由 init 进程（pid == 1）收割 —— 除非 ppid == 1！那就得重启了……
什么时候必须显式收割只有长期运行的进程才需要，比如 shell 与服务器
交互：僵尸 / 孤儿生命周期模拟器 —— 逐阶段看 ps 输出，对照课件第 51、52 页的快照

10.3 wait：与子进程同步原第 53–55 页

int wait(int *child_status)
  • 挂起当前进程，直到它的某个子进程终止；
  • 作为系统调用实现（内核在等待期间可以跑别的进程 —— 课件第 53 页特别画出「以及可能还有别的用户进程，包括父进程的子进程」）；
  • 返回值是终止的那个子进程的 pid；
  • 如果 child_status != NULL，它指向的整数会被设成一个指示子进程终止原因与退出状态的值，用 wait.h 里的宏来解读：WIFEXITED、WEXITSTATUS、WIFSIGNALED、WTERMSIG、WIFSTOPPED、WSTOPSIG、WIFCONTINUED。

课件第 55 页的例子（fork9）：子进程打印 HC 后 exit(0)；父进程打印 HP、wait(&child_status)、打印 CT，最后两者（其实是父进程）打印 Bye。可行的输出是 HC HP CT Bye 或 HP HC CT Bye；不可行的是 HP CT Bye HC。

10.4 waitpid：等一个指定的进程原第 56–57 页

pid_t waitpid(pid_t pid, int *status, int options)
  • 挂起当前进程，直到指定进程终止；
  • 有各种选项（见教材）；options = 0 时就是「等这个 pid」；
  • 如果多个子进程都已经完成，wait 会以任意顺序取（课件第 56 页）；要用 WIFEXITED/WEXITSTATUS 才能知道拿到的是谁、退出状态是多少。
交互：wait / waitpid 收割顺序模拟器 —— N 个子进程各自 exit(100+i)，看父进程按什么顺序收
退出状态是被「打包」过的
wait 交回来的不是退出码本身，而是一个状态字；WEXITSTATUS(status) 才把它解出来。上面这个工具会同时显示状态字与解码结果，你也能看到 WIFEXITED 为假时（进程被信号杀死）那一支应该怎么处理 —— 下一讲讲信号时还会回来。

11. execve、程序启动栈与总结原第 58–62 页

fork 造出的是「自己的副本」；要让一个进程变成另一个程序，得用 execve。这一节还给出新程序启动时栈上到底摆了什么 —— 这是理解 main(argc, argv, envp) 参数从哪来的最后一环。

11.1 execve：在当前进程里加载并运行原第 58 页

int execve(char *filename, char *argv[], char *envp[])
参数含义（课件原文展开）
filename要加载并运行的可执行文件；可以是目标文件，也可以是以 #! 解释器开头的脚本文件（例如 #!/bin/bash）

envp[]环境变量列表，形如 "name=value" 的字符串（例如 USER=droh）；相关函数 getenv、putenv、printenv
  • 它覆盖代码、数据与栈；
  • 但保留 PID、打开的文件与信号上下文；
  • 调用一次，永不返回 —— 除非出错。

11.4 总结原第 61–62 页

异常（原第 61 页）
  • 需要非标准控制流的事件；
  • 由外部产生（中断）或由内部产生（陷阱与故障）；
  • 由 OS 内核处理，处理完可能返回下一条、重执行当前指令，或终止程序。
进程（原第 61 页）
  • 任何时刻系统里都有多个活动进程；
  • 单个核上任何时刻只有一个能执行；
  • 每个进程都看起来完全掌控处理器与私有内存空间。
进程控制（原第 62 页）
  • 孵化进程：调用 fork；一次调用，两次返回；
  • 进程完成：调用 exit；一次调用，没有返回；
  • 收割与等待：调用 wait 或 waitpid；
  • 加载并运行程序：调用 execve（或其变体）；一次调用，（正常时）没有返回。

四个函数正好对应本讲的四节内容 —— 也是下一讲（ECF II：信号与非局部跳转）的地基。
