一句话核心

Linux 把一切都表示为文件，于是内核能对外只露出一套极简接口；而 read 可能少读、write 可能少写（short count），以及 一次 read/write 就是一次内核调用（> 10 000 个时钟周期）这两件事，逼出了上面两层库：Standard I/O 与 RIO 各自用缓冲把它们包起来。

1. 文件与 Unix I/O 接口原第 4–5、41 页

Unix I/O 的全部魔法来自一个极简的抽象：文件就是一段字节序列，而所有设备都被映射成文件。于是内核只需对外提供六个函数 —— 打开、关闭、读、写、改位置、取元数据。

1.1 Linux 文件是 m 个字节的序列原第 4 页

B0, B1, …, Bk, …, Bm−1

课件用「Cool fact」形容接下来的事实：所有 I/O 设备都表示为文件 —— 磁盘分区是 /dev/sda2，终端是 /dev/tty2；连内核自己也表示为文件 —— 内核映像是 /boot/vmlinuz-3.13.0-55-generic，内核数据结构是 /proc。这套「文件到设备」的优雅映射，让内核能对外只导出一个简单接口。

1.2 六个函数与「当前文件位置」原第 5、41 页

要做的事函数（原第 5 页）原型（原第 41 页）
打开与关闭文件open() · close()int open(const char *path, int flags, mode_t mode);
int close(int fd);
读文件、写文件read() · write()ssize_t read(int fd, void *buffer, size_t max_count);
ssize_t write(int fd, void *buffer, size_t max_count);
改当前文件位置（seek）lseek()off_t lseek(int fd, off_t offset, int whence);
取文件元数据stat() · fstat()（见第 5 节）

其中「当前文件位置 = k」表示下一次读或写要从哪个偏移开始。课件第 5 页下方那条字节带正是这个意思：

B0  B1  •••  Bk−1  |  Bk  Bk+1  •••  ← 当前文件位置 = k：下一次读写从这里开始

课件在第 41 页把这两个原型又抄了一遍，并注明注释口径：read 从文件读至多 max_count 个字节到缓冲区，返回实际读到的字节数；write 从缓冲区写至多 max_count 个字节到文件，返回实际写出的字节数。两个「至多」就是 short count 的来源。

交互：文件位置模拟器 —— read / write / lseek 各执行一次，看游标与字节怎么动
「至多」两个字是本讲的伏笔
课件第 13 页写着：read(fd, buf, 512) 完全可能只返回 13 —— 这叫 short count（短计数），它不是错误。第 41 页再把这条规矩抄一遍，因为后面 RIO 包的 rio_readn 等的就是它：能出现 short count 的场景，正是 RIO 要替你兜住的场景。

2.2 文本文件、二进制文件与行尾原第 7 页

普通文件里的数据是任意的，应用程序习惯把其中一部分叫「文本文件」：只含 ASCII 或 Unicode 字符的那些；其余一律叫二进制文件 —— 比如目标文件、JPEG 图片。课件特别强调一句：Kernel doesn't know the difference!（内核分不出这两种）。

  • 文本文件是「文本行」的序列；文本行是以换行符结束的字符序列。
  • 换行符就是 0xa，也就是 ASCII 的 LF（line feed，换行）。
  • 行尾（EOL）指示符在不同系统上不一样：Linux 与 Mac OS 用 '\n'（0xa）；Windows 与互联网协议用 '\r\n'（0xd 0xa）—— 回车 CR 后跟换行 LF。

课件这一页配了一张打字机照片，标出两个动作：carriage return 把字车推回行首（对应 0xd），line feed 把纸向上推进一行（对应 0xa）。电传打字机时代这两个动作是分开的机械操作，PC 时代的「换行」把它们合成了一个字符 —— 而 Windows 保留了 0xd 0xa 两个字节，Linux 只留了 0xa，于是跨平台文本才需要「转换行尾」。照片只作示意，理解这两个代码点就够了。

交互：行尾与文件字节数 —— 同样的文本，LF 与 CRLF 差多少

3. 目录、层次与路径名原第 8–10 页

目录不是「装着文件的盒子」，而是一张把文件名映射到文件的链接表。所有目录串成一棵以 / 为根的树；而「文件在哪」这件事，最终总是靠一个路径名加一个工作目录算出来的。

3.1 目录 = 链接数组原第 8 页

  • 目录由一个链接（link）数组组成：每个链接把一个文件名映射到一个文件。
  • 每个目录至少有两个条目：.（dot）是指向自身的链接；..（dot dot）是指向目录层次中父目录的链接。
  • 操纵目录的命令：mkdir 建空目录、ls 查看目录内容、rmdir 删除空目录。

注意课件措辞：链接把 文件名映射到文件，而不是把目录映射到文件 —— 这也是为什么同一个文件可以有多个名字（硬链接），而 . 与 .. 只是两个自动生成的链接条目。

3.2 目录层次与工作目录原第 9 页

所有文件组织成一棵层次树，根目录名为 /（slash）。课件画的树（下面用表格重建）里，home 下住着 droh 与 bryant 两位用户，droh/hello.c 就是后面路径名例子里那个文件：

内核为每个进程维护一个当前工作目录（cwd），用 cd 命令修改。它是「相对路径名」的起点。

交互：路径名解析器 —— 给 cwd 与路径，一步步算出它指向哪个文件
顺带一提：cwd 是「每进程」的
课件第 9 页说内核为 每个进程维护 cwd。这和第 6 节要讲的「描述符表每进程一张、打开文件表全系统共享」是同一类分层思路：进程私有的状态放进程里，全局的对象放内核里。shell 里 cd 只改了它自己（以及它 fork 出来的子进程）的 cwd，别的进程纹丝不动。

4. 打开、关闭、读、写与 short count原第 11–17、41 页

六个函数里最常打交道的四个。课件一页一个函数，每页都把「返回值」讲透 —— 因为每一个返回值都可能是错误信号，而 read/write 的返回值还多一层歧义：比请求的少，不代表出错。

4.1 open：拿到一个小的整数原第 11 页

打开文件就是告诉内核你准备访问它。返回值是一个小的标识整数 —— 文件描述符（file descriptor）。fd == -1 表示出错。每个由 Linux shell 创建的进程，出生时就带着三个连着终端的打开文件：

int fd; /* file descriptor */
if ((fd = open("/etc/hosts", O_RDONLY)) < 0) {
    perror("open");
    exit(1);
}
fd名称含义
0stdin标准输入
1stdout标准输出
2stderr标准错误

0/1/2 被占着，所以程序里第一次 open 拿到的一般是 3 —— 这一点在第 7 节的 ffiles 例题里会看到它的后果。

4.2 close：连「显然不会失败」的函数也要查返回值原第 12 页

关闭文件是告诉内核「用完了」。课件用两句话给出态度：关闭一个已经关闭的文件，在多线程程序里是灾难的配方；教训：永远检查返回码 —— 哪怕 close() 这种看起来人畜无害的函数。

4.3 read 与 write：位置会动，返回值会短原第 13–14 页

读文件 = 把字节从当前文件位置复制到内存，然后更新文件位置；写文件同理，方向相反。课件的两个例子都声明了 char buf[512]：

读（原第 13 页）

char buf[512]; int fd; /* file descriptor */ int nbytes; /* number of bytes read */ /* Open file fd ... */ /* Then read up to 512 bytes from file fd */ if ((nbytes = read(fd, buf, sizeof(buf))) < 0) { perror("read"); exit(1); }

写（原第 14 页，括号已补全）

char buf[512]; int fd; /* file descriptor */ int nbytes; /* number of bytes read */ /* Open the file fd ... */ /* Then write up to 512 bytes from buf to file fd */ if ((nbytes = write(fd, buf, sizeof(buf))) < 0) { perror("write"); exit(1); }

勘误一：原第 14 页 write 那行的括号少了一个
原课件第 14 页写的是 if ((nbytes = write(fd, buf, sizeof(buf)) < 0) { —— 开括号四个、闭括号三个，而且 < 0 落在了赋值里面，这段代码根本编译不过（本机 clang 实测：error: expected ')'）。同一课件第 13 页的 read 版本是对的，CS:APP 原书也是对的。本页按 if ((nbytes = write(fd, buf, sizeof(buf))) < 0) { 呈现。

两页的正文都强调：nbytes < 0 才表示出错；返回类型 ssize_t 是有符号整数（所以能表示 −1）；short count（nbytes < sizeof(buf)）完全可能出现，而且不是错误。

4.4 两个逐字节拷贝的例子原第 15、17 页

课件用两个「把文件拷到标准输出」的程序做对照：前者一次搬 1 个字节，后者一次搬 BUFSIZE 个字节。两人的循环都是靠返回值控制：

showfile1_nobuf.c（原第 15 页）

#include "csapp.h" int main(int argc, char *argv[]) { char c; int infd = STDIN_FILENO; if (argc == 2) { infd = Open(argv[1], O_RDONLY, 0); } while(Read(infd, &c, 1) != 0) Write(STDOUT_FILENO, &c, 1); exit(0); } showfile1_nobuf.c

演示：linux> strace ./showfile1_nobuf names.txt

showfile2_buf.c（原第 17 页，声明已补）

#include "csapp.h" #define BUFSIZE 64 int main(int argc, char *argv[]) { char buf[BUFSIZE]; int infd = STDIN_FILENO; if (argc == 2) { infd = Open(argv[1], O_RDONLY, 0); } while((nread = Read(infd, buf, BUFSIZE)) != 0) Write(STDOUT_FILENO, buf, nread); exit(0); } showfile2_buf.c

演示：linux> strace ./showfile2_buf names.txt

勘误二：原第 17 页漏了 ssize_t nread; 这一行声明
原课件第 17 页的代码里只声明了 char buf[BUFSIZE]; 与 int infd，却在循环里直接用 nread —— 本机 clang 实测：error: use of undeclared identifier 'nread'。Read() 的返回值是 ssize_t（和 Unix 的 read 一样），本页按 ssize_t nread; 补上呈现。

4.5 short count 什么时候出现原第 16、41 页

可能出现 short count
  • 读的时候遇到 EOF（end-of-file）
  • 从终端读文本行
  • 读或写网络套接字
绝不会出现 short count
  • 读磁盘文件（除 EOF 之外）
  • 写磁盘文件

课件给的结论只有一句：最佳实践是永远为 short count 做好准备（best practice is to always allow for short counts）。

5.2 statcheck.c：两个宏搞定一切原第 20 页

课件用一个极短的例子展示元数据的用法：用 S_ISREG / S_ISDIR 判断类型，用 st_mode & S_IRUSR 判断属主是否可读。程序跑三次，输出三种结果：

statcheck.c

int main (int argc, char **argv) { struct stat stat; char *type, *readok; Stat(argv[1], &stat); if (S_ISREG(stat.st_mode)) /* Determine file type */ type = "regular"; else if (S_ISDIR(stat.st_mode)) type = "directory"; else type = "other"; if ((stat.st_mode & S_IRUSR)) /* Check read access */ readok = "yes"; else readok = "no"; printf("type: %s, read: %s\n", type, readok); exit(0); } statcheck.c

三次运行（原第 20 页原话）

linux> ./statcheck statcheck.c type: regular, read: yes linux> chmod 000 statcheck.c linux> ./statcheck statcheck.c type: regular, read: no linux> ./statcheck .. type: directory, read: yes

chmod 000 把权限位全部清掉，于是 st_mode & S_IRUSR 为 0 —— 但这个文件仍然是 regular。类型位与权限位住在同一个 st_mode 里，互不影响。

交互：st_mode 解码器 —— 给一个八进制模式位，算出类型与权限

6. 内核如何表示打开的文件原第 21–27 页

这是本讲最值钱的一节：内核用三张表表示「哪些进程打开了哪些文件」。把它们摆在一起，fork 共享、dup2 重定向这些行为就不再是「规定」，而是表结构决定的必然后果。

6.1 三张表原第 21 页

表作用域表项里有什么
描述符表 Descriptor table每个进程一张一行一个 fd，指向「打开文件表」里的某个表项
打开文件表 Open file table所有进程共享文件位置（File pos）、引用计数 refcnt、文件访问模式（File access）、文件类型……
v-node 表 v-node table所有进程共享文件大小（File size）、文件访问、文件类型等 stat 结构信息

课件第 21 页的例子是「两个描述符指向两个不同的打开文件」：fd 1（stdout）指向终端，fd 4 指向一个打开的磁盘文件；两个打开文件表表项的 refcnt 都是 1。页面下方那句总结很重要：File pos is maintained per open file —— 文件位置记在打开文件表表项上，不是记在描述符上，也不是记在 v-node 上。

6.2 文件共享：两次 open = 两个表项原第 22 页

两个不同的描述符也可以指向同一个磁盘文件 —— 只要它们是通过两次 open（同一个文件名参数）得到的：那会创建两个独立的打开文件表表项，各自有自己的 File pos，最终指向同一个 v-node。课件称之为「逻辑上不同、物理上相同的文件」。

6.3 fork：子进程继承描述符，共享文件位置原第 23–24 页

  • fork 之前：父子共用一套的前提还不存在，描述符表只有父进程的，打开文件表表项 refcnt 全为 1。
  • fork 之后：子进程继承父进程的打开文件；子进程的描述符表与父进程一模一样，而每个打开文件表表项的 refcnt 加 1。
  • 课件第 23 页还有一句关键补充：exec 系列函数不会改变这个局面（要用 fcntl 才能改）。
所以 fork 之后「文件位置」是共享的
子进程的 fd1 与父进程的 fd1 指向同一个打开文件表表项，也就是同一个 File pos。父进程读走一个字节，子进程接着读到的就是下一个字节 —— 这正是第 7 节 ffiles2.c 那道题的答案来源。第 24 页图下标着「File is shared between processes」。

6.4 dup2：shell 重定向的全部秘密原第 25–27 页

课件的设问是：shell 是怎么实现 I/O 重定向的？

linux> ls > foo.txt   /* 答：调用 dup2(oldfd, newfd) */

dup2(oldfd, newfd) 做的事只有一件：把（每进程的）描述符表里 newfd 那一项，改成和 oldfd 一样。于是第 25 页画出 before/after 两张表：dup2(4, 1) 之前 fd1 → a，之后 fd1 → b（fd4 本来就指向 b）。

第 26、27 页把这个动作拆成两步：

  1. Step 1：打开要重定向到的文件 —— 发生在执行 shell 代码的子进程里，exec 之前。此刻 fd1 仍指向终端（File A），新开的 fd4 指向磁盘文件（File B）。
  2. Step 2：调用 dup2(4, 1) —— 让 fd 1（stdout）指向 fd 4 所指的磁盘文件。图上随之变化：File A 的 refcnt 变成 0（stdout 原来那个表项没人引用了，被释放），File B 的 refcnt 变成 2（fd1 与 fd4 同时引用）。子进程接着 exec，程序以为自己还在往 stdout 写，其实全进了文件。

7.1 ffiles1.c：dup2 之后谁跟谁共享原第 28–29、56 页

三次 open 同一个文件，各自建一个打开文件表表项（三个独立的 File pos，全在 0）；然后 Dup2(fd2, fd3)：

程序（原第 28 页）

#include "csapp.h" int main(int argc, char *argv[]) { int fd1, fd2, fd3; char c1, c2, c3; char *fname = argv[1]; fd1 = Open(fname, O_RDONLY, 0); fd2 = Open(fname, O_RDONLY, 0); fd3 = Open(fname, O_RDONLY, 0); Dup2(fd2, fd3); Read(fd1, &c1, 1); Read(fd2, &c2, 1); Read(fd3, &c3, 1); printf("c1 = %c, c2 = %c, c3 = %c\n", c1, c2, c3); return 0; } ffiles1.c

答案（原第 29 页）

文件内容为“abcde”时输出：

c1 = a, c2 = a, c3 = b

课件在 Dup2(fd2, fd3); 旁边标注了 dup2(oldfd, newfd)，提醒参数次序：把 newfd 改成 oldfd 的副本。

  • fd1、fd2、fd3 是三次 open 的产物，本来就是三个独立表项，位置都在 0。
  • Dup2(fd2, fd3) 让 fd3 指向 fd2 的表项 —— 只复制描述符表的一格，不新建打开文件表表项。
  • 于是前两次读各自从位置 0 拿到 a，第三次读走的是 fd2 那个表项（位置已推进到 1），拿到 b。

7.2 ffiles2.c：fork 之后谁先读到第二个字节原第 30–31、57 页

这个程序的精彩之处在一个看似无关的细节：int s = getpid() & 0x1; 写在 fork 之前，所以父子拿到的 s 是同一个值（父进程 pid 的奇偶）。父睡 s 秒、子睡 1−s 秒 —— 必然有一个睡 0 秒、另一个睡 1 秒，于是「谁先读第二个字节」完全由父进程 pid 的奇偶决定。

程序（原第 30 页）

#include "csapp.h" int main(int argc, char *argv[]) { int fd1; int s = getpid() & 0x1; char c1, c2; char *fname = argv[1]; fd1 = Open(fname, O_RDONLY, 0); Read(fd1, &c1, 1); if (fork()) { /* Parent */ sleep(s); Read(fd1, &c2, 1); printf("Parent: c1 = %c, c2 = %c\n", c1, c2); } else { /* Child */ sleep(1-s); Read(fd1, &c2, 1); printf("Child: c1 = %c, c2 = %c\n", c1, c2); } return 0; } ffiles2.c

课件第 31 页下方还有一行：Bonus: Which way does it go?

两种可能的输出（原第 31 页原话）

Child: c1 = a, c2 = b Parent: c1 = a, c2 = c Parent: c1 = a, c2 = b Child: c1 = a, c2 = c

两种都出现，但不是随机的：c1 恒为 a（fork 之前父进程已经读走第一个字节，父子共享的那个 File pos 现在是 1），而第二个字节 b 归先醒来（睡 0 秒）的那个进程，后醒的只能拿到 c。

8. 标准 I/O 与缓冲原第 33–38 页

C 标准库（libc.so）在一套文件描述符之上，又造了一层更高级的接口：流（stream）。它替你做缓冲、替你处理 short count，代价是你再也看不到元数据、也不能在信号处理器里用它。

8.1 标准 I/O 函数与流原第 33–34 页

8.2 为什么要缓冲原第 35 页

  • 应用程序经常一次读写一个字符：getc、putc、ungetc、gets、fgets（比如「一次一个字符读一行文本，遇到换行停下」）。
  • 而 read 和 write 需要陷入内核（kernel call），课件给的量级是 > 10 000 个时钟周期。
  • 于是有了带缓冲的读：用 Unix 的 read 一次抓一整块字节；用户的输入函数从这个缓冲里一个字节一个字节地拿；缓冲空了就再抓一块。
Buffer：  [ 已经读走的 | 还没读的 ]   /* 原第 35 页原话：Buffer / already read / unread */

9. RIO：健壮的 I/O 包原第 39–49 页

课件第 39、40 页的分隔页先把话说重：Standard I/O 与 RIO 是两套互不兼容的库，都架在 Unix I/O 上。RIO 是 CS:APP 自带的「教学用包装」（课件原话：15-213 special wrappers）—— 它替你处理错误检查、信号、short count 这三件烦心事。

9.1 两类函数原第 42–43 页

类别函数用途与要点
无缓冲的二进制输入输出rio_readn · rio_writen接口与 Unix 的 read/write 相同；特别适合在网络套接字上搬运数据。返回：成功则为传输的字节数，rio_readn 只在遇到 EOF 时返回 short count，出错为 −1；rio_writen 永不返回 short count。只有在「你知道要读多少字节」时才用它。

9.2 rio_readn 的实现原第 44 页

短短二十行，把「short count 不是错」这条规矩用循环兜住了。三个细节值得盯着看：EINTR（被信号处理器打断）要重试、读到 0（EOF）要跳出、返回值是 n − nleft。

ssize_t rio_readn(int fd, void *usrbuf, size_t n)
{
    size_t nleft = n;
    ssize_t nread;
    char *bufp = usrbuf;
    while (nleft > 0) {
        if ((nread = read(fd, bufp, nleft)) < 0) {
            if (errno == EINTR) /* Interrupted by sig handler return */
                nread = 0;       /* and call read() again */
            else
                return -1;       /* errno set by read() */
        }
        else if (nread == 0)
            break;              /* EOF */
        nleft -= nread;
        bufp += nread;
    }
    return (n - nleft);         /* Return >= 0 */
}
交互：rio_readn 逐步 —— 给「要读 n 字节」与「文件还剩多少」，看 read 被调用几次

9.3 rio_readlineb / rio_readnb：带缓冲的输入原第 45–46 页

void rio_readinitb(rio_t *rp, int fd);
ssize_t rio_readlineb(rio_t *rp, void *usrbuf, size_t maxlen);
ssize_t rio_readnb(rio_t *rp, void *usrbuf, size_t n);
/* Return: num. bytes read if OK, 0 on EOF, -1 on error */
  • rio_readlineb 读一条文本行，最多 maxlen 字节，存进 usrbuf；特别适合从网络套接字读文本行。停止条件有三个：读满 maxlen 字节、遇到 EOF、遇到换行符 '\n'。
  • rio_readnb 读至多 n 字节；停止条件两个：读满/EOF。
  • 两者可以在同一个描述符上任意交错调用 —— 它们共用同一个缓冲。
  • 课件第 46 页的警告：不要与 rio_readn 交错（rio_readn 绕过缓冲直接读内核，会让缓冲里已预读的字节「看不见」）。

9.4 缓冲的记账方式原第 47–48 页

课件第 47 页把文件画成两段：已经进了缓冲的部分（还能再分成「已被用户读走」与「还没读」）与还没见过的部分。第 48 页给出 rio_t 的全部字段 —— 只有三个变量在记账：

三个变量怎么配合
  • rio_cnt：缓冲里还没被用户读走的字节数 —— 和第 1 节的「当前文件位置」是一回事，只不过位置管的是文件，rio_cnt 管的是缓冲。
  • rio_bufptr：缓冲里下一个待读字节的指针。
  • 缓冲空了（rio_cnt == 0）才再调一次 read 抓 RIO_BUFSIZE 个字节进来。

10. 该用哪一种 I/O原第 51–55 页

三套接口摆在一起，第 51 页替所有人问了那句最实际的话：Which ones should you use in your programs? 答案不是「哪个最好」，而是「按场景选」—— 而且总原则是：能用高级的，就别用低级的。

10.1 Unix I/O 的优缺点原第 52 页

优点
  • 最通用、开销最低的 I/O 形式；
  • 所有其它 I/O 包都是用它实现的；
  • 提供了访问文件元数据的函数；
  • async-signal-safe（异步信号安全），可以在信号处理器里安全使用。
缺点
  • 处理 short count 很棘手、易错；
  • 高效地读文本行需要某种缓冲，同样棘手易错；
  • 这两个问题分别由 Standard I/O 与 RIO 包解决。

10.2 Standard I/O 的优缺点原第 53 页

优点
  • 缓冲通过减少 read/write 系统调用次数提高效率；
  • short count 被自动处理。
缺点
  • 不提供访问文件元数据的函数；
  • 函数不是 async-signal-safe，不适合信号处理器；
  • 不适合在网络套接字上输入输出 —— 流与套接字上的限制互相打架，且文档很少（CS:APP3e 10.11 节）。

10.3 选型规则原第 54 页

什么时候用哪个为什么
处理磁盘或终端文件Standard I/O缓冲效率 + 自动处理 short count
在信号处理器里raw Unix I/O只有它是 async-signal-safe
需要绝对最高性能的少数场合raw Unix I/O最少的一层封装
读写网络套接字RIO套接字上 short count 是常态；避免在套接字上用 Standard I/O

总原则原话：use the highest-level I/O functions you can —— 很多 C 程序员一辈子只用 Standard I/O 就够了；但要确保你真的理解你在用的函数。

10.4 二进制文件：三个禁忌原第 55 页

禁忌例子为什么

11.1 访问目录：只推荐读条目原第 59 页

  • 对目录唯一推荐的操作是：读它的条目（read its entries）。
  • dirent 结构：保存一个目录条目的信息；DIR 结构：保存「正在遍历」的目录信息。
  • 三件套：opendir 打开、readdir 逐个取、closedir 关闭。
#include <sys/types.h>
#include <dirent.h>
{
    DIR *directory;
    struct dirent *de;
    ...
    if (!(directory = opendir(dir_name)))
        error("Failed to open directory");
    ...
    while (0 != (de = readdir(directory))) {
        printf("Found file: %s\n", de->d_name);
    }
    ...
    closedir(directory);
}

循环条件 0 != (de = readdir(directory)) 和第 4 节里那几个 Read(...) != 0 是同一个套路：用「非零即失败」的返回值控制循环。别忘了 . 与 .. 也在这串条目里 —— 它们是每个目录天生就有的两个链接。
