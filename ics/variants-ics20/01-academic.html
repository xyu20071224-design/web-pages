一句话核心

翻译一次地址，抽象上是「查页表」；工程上必须解决三个代价问题：查表要两次访存（→ TLB）、页表本身太大（→ 多级页表）、上下文切换后 TLB 内容作废（→ flush 或 ASID）。解决好之后，地址翻译就成了一台机器，剩下的能力（共享、写时复制、按需加载）都是从它免费长出来的。

这些内容在整门课里的位置

上一讲（虚拟内存 I）给了页表与缺页的机制；本讲把它们落到真实硬件上。第 13 讲的缓存、第 12 讲的存储层次在这里汇合 —— 页表项（PTE）自己也是「内存里的数据」，也要经过缓存。下一讲（动态内存分配）会用到这里的内存映射。

1. 为什么需要 TLB原第 3–12 页

课件用四张「Question #N」页把实现虚拟内存的四个痛点摆出来，每一问立刻给答案。前两问关于速度：PTE 能不能被缓存？每次访问都走两遍内存怎么办？

1.1 两副面孔与页命中的五步原第 3–8 页

程序员视角（课件第 3 页）
  • 每个进程有自己私有的线性地址空间；
  • 不会被其它进程破坏。
系统视角（课件第 3 页）
  • 通过缓存虚拟内存页来高效使用内存；之所以高效，全靠局部性；
  • 简化内存管理与编程；
  • 提供一个方便的插入点（interpositioning point）来检查权限，从而简化保护。

第 4、5 页复习页表本身：页表把虚拟页映射到物理页，每个页表项（PTE）里有有效位与物理页号 PPN（有效位为 0 时页不在内存里，缺页）。查表用的地址是页表基址寄存器 PTBR 给出的；虚拟地址被切成 VPN（虚拟页号）+ VPO（虚拟页内偏移），物理地址切成 PPN + PPO，其中 VPO 与 PPO 是同几位、直接照抄。

第 6、8 页给出一次页命中的五个步骤（括号里是第 8 页补充的关键事实）：

1) 处理器把虚拟地址交给 MMU
2–3) MMU 从内存中的页表取出 PTE（PTE 和别的内存字一样，会被 L1 缓存 —— 所以要走一趟 L1，可能命中也可能缺失）
4) MMU 把物理地址交给缓存/内存
5) 缓存/内存把数据字送回处理器
交互：一次访存的三种命运 —— 单步看每一步落在哪里、走了几次内存
Question #1（原第 7–8 页）：PTE 会像其它内存访问一样被缓存吗？
会 —— 也不会。PTE 就是内存里的数据，第一次读它要经过 L1 数据缓存（PTEA 是「PTE 的地址」，它自己也要翻译吗？不 —— 页表用的物理地址由 MMU 直接给出，见图）；但 PTE 可能被其它数据访问挤出缓存，而且即使命中也要等一小段 L1 延迟。这两条就是下一问的伏笔。

1.2 三个问号与 TLB原第 9–12 页

Question #2（第 9 页）：每次都要走两遍内存，是不是太慢了？是 —— 所以真实的 MMU 不会这么干。第 10–11 页的答案：TLB（Translation Lookaside Buffer，旁路转换缓冲） —— MMU 里一块又小又快、专用的 PTE 硬件缓存，装着少数几个页的完整页表项。课件原话：通常一次 TLB 命中就消掉了做一次页表查询所需的 k 次内存访问。

Question #3（第 13 页）：页表那么大，怎么塞进内存？是 —— 所以真实页表不是简单数组（见第 2 节）。Question #4（第 17 页）：上下文切换后 TLB 里的内容不就错了？会错，所以要做事：方案 1 切换时冲刷（flush）整个 TLB；方案 2 给每个 TLB 项关联一个进程 ID（ASID）—— 下面第二节的模拟器把两者的代价摆在一起比。

第 12 页的 TLB 缺失路径比命中多一步：要用 PTEA 去内存取 PTE，再重放这次访问。课件补了一句「幸运的是 TLB 缺失很少见 —— 为什么？」答案就在第 1.1 节：局部性。一个页有 4 KB，命中一个页意味着接下来成百上千次访问都落在同一个 TLB 项上。

交互：上下文切换时怎么办 —— 对比 flush 与 ASID 两种方案

2. 多级页表原第 13–17 页

Question #3 的答案是本讲最漂亮的一处工程折衷：不让页表单级铺满整个地址空间，而是按需分层。核心算术只有一句：单级页表大小 = 页数 × PTE 宽度。

2.3 k 级页表：翻译与级数原第 16–17 页

第 16 页给出 k 级翻译的骨架：虚拟地址被切成 VPN1 | VPN2 | … | VPNk | VPO，页表基址寄存器（属于进程上下文）指向一级表；每一级用自己的 VPN 段做索引，PTE 里存的是下一级表的物理基址，走到第 k 级才拿到 PPN，与 VPO 拼成物理地址。多级让页表体积大幅下降（未使用的区域不需要二级表），代价是一次翻译要访问 k 个 PTE —— 所以 TLB 更不可少了。

级数不是拍脑袋定的：如果每张表都要装得进一个页面，那么每一级能覆盖的位数就是 log2(页大小 / PTE 宽度)。下面的计算器据此算「需要几级」。

交互：级数计算器 —— 每张表装进一个页面时，要几级才够？
课件第 16 页的两个要点
① 多级大幅减小页表体积；② 代价是 k 次访存。级数与每级位数的选择因此是一个权衡：级数多 → 稀疏时省内存、稠密时多走路；级数少 → 走路快、但大地址空间下页表庞大。i7 的答案见第 6 节：每级 9 位、共 4 级，正好覆盖 36 位 VPN。

读这三个填空最容易踩的两处
①「命中」= tag 相同 且 有效位为 1。第 26 页的 0x0020 就是反例：TLBT = 0x00 这一路确实坐在组 0 里（第 21 页的 TLB 表写着 (00, –, 0)），但它的有效位是 0 —— 所以是未命中，必须回页表。这正是「有效位」存在的意义。
② PPN 从哪来，取决于 TLB 是否命中。命中时 PPN 由 TLB 直接给出（第 24 页 0x0D）；缺失时要查页表（第 26 页 0x28）；页表说「不在内存」时根本没有 PPN（第 28 页写 TBD）。三种情况课件都印了 —— 一字之差背后是三条不同的硬件路径。

6. Core i7 与四级页表原第 30–36 页

从第 30 页起进入真实硬件。Core i7 把前面所有概念一次性落地：4 级页表、每级 9 位；L1 TLB 与 L1 数据缓存都做了「虚拟索引、物理标记」的加速。这一节的所有数字都来自课件第 31–36 页。

第 32 页的图上有三处「集合大小」，来源各不相同，别互相借位：L1 TLB 是 16 sets, 4 entries/set（= 64 项，与第 31 页的「64 entries, 4-way」一致）→ TLBI 取 VPN 的低 4 位；L1 d-cache 是 64 sets, 8 lines/set（64 组 × 8 路 × 64 B = 32 KB，与第 31 页的「32 KB, 8-way」一致）→ CI 取 6 位；而 四级页表每级是 512 项（9 位索引）。三个「组数」分别是 16、64、512，对应的位段是 4、6、9 —— 混一个，地址就全错。

6.3 逐级翻译与「虚拟索引、物理标记」原第 35–36 页

7. Linux 进程地址空间与缺页原第 37–39 页

课件从第 37 页开始把视角从硬件切回操作系统：Linux 用一个「区域（area）」的链表来描述一个进程的虚拟地址空间，缺页处理就是在这张表上做判定。

7.1 进程虚拟地址空间原第 37 页

7.3 缺页处理：三分支原第 39 页

第 39 页的图把缺页处理总结成三个分支，对应图上标的 1、2、3：

1 · 地址不在任何区域里

段错误（Segmentation fault）：访问一个不存在的页。

2 · 在区域里，但权限不符

保护异常（Protection exception）：例如往只读页里写。Linux 会把它也报成 Segmentation fault。

3 · 在区域里、权限也对

正常缺页（Normal page fault）：选中一个牺牲页，把需要的页读进来，更新页表，重新执行这条指令。

交互：缺页判定器 —— 给地址与访问类型，看内核走哪条分支
缺页 ≠ 出错
「正常缺页」是例行公事：程序启动时 .text/.data 都还没有物理页，第一次碰它们必然缺页；mmap 出来的区域、malloc 出来的堆也是这样长出来的。真正出事的是 1、2 两条分支 —— 它们都让进程挨一个 SIGSEGV。

8. 内存映射与写时复制原第 40–48 页

内存映射（memory mapping）是把「磁盘对象」和「虚拟内存区域」绑起来：区域可以直接拿一个普通文件做后盾（页的初始字节来自文件的某一段），也可以拿一个匿名文件做后盾（第一次缺页时分配一整页 0 —— 按需零页 demand-zero）。被写过的脏页在内存与交换文件（swap file）之间来回搬运。

8.1 共享对象与私有对象原第 42–45 页

课件第 42 页复习虚拟内存的另一个身份：它让代码和数据可以按需在进程间隔离或共享。于是同一个磁盘对象可以被多个进程映射：

  • 共享对象（shared object）：进程 1 与进程 2 都映射同一个对象，看到同一份物理内存；它们的虚拟地址可以不同，但差必须是页大小的整数倍（课件第 44 页原话）。
  • 私有对象 + 写时复制（COW）：区域被标记为 private copy-on-write，两个进程的 PTE 都被标成只读；谁先写，谁触发保护异常，处理程序给它复制出一页新的可写页，然后重新执行那条指令 —— 只要没人写，就永远不用复制。
交互：写时复制模拟器 —— 一步一步来，看物理页什么时候才真的被复制

8.2 fork 与 execve 里的内存映射原第 47–48 页

fork 之后（第 47 页）
  • 为子进程创建 vm_struct、vm_area_struct 与页表的精确副本；
  • 两个进程的每一页都标成只读，每一段区域都标成 private COW；
  • 返回时两个进程拥有完全相同的虚拟内存；
  • 此后的写操作才通过 COW 机制产生新页 —— 对「fork 之后紧跟 execve」这种常见情况这是完美的做法（省掉一次白复制）。
execve 之后（第 48 页）
  • 释放旧的区域与页表；
  • 为新程序建新的区域与页表：代码与已初始化数据由目标文件支撑（private、file-backed），.bss 与栈由匿名文件支撑（private、demand-zero）；
  • 把 PC 设成 a.out 的入口点；
  • 之后 Linux 会按需要把代码页和数据页缺进来。

8.3 还能共享哪些页原第 49 页

第 49 页先把「容易想到的共享」列出来（fork 出来的父子进程、加载同一个可执行文件的进程 —— 比如 bash、python 解释器、浏览器、加载同一个库文件的进程），然后给出一个不那么显然的答案：内核同页合并（Kernel Same-Page Merging，KSM） —— 操作系统扫描整个物理内存找重复的页，找到就合并成一份并标成写时复制；它在 2009 年进入 Linux 内核；只对标记为「可能是候选」的页生效；在处理器上同时跑很多虚拟机时特别有用。

9. mmap 的用法原第 50–53 页

用户级的内存映射只有一个函数：mmap。课件用一个签名、三个用法、一个完整示例把它说完。

9.1 函数签名与参数原第 50–51 页

void *mmap(void *start, int len,
         int prot, int flags, int fd, int offset)
  • 做什么：把文件描述符 fd 所指文件、从 offset 起 len 字节，映射到虚拟地址 start（最好放在 start，不保证）；
  • start：填 0 表示「你（内核）挑一个地址」；
  • prot：PROT_READ、PROT_WRITE ……；
  • flags：MAP_ANON、MAP_PRIVATE、MAP_SHARED ……；
  • 返回：指向映射区起点的指针（可能不等于 start）。

第 51 页的图把这件事画成一次「搬运」：磁盘文件里 offset 起的 len 字节，对应进程虚拟内存里从 start（或内核挑的地址）起的 len 字节。

9.2 三种典型用法原第 52 页

用法怎么做要注意
读大文件用分页机制把文件搬进内存（不用自己 read 到缓冲区）—

9.3 示例：用 mmap 复制文件原第 53 页

课件第 53 页的 mmapcopy 只做一件事：不把数据搬进用户空间就复制到标准输出。注意它把 len 直接传成文件长度、offset 传 0：

void mmapcopy(int fd, int size) {
  struct stat stat; /* Ptr to memory mapped area */
  char *bufp;
  bufp = Mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
  Write(1, bufp, size);
  return;
}
int main(int argc, char **argv) {
  int fd; /* Check for required cmd line arg */
  if (argc != 2) { printf("usage: %s <filename>\n", argv[0]); exit(0); }
  fd = Open(argv[1], O_RDONLY, 0);
  Fstat(fd, &stat);
  mmapcopy(fd, stat.st_size);
  exit(0);
}

（Mmap / Write / Open / Fstat 是 CS:APP 教材的包装函数：出错就打印信息并退出，其它与系统调用同名同参。）

11.3 关键代码原第 61 页

课件的做法很直接：用 mmap 在固定地址 START_ADDR 分配 STACK_SIZE 字节，权限里带 PROT_EXEC；然后把 %rsp 换成新区域顶部往下 8 字节（保留一个 8 字节的「返回地址」位置），旧栈指针先存进 global_save_stack。攻击代码跑完后，把 %rsp 换回去，再 munmap 掉这块区域。

/* 分配新区域 */
void *new_stack = mmap(START_ADDR, STACK_SIZE,
        PROT_EXEC | PROT_READ | PROT_WRITE,
        MAP_PRIVATE | MAP_GROWSDOWN | MAP_ANONYMOUS | MAP_FIXED, 0, 0);
if (new_stack != START_ADDR) { munmap(new_stack, STACK_SIZE); exit(1); }
/* 把栈改接到新区域，并执行攻击代码 */
stack_top = new_stack + STACK_SIZE - 8;
asm("movq %%rsp,%%rax ; movq %1,%%rsp ; movq %%rax,%0"
    : "=r" (global_save_stack) /* %0 */
    : "r" (stack_top) /* %1 */ );
launch(global_offset);
/* 还原并把区域还回去 */
asm("movq %0,%%rsp" : : "r" (global_save_stack) /* %0 */ );
munmap(new_stack, STACK_SIZE);
这一步和前面的哪一节对上
这正是「VM 把权限检查做成一个方便的插入点」（第 1.1 节，课件第 3 页）的实战应用：栈页默认可读可写但不可执行，是页表项里的权限位说了算；要让学生在栈上跑代码，就得让这段内存由页表说了算地可执行 —— 而 mmap 是用户程序能申请到这种页的唯一入口。
