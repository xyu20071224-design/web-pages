一句话核心

网络编程的全部复杂性，来自一个朴素的事实：两台机器上的两个进程要交换字节，但它们之间隔着一堆互不兼容的局域网、广域网和设备。协议负责抹平差异（统一地址 + 统一分组），而套接字接口负责把「一次跨网络的读写」伪装成文件描述符上的 read/write。

于是「写网络程序」被压缩成两步：先用 getaddrinfo 把域名/服务名换成地址结构，再按固定顺序调用那几个套接字函数。

1. 协议、客户机-服务器与封装原第 2–9 页

课件用三页回答「协议是什么」，一页画客户机-服务器事务，一页画数据封装，再用四页给出全局 IP 互联网与程序员的视角。先建立「分层 + 封装」的心智模型，后面所有 API 才不是死记硬背。

1.1 什么是 internet 协议原第 2–3 页

课件先做类比：人类也有「协议」——「现在几点？」「我有个问题」；计算机之间同样需要一套约定，互联网里所有通信活动都受协议支配。要解决的核心问题是：

  • 怎么在不兼容的 LAN / WAN 之间传比特？答案：在每个主机和路由器上跑协议软件。
  • 协议（protocol）是一组规则，规定主机与路由器在把数据从一个网络搬到另一个网络时该如何配合；它抹平了不同网络之间的差异。

2. IP 地址与子网原第 10–15 页

课件用六页把 32 位地址讲透：点分十进制只是给人看的写法，真正的地址是 32 位比特；地址被切成「子网部分 + 主机部分」，子网部分由 /n 指定；而一旦进入内存，地址与端口一律是网络字节序（大端）。

2.1 点分十进制与接口原第 10 页

  • IP 地址：与每个主机或路由器接口关联的 32 位标识符。
  • 接口（interface）：主机/路由器与物理链路之间的连接。课件原话：路由器通常有多个接口，主机通常只有一到两个（例如有线以太网、无线 802.11）。
  • 点分十进制记法：把 32 位按字节切四段，每段写成十进制并用句点分隔 —— 223.1.1.1 = 11011111 00000001 00000001 00000001。
交互：IP 地址解析器 —— 点分十进制 / 十六进制 / 二进制互转，并判定类别与私有性

2.2 子网：什么是子网、怎么划原第 11–13 页

课件的定义只有一句话：子网（subnet）就是那些「不经过中间路由器就能在物理上互相到达」的设备接口的集合。IP 地址因此具有结构：

部分含义例子
子网部分同一子网里的设备都有相同的若干高位223.1.1.0/24 的高 24 位
主机部分剩下的低位部分，用来区分同一子网内的不同接口最后 8 位

划分的「配方」（第 12 页原文）：把每个接口从它的主机或路由器上摘下来，得到一个个「孤岛」，每个孤岛就称为一个子网；子网掩码 /24 表示高 24 位是 IP 地址的子网部分。

2.4 网络字节序：地址与端口在内存里躺成什么样原第 15 页

课件第 15 页给了两条规矩：

  • 32 位 IP 地址存放在 struct in_addr 里，永远以网络字节序（network byte order，即大端）存放。
  • 这对任何在分组首部里从一个机器传到另一个机器的整数都成立 —— 课件特别点名：例如用来标识一条互联网连接的端口号。
/* Internet address structure */
struct in_addr {
  uint32_t s_addr;  /* network byte order (big-endian) */
};

按约定，32 位地址里的每个字节都写成十进制、用句点分隔 —— 课件给的对照是 0x8002C2F2 = 128.2.194.242。

交互：网络字节序转换器 —— htons / htonl 到底翻了什么
为什么必须统一字节序
两台机器如果一个大端一个小端，各自按本地习惯解释首部里的同一个整数，会把 端口 80（0x0050）读成 20480（0x5000）。所以协议规定：凡是要进首部的整数，先转成网络字节序再发。页面上的转换器会同时给你「主机内存里的字节顺序」和「线上传的字节顺序」两栏 —— 你会发现在大端主机上两者相同，在小端主机上刚好逐字节倒过来，而 x86 是小端。

3.2 DNS 数据库与 nslookup原第 17–20 页

  • 互联网把 IP 地址与域名的映射维护在一个巨大的、全世界分布的数据库里，这个数据库叫 DNS。
  • 概念上，程序员可以把 DNS 数据库看成几百万条主机条目（host entry）的集合；每条主机条目定义了一组域名与 IP 地址之间的映射。
  • 用数学话说：一条主机条目是「域名集合」与「IP 地址集合」之间的一个等价类 —— 这句话就是在预告下面四种映射情形。
  • 每条主机都有一个本地定义的域名 localhost，永远映射到回环地址 127.0.0.1；用 hostname 命令可以查到本机真实的域名（课件里是 whaleshark.ics.cs.cmu.edu）。

第 25–28 页转向「怎么把这些地址交给函数」。套接字接口诞生于 80 年代初 Berkeley 版 Unix；它今天在所有现代系统上都可用（Unix 各变体、Windows、OS X、iOS、Android、ARM）。核心抽象是：

  • 对内核而言，套接字是一个通信端点；对应用程序而言，套接字是一个文件描述符，让你能从/向网络读写（Unix I/O 里所有设备都被建模成文件，网络也不例外）。
  • 常规文件 I/O 与套接字 I/O 的主要区别在于应用「怎么打开」这个描述符。
  • 地址参数需要一套结构体：通用的 struct sockaddr 与 IPv4 专用的 struct sockaddr_in，后者调用时必须强制转换成前者。
struct sockaddr {  /* 通用套接字地址：给 connect / bind / accept 传地址用 */
  uint16_t sa_family;    /* Protocol family */
  char     sa_data[14];  /* Address data  */
};
struct sockaddr_in {
  uint16_t       sin_family; /* Protocol family (always AF_INET) */
  uint16_t       sin_port;   /* Port num in network byte order */
  struct in_addr sin_addr;   /* IP addr in network byte order */
  unsigned char  sin_zero[8]; /* Pad to sizeof(struct sockaddr) */
};

为什么要两套结构？课件说得很直白：只因为设计套接字接口时 C 还没有 (void *) 这种通用指针；为了转换方便，大家采用 Stevens 约定的 typedef struct sockaddr SA;。

交互：套接字地址结构 —— 16 字节里每一格放什么
记住这条：sin_zero[8] 是为了「凑齐 16 字节」
struct sockaddr 与 struct sockaddr_in 长度都是 16 字节。sockaddr_in 里有用的是前 8 字节（family 2 字节 + port 2 字节 + addr 4 字节），后面 8 字节的 sin_zero 纯属填充，保证强制转换后布局对得上。这也是「为什么可以用一个通用指针接收任意家族地址」的物理基础 —— 第 5 节的 getaddrinfo 正是靠 ai_addrlen 把「这个地址结构有多长」一并交给你。

7.1 五个函数的要点原第 51–59 页

  • socket：int socket(int domain, int type, int protocol)。写死版 socket(AF_INET, SOCK_STREAM, 0) 表示「用 32 位 IPv4 地址、可靠（TCP）连接端点」；协议无关版用 socket(ai->ai_family, ai->ai_socktype, ai->ai_protocol)，让 getaddrinfo 自动生成参数。
  • bind：int bind(int sockfd, SA *addr, socklen_t addrlen)。读完 addr 那个端点的连接上到达的字节，就可以从 sockfd 读出；同理写 sockfd 的字节会沿着那个连接送出去。最佳实践：用 getaddrinfo 提供 addr 与 addrlen。
  • listen：int listen(int sockfd, int backlog)。把主动套接字变成监听套接字；backlog 是对「内核应排队多少个尚未处理的连接请求」的提示（课件：默认 128 左右），超过就开始拒绝。
  • accept：int accept(int listenfd, SA *addr, int *addrlen)。等待到达 listenfd 上那条连接的请求，然后把客户端的套接字地址填进 addr、把地址长度填进 addrlen，返回一个可用于与客户端通信的已连接描述符 connfd（用 Unix I/O 例程读它）。
  • connect：int connect(int clientfd, SA *addr, socklen_t addrlen)。尝试与 addr 处的服务器建立连接；成功后 clientfd 就可以读写了。得到的连接由套接字对 (x:y, addr.sin_addr:addr.sin_port) 刻画，其中 x 是客户机地址、y 是唯一标识客户机上该进程的临时端口。同样推荐用 getaddrinfo 提供参数。

  • open_listenfd 在 bind 之前多做一步：Setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, …) —— 消除来自 bind 的「Address already in use」错误。
  • 课件第 69 页有一条诚实的免责声明：生产服务器不会在第一次成功时就跳出循环，我们这样写只是为了简单。
  • 最后的结论：open_clientfd 与 open_listenfd 都与具体的 IP 版本无关。

9.4 报文格式：请求与响应原第 79–80 页

HTTP 请求

一个请求行，后跟零个或多个请求头。请求行形状：

<method> <uri> <version>

  • <method> 是 GET、POST、OPTIONS、HEAD、PUT、DELETE、TRACE 之一
  • <uri> 通常是给代理用的 URL，给服务器的则是 URL 后缀
  • <version> 是请求的 HTTP 版本（HTTP/1.0 或 HTTP/1.1）
HTTP 响应

一个响应行，后跟零个或多个响应头，之后可能有内容，用空行（"\r\n"）把头和内容分开。响应行形状：

<version> <status code> <status msg>

  • 200 OK —— 请求被无错处理
  • 301 Moved —— 提供另一个 URL
  • 404 Not found —— 服务器找不到该文件

两边都用 <header name>: <header data> 形式的头行；请求头给服务器提供附加信息，响应头里最重要的两个是 Content-Type（响应体内容的 MIME 类型）与 Content-Length（响应体内容的长度）。

交互：HTTP 报文构造器 —— 请求行 + 头 + 空行 = 一个请求

① HTTP 标准要求每一行文本都以 "\r\n" 结尾；② 一个空行（"\r\n"）终止请求头与响应头；③ 因此报文里第一个空行之后的内容就是响应体 —— 三次会话里那些 15c、1000、0 是分块传输编码（chunked）的长度标记（十六进制字节数，0 表示结束），不是正文的一部分。

10. 服务静态内容：Tiny Web 服务器原第 84–87 页

Tiny 是教材里那个「239 行带注释的 C 代码」的迷你 Web 服务器：顺序式（sequential）、能给真实浏览器同时服务静态与动态内容、支持文本/HTML/GIF/PNG/JPEG。它不完整也不健壮 —— 课件明确说：用格式错误的 HTTP 请求就能把它弄坏（比如行尾用 "\n" 而不是 "\r\n"）。

10.1 Tiny 的整体流程原第 86 页

  1. 接受来自客户端的连接；
  2. 从客户端读请求（通过已连接套接字）；
  3. 把请求拆成 <method> <uri> <version>；
    • 如果 method 不是 GET，就返回错误；
  4. 如果 URI 里含有 "cgi-bin"，就服务动态内容（fork 一个进程去执行那个程序）；课件顺带自嘲了一句：如果真有一个叫 abcgi-bingo.html 的文件，它就会做错事；
  5. 否则服务静态内容（把文件复制到输出）。

10.2 serve_static：响应头是怎么拼出来的原第 87 页

11. 动态内容与 CGI原第 88–99 页

动态内容是这件事的难点：请求里带着参数，参数要穿过服务器传到某个程序里，程序的输出又要被服务器当成响应体发回客户端。课件用 12 页把这条链路逐段拆开，最后给出一个能算出 15213 + 18213 = 33426 的完整例子。

11.1 三步：fork、执行、转发原第 88–90 页

  1. 客户端请求 GET /cgi-bin/env.pl HTTP/1.1；如果请求 URI 里含有字符串 "/cgi-bin"，Tiny 就认为这是动态内容请求。
  2. 服务器创建一个子进程，在子进程里运行 URI 所标识的那个程序（fork + exec）。
  3. 子进程运行并生成动态内容；服务器捕获子进程的输出，不加修改地转发给客户端。

12.1 代理：对客户端像服务器，对服务器像客户端原第 100–101 页

① 看到一个 IP 地址能说出它的二进制、类别、是否私有、按 /n 划分时子网地址是什么；② 知道端口号与 IP 地址进首部前要转网络字节序，并能手算一次字节颠倒；③ 能默写服务器与客户端两侧的套接字调用顺序，并说清 listenfd / connfd / clientfd 的区别；④ 能读懂一次 telnet 到端口 80 或 15213 的会话，并能用 getaddrinfo 写出协议无关的连接代码。
