课程导览原第 1 页

北京大学《计算机系统导论》第 24 讲：并发编程（Concurrent Programming）。这一讲回答一个工程问题：一个服务器怎么同时伺候多个客户端？课件给了三条路 —— 多进程、事件驱动、多线程 —— 并在这三条路上把并发的四种典型灾难（竞争、死锁、活锁、饥饿）逐个点出来。

  2. 案例：信号处理器里的 printf 死锁

一句话核心

「并发」= 多个逻辑控制流在时间上交叠。交叠带来两个后果：并行能提速，但共享状态会被交错访问。课件第 2 页的原话是：人的脑子习惯顺序思维，而「穷举一个计算机系统里全部可能的事件序列」至少是容易出错的，而且经常根本做不到。

和前后讲的衔接

上一讲的网络编程让你写出了第一个能跑的服务器；这一讲解释它只能服务一个客户的结构性原因，然后给出三种修法。课件第 11 页说明：并发里还有很多方面超出本课范围，接下来几讲会陆续展开（同步与信号量在第 25 讲）。

1.1 「并发编程很难」的原文理由原第 2 页

人的脑子是顺序的

The human mind tends to be sequential —— 我们习惯「先发生 A，再发生 B」，而并发程序里没有这种保证。

时间的概念常常骗人

The notion of time is often misleading —— 两条语句在源码里相邻，运行时的间隔却可能是任意长。

穷举事件序列做不到

「思考一个计算机系统里全部可能的事件序列」至少是 error prone（容易出错），而且 frequently impossible（经常根本不可能）。

2. 案例：信号处理器里的 printf 死锁原第 5–7 页

这是本讲唯一一个「能完整看到机制」的案例：信号处理器打断了一次 printf，而处理器自己又调用 printf —— 第 7 页解释了为什么这会死锁。

2.1 出事的代码原第 5、6 页

课件第 5、6 页反复给出同一段 catch_child（第 6 页配上 main，用一千万次循环去「撞」这个竞态）：

void catch_child(int signo) {
  printf("Child exited!\n");  // this call may reenter printf/puts! BAD! DEADLOCK!
  while (waitpid(-1, NULL, WNOHANG) > 0) continue;  // reap all children
}

第 6 页的 main 用一个 100 万次的 fork 循环来暴露它，右侧输出里滚过的是 Child #0 started … Child #5889 started 夹杂着 Child exited!。课件在第 6 页提出的问题是：Testing Printf Deadlock —— 这么测能测出死锁吗？下面这套状态机把机制摊开给你看。

交互：printf 重入死锁 —— 一步一步走，或直接穷举所有交错

2.2 第 7 页：为什么 printf 需要锁原第 7 页

课件第 7 页的三句话：printf（以及 fprintf、sprintf）实现的是带缓冲的 I/O（buffered I/O）；访问共享缓冲区需要锁（require locks to access to shared buffers）。页面中间那张图把文件缓冲拆成四段，并标出「当前文件位置」：

区段（课件原词）含义
no longer in buffer已经移出缓冲区（早就刷走了）
already read已被用户程序读走的部分
unread已读入缓冲区、还没被用户程序取走的部分
unseen还没读进缓冲区的部分

「已缓冲部分」（Buffered Portion）= already read + unread 这两段；「当前文件位置」（Current File Position）落在 unread 段的左边界上 —— 也就是「用户程序下一次读从这里开始」。这个位置与整块缓冲区都是多个线程/处理器共享的状态，所以每次 printf 都要先拿锁再改它。

死锁链条（把第 5、6、7 页串起来）
  1. 主流程调用 printf → 它内部 Acquire lock（课件第 5 页把这两步画成 Acquire / lock）；
  2. SIGCHLD 到达，内核打断主流程，跳到 catch_child；
  3. 处理器里第一句又是 printf → 它 再次去 Acquire 同一把锁；
  4. 锁不是可重入的（non-recursive），持有者是「被打断的自己」，永远不会释放 → 死锁。第 5 页把它写成 I^{lock}_{curr} → I^{signal}_{next}：当前的加锁指令之后紧跟信号处理器。
为什么这属于「难测试」的一类 bug
死锁只在特定交错下发生：信号必须在 Acquire 之后、Release 之前这个窄窗口里到达。第 6 页那段「一千万次循环 + 大量 fork」正是在赌这个窗口；页面里的模拟器会把「所有合法交错」都列出来，你可以直接看到窗口有多大、有多少种交错会死锁。

3. 迭代服务器与阻塞原第 13–18 页

先看清楚问题本身：课件第 14–17 页用同一条时间线连画四页，把「迭代服务器一次只服务一个连接」的后果逐步放大 —— 直到第 17 页给出结论。

3.1 迭代回显服务器原第 13、14、21 页

3.3 结论：结构缺陷原第 17 页

第 17 页把三件事叠在同一时刻：客户端 1 在等用户输入（User goes out to lunch / Client 1 blocks waiting for user to type in data）、服务器阻塞在 read 上等客户端 1 的数据（Server blocks waiting to read data from Client 1）、客户端 2 卡在 read 上等服务器（Client 2 blocks waiting for from server）。于是整条链被一个人「出去吃午饭」卡死。

课件的结论与出路（第 17 页原文）
Solution: use concurrent servers instead —— 并发服务器用多条并发流在同一时间服务多个客户端（Concurrent servers use multiple concurrent flows to serve multiple clients at the same time）。

3.4 第 18 页：三条路原第 18 页

第 18 页给出三种写并发服务器的方法，本讲剩下的篇幅就是逐个展开。它们的区别只有两条轴：谁来交错这些逻辑流（内核自动 / 程序员手动），以及这些流共不共享地址空间：

方案谁交错逻辑流地址空间课件原话
1. 基于进程
Process-based		内核自动交错（Kernel automatically interleaves）每条流有自己私有的地址空间Kernel automatically interleaves multiple logical flows
2. 基于事件
Event-based		程序员手动交错（Programmer manually interleaves）全部流共享同一地址空间Uses technique called I/O multiplexing
3. 基于线程

4. 方案① 基于进程原第 19–31 页

第 19–20 页先把「每个客户端 fork 一个进程」画在时间线上，第 21–27 页把代码一行行补全，第 28–31 页解释 fork 之后的资源账。

4.1 两个客户端的交错原第 19、20 页

第 19 页：客户端 1 连上后父进程 fork 出 child 1，child 1 阻塞在 read 上等客户端 1（用户出去吃午饭），而父进程回到 accept 继续等下一个。第 20 页加上客户端 2：父进程 ret accept → fork child 2，child 2 直接读写、close；两个子进程互不干扰。这就是并发服务器的第一个可行结构。

4.3 fork 之后的资源账原第 29、30 页

第 29 页的三句话是本节的核心：每个客户端由独立的子进程处理；它们之间没有共享状态（No shared state between them）；父进程与子进程各有一份 listenfd 和 connfd 的副本。

4.4 优缺点原第 31 页

优点（第 31 页原文）
  • + 能并发处理多个连接
  • + 干净的共享模型：描述符不共享、全局变量不共享、文件表共享

第 31 页把 clean sharing model 展开成三行：descriptors (no)、file tables (yes)、global variables (no)。这三行说的是 fork 出来的父子进程之间「共不共享」：描述符表和全局变量各有各的副本（no），而打开文件表是共享的（yes，这正是第 30 页引用计数的来源）。第 29 页说「No shared state between them」指的是可写的程序状态；两句并不矛盾，但只看第 31 页的三行很容易读反，本页按「父↔子」这个主语写清楚。

5. 方案② 基于事件原第 32–34 页

第二条路是不用多进程、也不用多线程：一个控制流，自己维护一张「活跃连接表」，反复问内核「哪些描述符现在有输入？」—— 这就是 I/O 多路复用（I/O multiplexing）。

5.1 事件循环的三段结构原第 32 页

第 32 页把服务器要做的事写成「维护一张活跃连接表 + 反复做四件事」：

维护集合
Server maintains set of active connections
实现上就是一个 connfd 的数组（Array of connfd’s）。
① 找出有输入的描述符
Determine which descriptors (connfd’s or listenfd) have pending inputs
用 select 这类函数实现；「有输入到达」这件事本身就是一个事件（arrival of pending input is an event）。
② 若是 listenfd 有输入
If listenfd has input, then accept connection
并把新的 connfd 加进数组（add new connfd to array）。
③ 服务所有有输入的 connfd
Service all connfd’s with pending inputs
这一步是真正干活的回显。课件注明：select 版本服务器的细节在书上。
交互：select 事件循环 —— 注入事件、轮询一次，看这一步该服务谁

把第 57 页那段程序抽象成三种原子事件，交错就是这三种事件的一个合法全序：

9.2 线程 vs 信号原第 43 页

9.3 线程方案的最终评价原第 60 页

优点（第 60 页原文）

  • + 线程比进程更高效
缺点（第 60 页原文）
  • – 无意的共享会引入微妙且难以复现的错误（subtle and hard-to-reproduce errors）
  • – 「数据共享起来有多容易」既是线程最大的优点，也是它最大的弱点
  • – 很难知道哪些数据是共享的、哪些是私有的
  • – 很难靠测试发现：坏结果的概率很低，但不是零（Probability of bad race outcome very low / But nonzero!）
「概率很低但不是零」意味着什么
第 60 页这条正是第 6 页那段「一千万次循环」测试的注解：测试跑过 = 什么都没证明。一个竞争 bug 可能在你机器上跑一万次都不出现，在客户的多核机器上一次就中 —— 而且出现的形态（哪个 bin 丢、哪个 bin 多）每次都不一样（第 58 页两张实测图就是证据）。

10. 总结与测验原第 61、11 页

第 61 页用一张三栏表给全讲收官：三种方案各自的代价写在同一栏里，读的时候请两边一起读。

第 61 页原文的三种措辞是：进程 High overhead、事件 Very low overhead、线程 Medium overhead。它们是三者互相比得出的措辞（事件 < 线程 < 进程），不是各自独立的测量值；第 42 页给的 Linux 数字（约 20K vs 10K 周期）只覆盖「创建+回收」这一步，不含上下文切换与调度差异。本页按原文措辞照实呈现，避免把 Medium 误读成「线程开销可以忽略」。（此处不是勘误 —— 原课件这两页没有错。）

10.2 一句话回看全讲综合原第 1–61 页

问题

迭代服务器一次只走一个逻辑流，第 17 页那张「三方一起卡住」的图就是它的死因。

三条路

进程（内核交错 + 私有地址空间）、事件（手动交错 + 共享地址空间）、线程（内核交错 + 共享地址空间）。

代价

共享得越容易，竞争越难发现。第 58 页的直方图与第 60 页的「概率很低但不是零」是同一件事。
