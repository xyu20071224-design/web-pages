一句话核心

两个线程各执行一句 cnt++，结果却可能是 cnt = 1 而不是 2 —— 因为 cnt++ 在机器级是「取、加、存」三条指令，交错执行时会互相覆盖。要挡掉这种交错，就得让关键区（critical section）互斥，而信号量是最经典的实现手段。

和上一讲的衔接

1. 进程与线程：回顾原第 3–8 页

同一个东西，两种画法：传统视图把进程看成「进程上下文 + 代码、数据、栈」，替代视图把它看成「线程 + 代码、数据、内核上下文」。原第 3–6 页连续画了三个版本，为的是说清一句话：内存是全体线程共享的。

1.1 一个进程的两种画法原第 3–4 页

视图公式（课件原话）「上下文」里装了什么
传统视图Process = process context + code, data, and stack程序上下文：栈、数据寄存器、条件码、栈指针 SP、程序计数器 PC
内核上下文：VM 结构、描述符表、brk 指针
替代视图Process = thread + code, data, and kernel context线程上下文：栈、数据寄存器、条件码、SP、PC —— 只此一份，就是主线程

替代视图的价值在于可扩展：把「线程上下文」这一块复制几份，就得到一个多线程进程 —— 代码、数据、堆、共享库都还是同一份。

1.2 多线程进程：私有什么，共享什么原第 5–6 页

  • 多个线程可以和同一个进程关联（associated with a process）；
  • 每个线程有自己的逻辑控制流；
  • 每个线程共享同一份代码、数据和内核上下文；
  • 每个线程有自己的栈用来放局部变量 —— 但不受其他线程保护（原话：but not protected from other threads）；
  • 每个线程有自己的线程 ID（TID）。
别被画法骗了
原第 6 页的标题就是 Don't let picture confuse you!，页脚一句话写死了结论：Memory is shared between all threads。示意图里把「线程 1 的栈」和「线程 2 的栈」画成两个分开的方块，只是逻辑上分开；它们同在一个进程虚拟地址空间里，任何线程都能读写别人的栈。
交互：点击内存区段，看它属于线程私有还是全体共享 （对应原第 5、11、12 页三张示意图）

1.3 线程 vs. 进程原第 7 页

相似点（similarities）
  • 每个都有自己的逻辑控制流
  • 每个都能与其他执行流并发运行
  • 每个都由内核调度、被内核做上下文切换
差异（differences）
  • 线程共享代码和数据，进程（通常）不共享
  • 线程比进程开销更小：进程控制（创建与回收）比线程控制贵；进程的上下文切换也比线程贵

1.4 线程设计的利与弊原第 8 页

+ 好处
线程之间共享数据结构很容易（例如日志信息、文件缓存）；线程比进程更高效。
− 代价
无意的共享（unintentional sharing）会引入微妙且极难复现的错误。这正是本讲后半程要解决的事 —— 而且「难复现」三个字毫不夸张：第 3 节会把所有合法交错穷举出来，你会看到出错的那些只占一部分，全靠调度器的脸色。
交互：判断题 —— 线程到底共享了什么

2. 共享变量与线程内存模型原第 10–22 页

「全局变量共享、栈变量私有」是一条近似正确但会害人的经验法则。原第 10 页给出的定义是严格的：变量 x 是共享的，当且仅当多个线程引用了 x 的某个实例。要判断共享，必须回答三个问题：线程的内存模型是什么？变量的实例怎么映射到内存？每个实例可能被多少线程引用？

2.1 共享的定义原第 10 页

x 是共享的 ⟺ 有多个线程引用了 x 的至少一个实例（instance）

注意定义里的两个词：多个线程、某个实例。同一个变量名可能对应多个实例（每次函数调用、每个线程的栈各一份），共享与否要看实例被谁引用了。

2.2 概念模型 vs 实际模型原第 11–12 页

概念模型（Conceptual）实际模型（Actual）
线程私有线程 ID、栈、栈指针、PC、条件码、通用寄存器只有寄存器值是真正分离且受保护的
全体共享进程虚拟地址空间的代码段、数据段、堆、共享库段；打开的文件与已安装的处理函数同上，并且任何线程都能读写其他线程的栈
概念模型与实际模型的错位，正是困惑与错误的来源
原第 12 页的结语：The mismatch between the conceptual and operation model is a source of confusion and errors。
换句话说：「栈是私有的」只是逻辑约定，不是硬件保护。所以把局部变量的地址交给别的线程（下一小节就要看到），编译器不会拦你，内核也不会拦你，错误只会在运行时以数据竞争的形式出现。

2.3 给线程传参的三种写法（外加一个反面教材）原第 13–17 页

原课件用一个例子讲了四遍：hist[] 是全局数组，main 开 N 个线程，每个线程要把自己的编号写进 hist[编号] += 1，最后检查每个桶是否恰好被写过一次。差别只在「编号」这个参数怎么传进去。

2.4 变量实例到内存的映射原第 19–20 页

类别定义（课件原话）实例数
全局变量声明在函数外面的变量虚拟内存里恰好一份（如 ptr，位于数据段）
局部变量声明在函数里面、且不带 static 属性的变量每个线程的栈上各一份（如 i.m、msgs.m、线程里的 myid）
局部静态变量声明在函数里面、带 static 属性的变量虚拟内存里恰好一份（如 cnt，也位于数据段）

于是同一份程序里的局部变量 myid 就有了多个实例：主线程栈上有它的调用点，每个 peer 线程的栈上各有一份被 thread 函数使用的拷贝。原第 20 页给这些实例起的名字就是 myid.p0、myid.p1（p = peer）。

这一节最容易翻车的两个点
其一：cnt 是 thread() 里的 static 局部变量，名字听着「局部」，实体却只有一份、被两个 peer 线程同时读写 —— 它就是下一节 badcnt.c 里那个被争抢的计数器。
其二：判断共享看的是实例被谁引用，不是看变量名。两个线程各自引用不同实例（myid.p0 与 myid.p1）不算共享；两个线程引用同一实例（cnt）才算。

3. 竞争、交错与不安全轨迹原第 24–30、36 页

原第 24 页只有一句话：共享变量很方便，但它引入了棘手的同步错误。第 25 页立刻给出第一个受害者 —— badcnt.c：两个线程各把自己的计数器加 N 次，结果应该是 2N，可它时不时会打印一个别的数。

3.1 第一个出错的程序原第 25、36 页

badcnt.c —— 全局计数器与线程例程
/* Global shared variable */
volatile long cnt = 0;   /* Counter */

/* Thread routine */
void *thread(void *vargp)
{
    long i, niters =
        *((long *)vargp);

    for (i = 0; i < niters; i++)
        cnt++;

    return NULL;
}
main —— 创建两个线程并检查结果
int main(int argc, char **argv)
{
    long niters;
    pthread_t tid1, tid2;

    niters = atoi(argv[1]);
    Pthread_create(&tid1, NULL,
                   thread, &niters);
    Pthread_create(&tid2, NULL,
                   thread, &niters);
    Pthread_join(tid1, NULL);
    Pthread_join(tid2, NULL);

    /* Check result */
    if (cnt != (2 * niters))
        printf("BOOM! cnt=%ld\n", cnt);
    else
        printf("OK cnt=%ld\n", cnt);
    exit(0);
}
linux> ./badcnt 10000  →  OK cnt=20000
linux> ./badcnt 10000  →  BOOM! cnt=13051

同一个程序、同一个参数，两次运行结果一个对一个错。原课件在这一页的右下角只留了一个问题：What went wrong?（cnt 本该等于 20,000。）

3.2 cnt++ 的机器级真相原第 26 页

一句 cnt++ 编译出来是三条指令。原课件把它们命名为 L（Load）、U（Update）、S（Store），另外加上循环头 H（Head）与循环尾 T（Tail）：

标记含义x86-64 汇编
HiHead：循环条件判断movq (%rdi),%rcx · testq %rcx,%rcx · jle .L2 · movl $0,%eax
LiLoad：把 cnt 读进 %rdxmovq cnt(%rip),%rdx
UiUpdate：把 %rdx 加一addq $1,%rdx
SiStore：把 %rdx 写回 cntmovq %rdx,cnt(%rip)
TiTail：%rax 自增、比较、跳回 .L3addq $1,%rax · cmpq %rcx,%rax · jne .L3
%rdx 是线程私有的
%rdx 在每个线程自己的上下文里各有一份（原第 27 页的记号 %rdxi 指线程 i 的那份）。所以覆盖不是发生在寄存器上，而是发生在写回 cnt 的那一刻：两个线程各自算出了自己的新值，后写的那个把先写的抹掉了。

4. 进度图与临界区原第 31–35、37 页

要在 252 种交错里一眼看出「哪些会错」，靠列表是看不完的。原第 31–33 页给出一张图：把两个线程的指令顺序各当作一根坐标轴，交点就是执行状态，轨迹就是一次并发执行。

4.1 进度图（progress graph）原第 31 页

  • 两条轴分别对应该线程内指令的顺序；
  • 每个点对应一个可能的执行状态 (Inst1, Inst2)；
  • 例如 (L1, S2) 表示「线程 1 已完成 L1，线程 2 已完成 S2」。

坐标轴上的状态点依次记为 初始 · H · L · U · S · T（初始 = 什么都没执行）。沿轴每前进一步 = 该线程完成一条指令，所以一次执行在图上是只向右或向上走的一条折线。

4.2 轨迹（trajectory）原第 32–33 页

课件的定义：轨迹是一串合法的状态转移，描述多个线程的一次可能的并发执行。它给的例子是

H1, L1, U1, H2, L2, S1, T1, U2, S2, T2

把它换成图上的语言：从 (0,0) 出发，每执行一条线程 1 的指令就右移一格、每执行一条线程 2 的指令就上移一格，终点是 (5,5)。于是 —— 一次交错 ↔ 一条单调轨迹，一一对应，条数都是 252。

4.3 临界区与不安全区原第 34–35 页

课件指出：L、U、S 三条指令对共享变量 cnt 构成一个临界区（critical section），临界区里的指令不应该交错；把这些交错对应的状态画出来，就是图中的不安全区（unsafe region）。

术语定义（课件原话的翻译）
临界区对某个共享变量而言，L、U、S 这三条指令构成的整体（wrt cnt）
不安全区「两个线程都在自己的临界区里」的那些状态构成的集合
安全轨迹定义：轨迹是安全的（safe），当且仅当它不进入任何不安全区
正确性判据论断：一条轨迹对 cnt 而言是正确的，当且仅当它是安全的

「都在临界区里」要精确到状态：线程处于已执行 L、尚未执行 S 的状态（即状态 L 或 U）才算在临界区里。于是不安全区是 {L,U} × {L,U} 这 2×2 = 4 个状态（课件图上就是那块被标了 Unsafe region 的阴影）。

勘误：课件图上的阴影画大了一圈
原第 34–35 页的进度图里，阴影区看起来盖住了 L、U、S 三列三行。本页按 2×2 呈现，理由是这可以穷举验证：把 252 条轨迹全部走一遍，判据「不进入 {L,U}²」与判据「最终 cnt == 2」逐条一致（0 条例外）；而换成 3×3 的 {L,U,S}² 会有 40 条轨迹被误判为不安全。第 4.4 节的交互组件就在页面里现场跑这个穷举。

问：怎样保证轨迹是安全的？
答：必须同步（synchronize）线程的执行，使它们永远走不出不安全轨迹 —— 也就是必须保证每条临界区都互斥访问（mutually exclusive access）。

5. 信号量与 P/V 操作原第 39–41、43、49 页

安全轨迹靠「让临界区不交错」来保证，而这件事需要一个由内核兜底的原子操作。Dijkstra 给出的答案是信号量（semaphore）：一个非负的全局整型同步变量，只允许用 P 和 V 两个操作来碰它。

5.1 信号量的定义原第 39 页

Semaphore
一个非负的全局整型同步变量，只能通过 P 与 V 两个操作来操纵。
不变量（semaphore invariant）：s >= 0 —— 这是整套机制的地基，后面所有「禁区」都是从它推出来的。
P(s)：等待/上锁
  • 如果 s 非零：把 s 减 1，立即返回；
  • 「测试」和「减一」原子地（原子、不可分割地）发生；
  • 如果 s 为零：挂起该线程，直到 s 变成非零，并由某个 V 操作把它重启；
  • 被重启后，这个 P 操作完成「减 1」并把控制权交回调用者。
V(s)：发信号/解锁
  • 把 s 加 1；
  • 「加一」也是原子的；
  • 如果有线程正阻塞在 P 上等待 s 变成非零，就恰好重启其中一个，让它完成自己的 P（减 1）。

5.2 伪代码与名字的来历原第 40 页

P(s):  [ while (s == 0) wait(); s--; ]
V(s):  [ s++; ]
  • P 来自荷兰语 Proberen（测试）；V 来自 Verhogen（增加）。
  • 操作系统内核保证方括号 [ ] 里的操作不可分割地执行：
  • 任一时刻只有一个 P 或 V 能修改 s；
  • 当 P 里的 while 循环结束时，只有那个 P 能执行 s--。
这两条保证少了任何一条，互斥就废了
「测试与减一是原子的」这句话不是修辞。第 5.4 节的交互组件会把非原子版本的所有交错穷举一遍，你会看到 s 掉到 −1，直接把信号量不变量打破。

5.6 互斥的术语表原第 43 页

术语含义

互斥锁（mutex）用来做互斥的二元信号量

5.7 互斥锁（mutex）是信号量的特例原第 49 页

  • mutex 是信号量的特例：取值只能是 0 或 1；
  • Pthreads 提供了专门的类型 pthread_mutex_t，操作是 lock 与 unlock；
  • 在合适的场合，推荐优先使用 mutex 而不是通用信号量 —— 语义更清楚，实现也更省。

6.3 为什么互斥锁有效原第 45–48 页

7.4 代码原第 55–56 页

共享结构体与主程序（初始化是 empty = 1、full = 0）
#include "csapp.h"
#define NITERS 5

void *producer(void *arg);
void *consumer(void *arg);

struct {
    int buf;      /* shared var */
    sem_t full;   /* sems */
    sem_t empty;
} shared;

int main(int argc, char** argv) {
    pthread_t tid_producer;
    pthread_t tid_consumer;

    /* Initialize the semaphores */
    Sem_init(&shared.empty, 0, 1);
    Sem_init(&shared.full,  0, 0);

    /* Create threads and wait */
    Pthread_create(&tid_producer, NULL, producer, NULL);
    Pthread_create(&tid_consumer, NULL, consumer, NULL);
    Pthread_join(tid_producer, NULL);
    Pthread_join(tid_consumer, NULL);

    return 0;
}
生产者线程
void *producer(void *arg) {
    int i, item;

    for (i=0; i<NITERS; i++) {
        /* Produce item */
        item = i;
        printf("produced %d\n", item);

        /* Write item to buf */
        P(&shared.empty);
        shared.buf = item;
        V(&shared.full);
    }
    return NULL;
}
消费者线程
void *consumer(void *arg) {
    int i, item;

    for (i=0; i<NITERS; i++) {
        /* Read item from buf */
        P(&shared.full);
        item = shared.buf;
        V(&shared.empty);

        /* Consume item */
        printf("consumed %d\n", item);
    }
    return NULL;
}

7.5 单槽为什么也要两个信号量原第 57 页

课件在这里推了一步：把场景换到多个生产者 + 多个消费者。

  • 生产者之间要互相竞争同一个「空」（只有一个槽位）；
  • 消费者之间要互相竞争同一个「满」（只有一个元素）；
  • 所以两个角色需要各自的一条队列 —— 这就是 empty 与 full 两个信号量各司其职的原因。
课件这一页的对照
Producers            Consumers
P(&shared.empty);    P(&shared.full);

V(&shared.full);     V(&shared.empty);
一句话
「有没有地方放」与「有没有东西取」是两件独立的事，用两个信号量分别记录，生产者和消费者才各自知道该等谁。这也解释了第 8 节为什么要往 sbuf 里再塞一个 mutex：slots 管槽位数量，items 管元素数量，mutex 管对缓冲区本身的互斥访问。

8. 环形缓冲区与 sbuf 包原第 58–67 页

单槽缓冲只是玩具。真实系统里缓冲区要能存 n 个元素，于是在数组上绕圈 —— 这就是环形缓冲区（circular buffer），也是 CS:APP 的 sbuf 包要解决的事。

8.1 n 槽缓冲需要什么原第 58、62 页

P₁ … Pₙ  →  缓冲区（0 到 n 个元素）  →  C₁ … Cₘ

原第 62 页把需求列全了：一个 mutex + 两个计数信号量。

同步变量作用取值范围
mutex强制对缓冲区及其计数器的互斥访问0 / 1
slots统计缓冲区里还可用的槽位数0 … n
items统计缓冲区里可用的元素数0 … n

8.2 环形缓冲区的约定原第 59–60 页

  • 元素存在大小为 n 的数组里；items = 缓冲区里元素的个数；
  • 空缓冲区：front == rear；
  • 非空缓冲区：rear 是最近插入的元素的索引，front 是下一个要删除的元素的索引减一（对 n 取模）—— 也就是说「下一个要取的」在 front+1；
  • 初始时 front = rear = items = 0。

课件用一组操作把这三个计数器演了一遍：插入 7 个、删除 5 个、插入 6 个、删除 8 个。本页的模拟器对这一组操作逐步核对课件第 60 页印出的 front / rear / items（数字是原文引用，比对在页面里做）。

8.3 顺序版代码原第 61 页

单线程（顺序）版本的 init / insert / remove
init(int v)
{
    items = front = rear = 0;
}

insert(int v)
{
    if (items >= n)
        error();
    if (++rear >= n) rear = 0;
    buf[rear] = v;
    items++;
}

int remove()
{
    if (items == 0)
        error();
    if (++front >= n) front = 0;
    int v = buf[front];
    items--;
    return v;
}

注意 insert 里先 ++rear 再判断越界、remove 里先 ++front 再判断 —— 这正是「front 指向最近删除的元素、rear 指向最近插入的元素」这套约定的由来。

8.4 sbuf 包原第 63–66 页

把「环形缓冲区 + 三个同步变量」封成一个可复用的包。这是本讲最完整的一段代码，四个函数刚好演示了 P/V 的顺序为什么这么排。

sbuf.h —— 声明
#include "csapp.h"

typedef struct {
    int *buf;     /* Buffer array              */
    int n;        /* Maximum number of slots   */
    int front;    /* buf[front+1 (mod n)]
                     is first item            */
    int rear;     /* buf[rear] is last item    */
    sem_t mutex;  /* Protects accesses to buf  */
    sem_t slots;  /* Counts available slots    */
    sem_t items;  /* Counts available items    */
} sbuf_t;

void sbuf_init(sbuf_t *sp, int n);
void sbuf_deinit(sbuf_t *sp);
void sbuf_insert(sbuf_t *sp, int item);
int  sbuf_remove(sbuf_t *sp);
sbuf.c —— 初始化与释放
/* Create an empty, bounded, shared
   FIFO buffer with n slots */
void sbuf_init(sbuf_t *sp, int n)
{
    sp->buf = Calloc(n, sizeof(int));
    sp->n = n;      /* Buffer holds max
                       of n items */
    sp->front = sp->rear = 0;
                    /* Empty iff
                       front == rear */
    Sem_init(&sp->mutex, 0, 1);
                    /* Binary semaphore */
    Sem_init(&sp->slots, 0, n);
                    /* Initially n slots */
    Sem_init(&sp->items, 0, 0);
                    /* Initially no items */
}

/* Clean up buffer sp */
void sbuf_deinit(sbuf_t *sp)
{
    Free(sp->buf);
}
sbuf_insert —— 放入一个元素
void sbuf_insert(sbuf_t *sp, int item)
{
    P(&sp->slots);   /* Wait for slot  */
    P(&sp->mutex);   /* Lock the buffer */
    if (++sp->rear >= sp->n)
        sp->rear = 0;               /* mod n */
    sp->buf[sp->rear] = item;
    V(&sp->mutex);   /* Unlock        */
    V(&sp->items);   /* Announce item */
}
sbuf_remove —— 取出一个元素
int sbuf_remove(sbuf_t *sp)
{
    int item;
    P(&sp->items);   /* Wait for item */
    P(&sp->mutex);   /* Lock the buffer */
    if (++sp->front >= sp->n)
        sp->front = 0;              /* mod n */
    item = sp->buf[sp->front];
    V(&sp->mutex);   /* Unlock        */
    V(&sp->slots);   /* Announce slot */
    return item;
}
读这两段代码时要盯住的三件事
其一：P(slots) 在 P(mutex) 之前 —— 先在「计数信号量」上排队，抢到名额后才去抢锁；顺序反了（先锁住缓冲区再等槽位）会让持锁的线程睡着，谁都进不来。
其二：V(mutex) 在 V(items) 之前 —— 先交还缓冲区的独占权，再宣告「多了一个元素」。
其三：缓冲区的不变量是 items + slots == n，下面这个组件会在每次随机交错执行后检查它。
交互：sbuf 交错不变量检测器

9. 总结与自测原第 68 页

原课件最后一页只有三条结论，本讲的全部内容都挂在这三条上。

① 模型

程序员需要对「变量如何被线程共享」有一个清晰的模型 —— 共享与否看的不是变量名，而是实例被多少线程引用。

② 保护

被多个线程共享的变量必须加以保护，以保证对它们的互斥访问 —— 否则 cnt++ 就会变成 BOOM! cnt=13051。

③ 机制
